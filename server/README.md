# kinige-server: the sync server

Spikes S4c-1 (KINIG-98, `docs/slices/S4c1-server-core.md`, `docs/adr/0019-s4c1-server-core.md`) and S4c-2 (KINIG-99, `docs/slices/S4c2-blobs-backup-compose.md`, `docs/adr/0020-s4c2-blobs-backup-compose.md`); HTTP shapes in ADR-0001 appendix §A.6. A workspace member, production code, Linux first: a lib and the binary `kinige-server`.

What it does: accounts and sessions (ADR-0001 §8.3-§8.7), push and pull of envelopes with `seq` issued under an account lock (§6, §A.3, §A.4), compaction (§10.2), **blobs** (§7, §A.2) on a disk or an S3-compatible store, **backup and restore** (§6.3, PRD §10.1), **account deletion** (§8.9), and the stack to run all of it (`deploy/`). It reads the open header of an envelope and nothing inside it, and the blob store holds ciphertext.

## Layout
- `src/rules/`: the decisions, as plain functions with unit tests and no database. `push.rs` is the check order of §A.4, `pull.rs` the stale rule with drops stored with their generation, the placement of a generation outside the lineage by the cut time of the fork of the device's lineage (§6.3, ADR-0017), `compact.rs` the plan of §10.2, `blob.rs` the framing of §A.2, the plan of an upload request, the `Range` header and the delayed removal.
- `src/store/`: Postgres only. It reads the facts, calls a rule, writes. `envelopes.rs` is push and pull, `accounts.rs` the credential flows, `compact.rs` applies a compaction plan, `sessions.rs` the tokens, `blobs.rs` the `blobs` table, `delete.rs` the deletion of an account, `credentials.rs` the credential journal, `lock.rs` the backup lock, the stamps (the database's clock, floored at the newest cut) and the server's own session lock (why they exist is in its header).
- `src/blobs/`: `objects.rs` (the object store behind one small interface: the disk with `fsync`, or any S3-compatible store, via the `object_store` crate), `staging.rs` (unfinished uploads are files), `sweep.rs` (the delayed physical deletion), `settings.rs`.
- `src/backup/`: `create.rs` (a backup), `rotate.rs` (the rotation), `restore.rs`, `journal.rs` (the deletion and credential journals: dump, read from a backup, from the installation and from a neighbour), `manifest.rs`.
- `src/api/`: the axum router and the handlers (`blobs.rs`, `body.rs` for the read timeout). `src/wire.rs`: the push body and its reader. `src/dto.rs`: the JSON bodies. `src/cli.rs`: `serve`, `backup`, `restore`.
- `migrations/`: the schema, embedded in the binary and applied at start (also by concurrent starts, under an advisory lock). `0001` is S4c-1, `0002` adds `blobs`, `deletions` and the cut time of a generation, `0003` the credential journal. A backup names its schema and a restore of another schema is refused; **slice 11 must settle the step from schema N to N+1** (a restore of an older backup into a newer server: restore it with the server version that took it, or give the restore a migration list that upgrades the dump), because an installation will outlive several migrations and its backups with it.
- `src/testing.rs` (feature `testing`): a throwaway database, a blob store and staging directory per test, an in-process client of the router, synthetic credentials. The S4a simulation uses them.
- `examples/smoke.rs`: the client of `deploy/smoke.sh`.

## Run
```text
openssl rand -hex 32 > server-secret          # 64 hex characters; keep it, an unknown login's salt is derived from it
KINIGE_DATABASE_URL=postgres://user:password@host:5432/kinige \
KINIGE_SERVER_SECRET_FILE=./server-secret \
KINIGE_BLOB_DIR=./blobs \
KINIGE_LISTEN=127.0.0.1:8080 \
cargo run --release -p kinige-server
```
TLS is not terminated here: a reverse proxy does it (`deploy/Caddyfile`). Postgres 17 is the tested version. The binary also takes two commands, `kinige-server backup <dir> [--prune]` and `kinige-server restore <backup directory>`, with the same environment.

## Self-hosting with `docker compose`
`deploy/` holds a multi-stage `Dockerfile` (a non-root user, both base images pinned by digest, SIGTERM stops the server with exit code 0), a `docker-compose.yml` (the server, `postgres:17` pinned by digest, a volume for blobs, a volume for backups, an optional S3 store through environment variables, healthchecks, and a Caddy reverse proxy with TLS), `.env.example` (placeholders only), `backup.cron.example` and `smoke.sh`.
```text
cd deploy
cp .env.example .env        # then fill in POSTGRES_PASSWORD (openssl rand -hex 24), KINIGE_SERVER_SECRET (openssl rand -hex 32), KINIGE_DOMAIN
docker compose up -d --build
docker compose --profile tools run --rm backup                       # a backup, and rotation of the ones older than 30 days
docker compose stop server proxy                                     # a restore is done with the server stopped
KINIGE_RESTORE_FROM=/backups/backup-<time> docker compose --profile tools run --rm restore
docker compose up -d
```
- **TLS.** With a public name in `KINIGE_DOMAIN` and ports 80 and 443 reachable, Caddy gets a Let's Encrypt certificate by itself; `localhost` gives its own local certificate, which is for trying the stack out. The TLS setup is documented and not tested beyond startup (the smoke test connects over it, accepting the local certificate).
- **Body limits.** The proxy refuses a body above the server's caps before the server reads a byte: 16 MiB for a push, 256 MiB for one blob upload request (a larger file goes in several requests, resuming by offset), 16 KiB for everything else. With nginx the same is `client_max_body_size` per `location`.
- **Docker is not local.** `docker compose` sends the build context to the daemon; nothing is bind-mounted from the machine that runs the command, so a remote daemon works (that is how it was tried). The server secret therefore comes from `.env` as a Compose secret (a file inside the container), not from a file path.
- **The smoke test** (`deploy/smoke.sh`, CI job `compose`) brings up a first stack, registers, pushes, uploads a blob in two parts, pulls, checks that the proxy refuses an oversize push body, takes a backup, stops the server with SIGTERM (exit code 0), brings up a SECOND stack with a fresh database and an empty blob volume, restores the backup into it, and checks that the old cursor gets `GenerationChanged` with the lineage and the cut time of the new generation, that every envelope is the same bytes and that the blob downloads byte for byte. Locally it uses whatever `docker` points at; its containers, volumes and images are prefixed `kinige-s4c2-smoke` and are removed on exit.

## Configuration
Everything comes from environment variables.
- `KINIGE_DATABASE_URL` (required): `postgres://user:password@host:port/database`. No TLS to the database, which sits next to the server.
- `KINIGE_SERVER_SECRET_FILE` (required): a file with 64 hex characters (32 bytes), the `server_secret` that keys the salt returned for an unknown login (§8.4).
- `KINIGE_LISTEN` (default `127.0.0.1:8080`): the address to listen on.
- `KINIGE_COMPACT_EVERY_SECS` (default `3600`): how often every account's log is compacted and the blob sweep runs.
- `KINIGE_CLIENT_ADDR_HEADER` (default none): the name of a header that a trusted reverse proxy sets to the client's address, for the rate limits. Without it the connection's address is used. **If you set it, bind `KINIGE_LISTEN` to the proxy's interface only** (a loopback or a private address the proxy reaches): a client that can connect directly can send that header itself and take a fresh per-address budget on every request. In the compose stack the server is not published, the proxy sets `X-Real-IP`.
- `KINIGE_LOG` (default `info`): `error`, `warn`, `info`, `debug` or `trace`, for the server's own records. Other crates are held at `warn`.
- `KINIGE_BLOB_DIR` (default `./blobs`): objects are in `<dir>/objects` on a disk store; unfinished uploads are always in `<dir>/staging`, also with an S3 store, because the offset of a resumable upload does not map onto S3 parts.
- `KINIGE_S3_BUCKET` (default none; setting it selects S3), `KINIGE_S3_ENDPOINT` (`https://host:port`, none means Amazon), `KINIGE_S3_REGION` (default `us-east-1`), `KINIGE_S3_ACCESS_KEY`, `KINIGE_S3_SECRET_KEY` (both required with a bucket), `KINIGE_S3_ALLOW_HTTP` (`1` for plain HTTP to a store on the private network). Path-style addressing.
- `KINIGE_BLOB_QUOTA_GIB` (default `10`): what one account may keep in blobs, published and being uploaded.
- `KINIGE_BACKUP_RETENTION_DAYS` (default `30`, Q14) and `KINIGE_BACKUP_INTERVAL_HOURS` (default `24`): backups older than the first are rotated by `backup --prune`; a deleted blob leaves the store when it is older than the first plus the second.
- `KINIGE_TEST_DATABASE_URL`, `KINIGE_TEST_S3_URL`, `KINIGE_TEST_S3_BUCKET`, `KINIGE_TEST_S3_ACCESS_KEY`, `KINIGE_TEST_S3_SECRET_KEY`, `KINIGE_TEST_REQUIRE_S3` (tests only, see below).

Fixed limits (`src/config.rs`; real numbers are slice 11's):
- Push body: 16 MiB and at most 1000 envelopes per request; an envelope is at most `MAX_ENVELOPE`.
- A blob: at most the sealed length of a 2 GiB file (PRD §4.2), one upload request at most 256 MiB.
- A request body that is quiet for 20 s, or whose average rate is under 8 KiB/s after 10 s, is cut off with `408` (push and blob upload).
- Account JSON bodies: 16 KiB.
- Pull page: 200 envelopes by default, at most 1000, and the page stops at 8 MiB (the first envelope always goes).
- Login attempts: 10 a minute per login and 60 a minute per client address.
- Word checks (the recovery fetch and the recovery share one budget): 5 a minute per login and 30 a minute per client address.

The rate limits are fixed windows in memory. Every attempt counts, a known and an unknown login alike, and an excess is a `429` with `Retry-After`. A restart empties them. Behind a reverse proxy without `KINIGE_CLIENT_ADDR_HEADER` every client has the proxy's address, so only the per-login budget separates them.

## Backups
`kinige-server backup <dir>` writes `<dir>/backup-<cut time>/` (first as `.tmp-…`, renamed when the manifest is on disk, so a directory that did not finish is never used):
- `tables/*.copy`: the server's own dump, one text `COPY` per table (`accounts`, `envelopes`, `ops`, `entity_known`, `purged_entities`, `drops`, `blobs`), taken in **one `REPEATABLE READ` snapshot**; text and not `pg_dump` so that a restore needs no client of a matching version and no binary format of one Postgres major;
- `lineage.json` (the generations and their cut times), `deletions.json` (the deletion journal), `credentials.json` (the credential journal);
- `blobs/<account_id>/<blob_id>`: the object of every published, not deleted blob (a hard link to the same file of the newest earlier backup when there is one, **after its hash was checked** against that backup's manifest: objects never change, but a damaged file is not carried forward; a file that does not match is copied from the store instead);
- `manifest.json`, written last: the format, the schema, the **cut time**, and the length and BLAKE2b hash (`crypto_generichash`) of every file.

Left out on purpose: **sessions** (a restore must not bring back a session that a logout, a password change or a recovery had ended; every device logs in again) and unfinished uploads (files in the staging area; the client resumes at what `GET /v1/blobs/{id}/status` says, which after a restore is 0).

`--prune` removes the backups whose cut time is older than the retention, **keeping the newest whatever its age** (so a server whose cron stopped keeps its last backup; a backup with a deleted account's data therefore lives until the next backup replaces it and the retention has passed, ADR-0001 §8.9, PRD §10.3), and half-written directories older than a day. A directory that is not a valid backup is never touched. Run it from cron at the interval `KINIGE_BACKUP_INTERVAL_HOURS` says (`deploy/backup.cron.example`) and copy the backups volume off the machine.

**Why a backup taken during writes restores (ADR-0020).** Two facts: a blob is immutable after publication, and the delete of a blob only marks it (the object leaves the store after the retention plus one interval, so every object a row of any restorable backup refers to is still there when the backup copies it); and the cut time is read under the backup lock (`store/lock.rs`), so the stamp of every compaction, account deletion and credential change is below the cut time exactly when it is inside the snapshot. The stamps are the database's `clock_timestamp()` read in the locked transaction, never below one more than the newest cut of the lineage. A blob published after the snapshot is not in it and is not copied.

## Restore
`kinige-server restore <backup directory>`, in place or into a clean installation, **by one code path**. **The server must be stopped:** a running `serve` holds a session advisory lock on the database for its life, and `restore` takes it with `pg_try_advisory_lock`; if it cannot, it refuses to run (`ServerRunning`) and changes nothing. A session lock dies with its connection (a Postgres restart, a network cut), so `serve` supervises it: when the connection ends it takes the lock again, and if a restore got it first, `serve` exits with an error and stops serving. **The restore's own lock is on the connection that writes:** the load transaction runs on the connection that holds the lock, so if that connection ends mid-restore, the lock and the transaction end together, nothing is replaced, and the restore stops with an error that says it lost its lock (the objects it copied into the store are removed again). A server that starts in that gap keeps serving the installation as it was. If the connection ends during the `COMMIT`, whether the database was replaced is not known: the error says so, and the copied objects are kept (a rerun finds them by hash).1. the manifest, the schema and every dump file (length and hash) are checked **before anything is changed**; a cut manifest, a missing dump file, a flipped byte or a path that leaves the directory is refused. A **blob** file that is missing or does not match its hash does not stop the restore (one bad file must not make every backup unrestorable): its row is marked deleted, its device finds the attachment `missing`, the restore ends with an error line (the category, never the id) and a **non-zero exit**. In place, a blob whose backup file is damaged but whose object the store still holds with the manifest's hash keeps its row and its object: only a blob that exists nowhere is lost;
2. the target database is migrated (a clean one gets its schema); the dump's objects go into the store. An object already there is kept **only if its hash is the manifest's**, not by size: an in-place restore replaces a damaged object of the right size. If the restore fails, the objects it put are removed again;
3. in **one transaction**: the tables are emptied and loaded from the dump, the lineage is loaded (trimmed to the newest 64) and a fresh generation is appended with the backup's **cut time**, the deletion and credential journals are re-applied (below), sessions are gone; a failure rolls everything back;
4. every object in the store that no restored row refers to (a blob published after the backup) becomes a deleted blob, and goes the delayed way. This step runs after the commit: if it fails, the restore is done and the failure is a **warning** (the sweep finds the objects later), not an error that reports a finished restore as failed.

After a restore every client's pull is answered `GenerationChanged` with the lineage and resyncs; the branch-cut rule (ADR-0001 §6.3, ADR-0017) uses the lineage to find where a device on an abandoned branch forked and decide whether it missed a drop. Devices re-upload the blobs they published after the backup (the trigger, a status check after `GenerationChanged`, is in ADR-0001 §7 for slice 11).

**Account deletion (§8.9).** `POST /v1/account/delete` (session and the password's `auth_key`) deletes the account, its wraps, hashes, sessions, envelopes, `op_id`s and indexes in one transaction, marks its blobs deleted (the objects stay the retention plus one interval, like any deleted blob), and writes `generichash(account_id)` and the time to the deletion journal. A restore re-applies every journal entry at or after the backup's cut time whose account is in the restored data. The journal is the union of the backup's, the replaced installation's and the newest other backup's next to it, the last read only if it verifies against its own manifest: restoring an old backup alone into a clean installation, with no later backup beside it, brings the account back (the limit of the rule, pinned by a test). A deleted account id is **never registered again** (`409 account_id_taken`), so one entry per account is enough.

**Credentials (§8.9).** A password change, a recovery and new words each write the credential state after the change to the credential journal, in the same transaction and under the shared backup lock. A restore puts the newest entry at or after the cut time (from the same three sources) back on each restored account: a password changed after a backup is not the old one again. A change that none of the three sources knew of is lost; sessions are never restored, so every device logs in again. Two changes never share a stamp (it is raised above the account's newest entry), and the sweep removes the retired entries after the retention plus one backup interval, like a deleted blob, **except the newest entry of each account** (it holds what the account holds now, and the newest backup needs it however old that backup is): an old password's wrap does not stay in the database for longer than that.

## Logs
`log` only, to stderr, one line per record: event kinds, ids and error categories. No request body, token, key or envelope byte is ever formatted into a record (ADR-0001 §8.8); a blob id is not in a record either (the path of a request is logged only when it is a plain route). Dependencies are held at `warn` at every level, because `tokio-postgres` logs every statement with its bound parameters at `debug`; the plain-text scan found it (ADR-0019).

**Postgres's own log is a third channel, and the tests do not read it.** On an error Postgres writes the value that clashed (`DETAIL: Key (login)=(...) already exists`) and, with other settings, whole statements with their parameters. The server does not provoke the first one in normal operation (registration serializes on the login and the account id with advisory locks, so a race does not reach the unique index), but the operator must protect Postgres's log like the server's own, keep `log_statement = none` and `log_parameter_max_length_on_error = 0`, and leave `log_min_duration_statement` off (it logs statements). The compose file sets all three.

### Accounts and sessions (§8.3-§8.7, §A.5)
`accounts.rs` covers registration and its idempotency, what the protocol refuses, an unknown login that looks like a known one (the answer and the log lines), the password change on a credential version (exactly one of six concurrent changes wins), the refusal of a lower profile on a change and on a recovery, `revoke_others`, recovery (the word check, one atomic replacement, every session ended, a repeat is a success, another package is a clash), new words, logout and the login that names the token it replaces, and the rate limits.

### The proofs of the spec
- **Appendix §B item 23 and PRD S4c, "the cursor does not skip records":** `concurrency::parallel_pushers_and_a_puller_never_skip_a_seq` runs 8 pushers (160 envelopes) and a puller with pages of 7 the whole time, 3 rounds; the `seq`s the puller collected equal the log. Negative control: `concurrency::control_seq_from_a_plain_sequence_without_the_lock_does_skip_records` runs the same race with `seq` from a plain Postgres sequence and no account lock, and the reader's cursor passes seqs that commit later. The control is raw SQL in the test; nothing like it is in the server.
- **PRD S4c, "no plain text in the server database":** `leak::nothing_the_user_wrote_and_no_secret_is_in_any_table_or_in_the_log`. Positive controls: `leak::the_scanner_finds_a_deliberate_leak_in_every_encoding`, and in the main test the scan finds the hashes, the salt, the login, a token hash and envelope bytes in the dump, finds a text planted in a table nobody listed, and finds a key appended to the log.
- **PRD S4c, "restore from a backup, clients do a full resync":** the S4a simulation against the real server (`spikes/S4a-sync/tests/real_server.rs`): property 8 with the restore mixes, the drop-epoch generator and the directed scenarios, every restore a real dump loaded into a clean database; a client-side control (`control_8_a_client_that_keeps_its_epoch_across_a_real_restore_fails`) shows the suite catches a breakage there.
- **Garbage:** `garbage::garbage_on_every_endpoint_is_a_4xx_and_never_a_5xx` sends random bytes, random JSON, the protocol's own field names with wrong values, and a real push body cut, flipped and extended, to every route, with and without a session.

## What is left

Known limits (ADR-0019, ADR-0020): no pool wait timeout; compaction loads the open metadata of one account into memory; `ops` and `drops` are never trimmed; rate limits are per process; one server process (the busy flag of an upload and the staging area are not shared); the backup copies every object it does not already have, so a first backup of a large store takes as long as copying it.
