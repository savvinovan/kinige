# ADR-0001: Протокол синхронизации и ключи

Дата: 2026-10-20. Статус: **предложено** — черновик для решения пользователя. Ревью `sync-crypto-guardian` и `codex-second-opinion` ещё не проводилось.
Основа: §4 и §10 ТЗ (`docs/plan/02-prd.md`, v0.6), `research/review-fable.md` п. 1–7, 13–16, `research/review-codex.md` п. 1–13, 16.
Нормативен ТЗ. Этот ADR конкретизирует то, что ТЗ оставил «на ADR», и ему не противоречит. Где ТЗ молчит или противоречит сам себе, это вынесено в раздел «Требует решения пользователя».

## Контекст

От этого ADR зависит локальная схема слайса 1: id, `hlc_json`, `schema_version`, `unknown_json`. Поэтому его нужно принять до слайса 1, хотя сервер появится только в слайсе 11.
Ограничения ТЗ: сервер не видит содержимого и не сливает его (§10.1). Слияние делают клиенты, по группам полей с HLC (§10.2). Удаление — обычная группа. Конверты неизменяемы. Пароль входа отделён от KEK, у DEK две обёртки (§10.3). Неизвестные поля сохраняются (§10.4).
Пробелы, которые ТЗ оставил открытыми и которые закрывает этот ADR:
- точный алгоритм HLC;
- что именно лежит в конверте;
- как отличить конфликт от последовательной правки;
- гонка «восстановление против `purged`»;
- как сервер проверяет ключ восстановления;
- атака понижения параметров Argon2;
- копирование базы с тем же `device_id`.

## Решение

### 1. Идентификаторы

| Что | Формат | Кто создаёт |
|---|---|---|
| Записи (chat, message, attachment, message_revision) | UUID v4, строка в нижнем регистре, 36 символов (§4.1) | устройство |
| Inbox | фиксированная константа, одна для всех аккаунтов (см. «Требует решения», п. 2) | код |
| Ревизия `reason='conflict'` | детерминированная, `uuid_from(BLAKE2b-keyed(K_rev, message_id ‖ hlc_проигравшей))`; биты версии и варианта ставятся как у v4 | любое устройство, одинаково на всех |
| `op_id` | UUID v4 | устройство при постановке в outbox |
| `device_id` | UUID v4, создаётся при первом запуске, лежит в `sync_state` | устройство |
| `account_id` | UUID v4 | сервер при регистрации |

**`device_id` уникален для экземпляра базы, а не для машины.** Восстановление базы из копии (ежедневная копия §2.1, Time Machine, импорт в режиме «восстановить») всегда создаёт новый `device_id`. Без этого две копии базы с одним `device_id` выдадут одинаковые HLC для разного содержимого, и сходимость сломается.
Как обнаружить копию: рядом с базой, но не в ней (в системном хранилище секретов), хранится второй экземпляр `device_id`. Если при старте они не совпали — это копия, и выдаётся новый `device_id`. Детали механизма уточняются в S4a.

### 2. HLC

**Формат** (по ТЗ §10.2): `{wall_ms:013}-{counter:05}-{device_id}`.
- `wall_ms` — десятичное число из 13 цифр. Его хватает до 2286 года.
- `counter` — от 00000 до 99999.
- `device_id` — 36 символов в нижнем регистре.
- Длина строки — 56 символов. Парсер строгий: строка с любым отклонением отвергается.

**Сравнение** — побайтовое сравнение строк. Из-за фиксированной ширины и нижнего регистра оно совпадает со сравнением кортежей `(wall_ms, counter, device_id)`. При равенстве `wall_ms` и `counter` решает `device_id`. Тест: сравнение строк и сравнение кортежей дают одинаковый результат на случайных парах.

**Алгоритм** — HLC из Kulkarni et al., 2014, рис. 5 (проверено по тексту статьи). `pt` — физическое время устройства в мс.
- **Локальное событие:** `l' = l; l = max(l', pt); c = (l == l') ? c + 1 : 0`.
- **Получение метки m:** `l' = l; l = max(l', l_m, pt)`. Затем:
  - если `l == l' == l_m`, то `c = max(c, c_m) + 1`;
  - иначе если `l == l'`, то `c = c + 1`;
  - иначе если `l == l_m`, то `c = c_m + 1`;
  - иначе `c = 0`.
- **Отступление от статьи:** если `c` превысил бы 99999, то `l = l + 1; c = 0`. Монотонность сохраняется, `l` лишь ненадолго обгоняет `pt`.

**Когда тикают часы:**
- каждая локальная правка группы `g` ставит `hlc[g] = now()`;
- при применении конверта часы получают максимальный HLC из его заголовка.

**Хранение.** Состояние `(l, c)` пишется в `sync_state` в той же транзакции, что и изменение. При старте берётся `l = max(сохранённое l, pt)`.

**Дрейф часов:**
- Пришедшая метка опережает `pt` больше чем на 10 минут — клиент показывает предупреждение, работа не блокируется (§10.2). Метка **принимается** в часы: иначе локальное восстановление записи проиграло бы «будущему» удалению, и пользователь не смог бы её восстановить (принцип 9).
- Защита от абсурдных меток — на сервере (см. «Требует решения», п. 5).

### 3. Записи, группы полей и слияние

**3.1. Конверт `upsert` несёт полный снимок записи: все группы, у каждой свой HLC.** Дельта (только изменённые группы) отвергнута по трём причинам:
- снимок самодостаточен, и устройство, у которого записи нет (после `purged` или полной пересинхронизации), может её воссоздать;
- слияние снимков коммутативно, ассоциативно и идемпотентно: это поэлементный максимум по группам, поэтому дубликаты, повторы и любой порядок дают одно состояние;
- сжатие на сервере и в outbox тривиально: конверт лишний, если по каждой его группе есть конверт с HLC не меньше.

Цена: смена флага заново шифрует тело. Сообщения короткие, размер выравнивается до 1 КБ — приемлемо.

**3.2. Группы.** Группа `core` пишется только при создании, её HLC — HLC создания. Производное (`body_search`, `day_activity`, `updated_at` чата, теги) не синхронизируется: каждое устройство пересчитывает его само (§4.1).

| Сущность | Группа | Поля |
|---|---|---|
| message | `core` | `created_at`, `created_tz`, `reply_to_id` |
| | `body` | `body_md`, `edited_at`, `base` (HLC версии `body`, от которой сделана правка; `null` при создании) |
| | `flags` | `is_task`, `task_done_at`, `favorite_at`, `pinned_at` |
| | `placement` | `chat_id`, `journal_date` |
| | `deleted` | `deleted_at` |
| chat | `core` | `created_at`, `is_inbox` |
| | `meta` | `title`, `icon`, `color` |
| | `order` | `sort_key` (при равных ключах порядок решает `id`) |
| | `state` | `pinned_at`, `archived_at` |
| | `privacy` | `ai_excluded` — отдельно, чтобы исключение из AI не потерялось при одновременном переименовании |
| | `deleted` | `deleted_at` |
| attachment | `core` | `message_id`, `kind`, `sha256`, `filename`, `mime`, `byte_size`, `width`, `height`, `duration_ms`, `url`, `link_title`, `link_site`, `remote_blob_id`, `blob_key` |
| | `order` | `sort_index` |
| | `deleted` | `deleted_at` |
| message_revision | `core` | `message_id`, `snapshot_json` (все группы сообщения вместе с их HLC), `saved_at`, `reason` |

`attachment_local` — локальное состояние файла на устройстве. Оно не синхронизируется (§4.2).

**3.3. Правило слияния (`kinige-domain`, без IO).** Для каждой группы из объединения групп локальной записи и конверта побеждает больший HLC.
- Группы нет в одной из сторон (запись старой схемы) — берётся та, что есть.
- Равный HLC и разное содержимое — ошибка целостности. При исправном `device_id` (§1) она невозможна. Победителя выбирают детерминированно: больший по байтам канонический JSON значения группы (ключи отсортированы, без пробелов). Проигравшее тело уходит в ревизию `conflict`, событие пишется в журнал без содержимого.
- Создание — это `upsert` всех групп, оно бесконфликтно (§10.2).

**3.4. Конфликт текста.** Правка `body` с устройства записывает в `base` HLC той версии, которую правили.
При слиянии `body` с локальной версией L и пришедшей R:
- если победитель отличается по тексту от проигравшего P **и** `winner.base ≠ hlc(P)`, правки были одновременными;
- тогда P сохраняется полным снимком как `message_revision(reason='conflict')` с детерминированным id (§1). Это делает **любое** устройство, которое видит такую пару, независимо от того, локален P или пришёл. Одинаковый id делает повторное создание идемпотентным, и версия не теряется, даже если устройство-автор погибло после push;
- если `winner.base == hlc(P)`, правка последовательная: конфликта нет. Обычную ревизию `edit` создало правившее устройство (§2.1).

Отметка «есть другая версия» производная: она означает, что у сообщения есть ревизия `conflict`. Как пользователь закрывает отметку — решает слайс 3 или 11.
Известное ограничение: `base` описывает только один шаг истории. Очень старая версия, пришедшая не по порядку, может дать ложную ревизию `conflict`. Ошибка всегда в безопасную сторону: лишняя копия, а не потеря.

**3.5. Удаление, корзина, восстановление, `purged`.**
- Удаление и восстановление — запись группы `deleted` (`deleted_at` = время или `null`) с новым HLC. Побеждает больший HLC, поэтому восстановление после удаления побеждает (§10.2). Отдельного правила «удаление побеждает» нет.
- Правка удалённой записи (если интерфейс её разрешит) меняет свою группу, и запись остаётся в корзине.
- **Purge.** Когда у записи `deleted_at` старше 30 дней по локальным часам и группа `deleted` не менялась, устройство ставит в outbox конверт `kind='purged'` с `purged_of` = HLC группы `deleted`. Запись физически удаляется локально после того, как сервер принял конверт.
- **Каскад на сообщение:** после принятия `purged(message)` то же устройство отправляет `purged` для его ревизий и вложений. Получатель `purged(message)` удаляет детей у себя сам, не дожидаясь их конвертов.
- **Сервер упорядочивает purge** только по открытым метаданным (см. «Требует решения», п. 5):
  - `purged` отклоняется как устаревший, если для этой сущности уже есть конверт с HLC `deleted` больше `purged_of` (кто-то восстановил запись);
  - после принятого `purged` любой следующий конверт этой сущности отклоняется ответом «удалено». Клиент переносит такую локальную правку в **карантин** (§10.2) на ручное решение. Тихой потери и воскрешения нет;
  - повторный `purged` той же сущности с другого устройства принимается как no-op.
- **Локальные tombstones.** Клиент хранит `(entity, id, purged_of)` не меньше 180 дней, как сервер (§10.2). Конверт для id из tombstone с HLC `deleted` не больше `purged_of` не применяется; если HLC больше, конверт применяется.
- **Цикл синхронизации — всегда сначала pull, потом push.** Так устройство узнаёт об удалении до того, как отправит правку удалённой записи.

**3.6. Зависимости и Inbox.**
- Внешних ключей нет. Запись без родителя хранится и не показывается, пока родитель не придёт (§10.2).
- Ребёнок, чей родитель есть в tombstones, удаляется локально.
- У Inbox фиксированный id и `core.is_inbox = 1`. Два устройства, создавшие Inbox до привязки к аккаунту, сливаются обычным слиянием групп: переписывать ссылки не нужно.
- Inbox нельзя удалить: интерфейс не даёт, а слияние игнорирует `deleted_at` у записи с `is_inbox = 1`.

### 4. Версии и эволюция формата

Номеров версий три, и они не смешиваются.

| Номер | Где | Что меняет | Старый клиент видит |
|---|---|---|---|
| `format_version` (u8) | первый байт конверта | байтовую раскладку конверта, AEAD, AD | не может разобрать: хранит конверт сырым в `pending_unknown`, курсор двигает, просит обновиться |
| `schema_version` (u32, «sv») | заголовок (в AD) и колонка записи | смысл полей записи | см. правила ниже |
| версия протокола HTTP | заголовок запроса | эндпоинты и коды ответов | сервер возвращает понятную ошибку «обновите клиент» (§10.4) |

Правила `schema_version`. Начальное значение — 1, номер один на все сущности.
1. **Аддитивное изменение** — новое необязательное поле или новая группа — `sv` **не повышает**. Старый клиент обязан провести неизвестное через себя без потерь:
   - неизвестная группа хранится целиком в `unknown_json` вместе с HLC из заголовка и сливается тем же правилом «больший HLC»: слиянию не нужно понимать поля;
   - неизвестные поля известной группы хранятся в `unknown_json` и возвращаются без изменений, когда клиент переписывает эту группу.
   - Поле, смысл которого зависит от другой группы, нельзя добавлять в существующую группу: только новой группой или через повышение `sv`.
2. **Несовместимое изменение** повышает `sv`. Клиент с поддержкой до `sv = N` для записи с `sv > N`:
   - хранит снимок сырым;
   - сливает его по группам так же, как в п. 1 — сходимость сохраняется;
   - показывает только для чтения, по возможности (`body_md`, если поле узнаётся), с предложением обновиться (§10.4);
   - конвертов для такой записи не создаёт.
3. Клиент пишет запись в своей версии `sv`, только если она не ниже версии записи. Перевод старой записи в новую версию — обязанность нового клиента.
4. Миграции локальной базы — с предварительной копией, отката нет (§10.4). Каждое изменение формата — новый ADR (§10.4).

### 5. Конверт операции (`format_version = 1`)

**5.1. Байты** (так же лежит в `change_outbox.envelope` и так же хранится на сервере):

```text
off   len    поле
0     1      format_version = 0x01
1     4      key_id, u32 big-endian (1 = первый DEK)
5     4      header_len, u32 big-endian
9     H      header: UTF-8 JSON (открыт серверу)
9+H   24     nonce: randombytes_buf, новый для каждого конверта
33+H  N+16   crypto_aead_xchacha20poly1305_ietf_encrypt(
               m  = sodium_pad(payload, blocksize = 1024),
               ad = "kinige.env.v1" ‖ account_id (16 байт) ‖ bytes[0 .. 9+H),
               k  = K_env[key_id])
```

Почему так:
- В AD входят все открытые байты до nonce целиком, плюс `account_id` и метка домена. Подлинность проверяется по **полученным байтам**, а не по повторной сериализации, поэтому канонический JSON не нужен и сервер не может подменить ни одно открытое поле (§10.3).
- Поля, которые ТЗ требует в AD — аккаунт, тип, id, `op_id`, группы и HLC, `purged`, `schema_version` — плюс `format_version` и `key_id` (`review-codex` п. 4) покрыты.
- Случайный 24-байтный nonce допустим для XChaCha20-Poly1305 (документация libsodium).

**5.2. Заголовок (виден серверу):**

```json
{"entity":"message","id":"…","op":"…","kind":"upsert","sv":1,
 "groups":{"core":"HLC","body":"HLC","flags":"HLC","placement":"HLC","deleted":"HLC"}}
{"entity":"attachment","id":"…","op":"…","kind":"purged","sv":1,"purged_of":"HLC","blob":"<remote_blob_id>"}
```

`blob` есть только у `purged(attachment)`: по нему сервер удаляет blob. Связь «вложение ↔ blob» сервер узнаёт в этот момент, а не раньше.

**5.3. Полезная нагрузка (зашифрована):** UTF-8 JSON вида `{"groups":{"body":{…поля…},…},"unknown":{…}}`. HLC в нагрузке **не повторяются**: единственный источник — подлинный заголовок. У `purged` нагрузка пустая и всё равно выровнена и зашифрована, поэтому подделать `purged` нельзя. Лимит нагрузки — 1 МиБ до выравнивания.

**5.4. Проверки при pull — строго в таком порядке:** разбор байтов → известны ли `format_version` и `key_id` (если нет — `pending_unknown`) → AEAD-расшифровка → только потом разбор заголовка, строгий парсер HLC, `sodium_unpad` и применение. Ошибка AEAD останавливает применение страницы: курсор не двигается, пользователь видит ошибку; пропустить молча нельзя.

### 6. Push, pull, курсор

Конкретизация §10.2, без HTTP-деталей (их решает S4c).
- **Outbox.** Конверт собирается и шифруется в транзакции изменения. После push строка outbox получает `acked_seq` и удаляется, когда курсор pull проходит этот `seq`. Это и есть «свои операции узнаются по `op_id`»: такие конверты при pull пропускаются.
- **Сжатие outbox.** Неотправленный конверт можно удалить, если более новый конверт той же сущности перекрывает все его группы (так работает полный снимок).
- **Ответы на push по каждому `op_id`:**
  - `ok(seq)`;
  - `duplicate(seq)` — тот же `op_id` и те же байты;
  - `op_conflict` — тот же `op_id`, другие байты: ошибка клиента, синхронизация останавливается;
  - `purged` — в карантин;
  - `stale_purge` — сделать pull и заново оценить;
  - `clock_skew` — показать предупреждение;
  - `too_old` — нужен новый клиент.
- **Курсор** — `(generation, seq)`. `seq` выдаётся под блокировкой аккаунта (§10.2). Страница pull и курсор сохраняются одной транзакцией.
- **Полная пересинхронизация** — при смене `generation` или ответе «курсор устарел» (старше 180 дней):
  - клиент забирает всё, начиная с `seq = 0`, и сливает это как обычно;
  - если локальная запись новее серверной хотя бы по одной группе, создаётся новый конверт;
  - локальная запись, которой нет на сервере: если её максимальный HLC старше горизонта (`server_now − 180 дней`), она уходит в карантин (§10.2), иначе — на push.
- **Сжатие журнала на сервере** — по §10.2: только конверты старше срока хранения tombstones, перекрытые по всем группам.

### 7. Вложения

- **Ключ.** У каждого вложения свой случайный ключ `blob_key` из `crypto_secretstream_xchacha20poly1305_keygen`. Он лежит в зашифрованной группе `core`. Ключ на blob не выводится из содержимого: схему convergent encryption не используем.
- **Шифрование файла** — `crypto_secretstream_xchacha20poly1305` (§10.2):
  - заголовок потока — 24 байта;
  - открытый текст режется на чанки по 1 МиБ, у каждого `ABYTES = 17`;
  - последний чанк помечен `TAG_FINAL`, поэтому обрезка файла обнаруживается;
  - открытый текст в конце выравнивается до 1 КБ (`sodium_pad`).
- **Проверка после расшифровки:** совпадение `sha256` и `byte_size` с группой `core`. Иначе состояние `missing` и повторная загрузка.
- **Порядок отправки.** Blob загружается возобновляемо и неизменяем после публикации. Конверт вложения уходит на push только после публикации blob; остальные конверты он не задерживает: операции независимы.
- **`remote_blob_id`** — см. «Требует решения», п. 3.

### 8. Ключи

**8.1. Иерархия** (всё — функции libsodium, см. §11):

```text
пароль ──crypto_pwhash(Argon2id13, salt 16 B, opslimit, memlimit, out 32 B)──► pw_root
pw_root ──crypto_kdf_derive_from_key(ctx "kinigePW")──► id 1: auth_key   (уходит на сервер)
                                                    └─► id 2: KEK_pw     (не покидает устройство)
24 слова = 256 бит энтропии BIP-39 ──► rc_root (32 B)
rc_root ──crypto_kdf_derive_from_key(ctx "kinigeRC")──► id 1: rc_auth_key (уходит на сервер)
                                                    └─► id 2: KEK_rc
DEK[key_id] (32 B, randombytes_buf) ──crypto_kdf_derive_from_key(ctx "kinigeDK")──► id 1: K_env (конверты)
                                                                               ├─► id 2: K_blobid
                                                                               └─► id 3: K_rev (id ревизий conflict)
wrap = crypto_aead_xchacha20poly1305_ietf(k = KEK_pw | KEK_rc, nonce 24 B, m = DEK,
         ad = "kinige.wrap.v1" ‖ account_id ‖ key_id ‖ kind(1 = пароль, 2 = восстановление)
              ‖ salt ‖ opslimit ‖ memlimit   — последние три только при kind = 1)
```

- Для 24 слов растягивание паролем не нужно: 24 слова BIP-39 — это ровно 256 бит энтропии и 8 бит контрольной суммы (BIP-39), то есть готовый 32-байтный мастер-ключ для `crypto_kdf`.
- Параметры KDF в AD обёртки: если сервер их подменит, расшифровка сорвётся, и подмена будет замечена.

**8.2. Параметры Argon2id.** `opslimit = 3`, `memlimit = 268435456` (256 МиБ) — пресет libsodium `MODERATE`. Документация libsodium: около 0,7 с на Core i7 2,8 ГГц. libsodium всегда считает с одной полосой (`parallelism = 1`, проверено в исходниках). Соль и параметры хранятся на сервере открыто (§10.3) и сохраняются в обёртке, поэтому при смене пароля их можно повысить.
**Нижняя граница на клиенте.** Клиент не выводит ключ с параметрами ниже `MODERATE`, даже если сервер их прислал. Иначе злонамеренный сервер прислал бы слабые параметры и получил `auth_key`, по которому пароль подбирается дёшево. Если параметры аккаунта изменились с прошлого входа на этом устройстве — предупреждение.

**8.3. Регистрация** (клиент):
1. Создаёт `salt`, `DEK[1]` и 24 слова.
2. Выводит `auth_key`, `KEK_pw`, `rc_auth_key`, `KEK_rc`.
3. Отправляет: логин, `salt`, параметры, `auth_key`, `rc_auth_key`, `wrap_pw`, `wrap_rc`.

Сервер хранит `BLAKE2b-256(auth_key)` и `BLAKE2b-256(rc_auth_key)` (`crypto_generichash`) и сравнивает их за постоянное время (`sodium_memcmp`). Быстрый хэш достаточен: на входе равномерные 256 бит, а не пароль. Пароль и KEK сервер не получает никогда (§10.3).
Слова показываются при регистрации и проверяются вводом (§10.3). Как выглядит онбординг — Q12.

**8.4. Вход и новое устройство** (MVP+ — только по паролю, §10.3):
1. Клиент запрашивает `salt` и параметры по логину. Для неизвестного логина сервер отдаёт детерминированную фиктивную соль `BLAKE2b-keyed(server_secret, login)`, чтобы нельзя было перебором выяснить, какие аккаунты существуют.
2. Клиент выводит `auth_key` и отправляет его.
3. Сервер выдаёт токен сессии устройства (32 случайных байта; сервер хранит только хэш) и `wrap_pw`.
4. Клиент разворачивает DEK и делает полный pull.

Сервер ограничивает частоту попыток входа по аккаунту и по IP.

**8.5. Смена пароля** — повторный ввод старого пароля, новые `salt`, `auth_key` и `wrap_pw`, атомарная замена на сервере. Данные не перешифровываются (§10.3).

**8.6. Восстановление** — 24 слова → `rc_auth_key` → сервер отдаёт `wrap_rc` → DEK. Затем новый пароль, как в 8.5, и отзыв остальных сессий («Требует решения», п. 7). Без `rc_auth_key` сервер не смог бы отличить владельца слов от постороннего — ТЗ об этом молчит, здесь пробел закрыт.

**8.7. Отзыв устройства** удаляет токен сессии. DEK, уже скопированный на устройство, забрать нельзя (§10.3); ротация DEK — P2. Поле `key_id` для неё уже заложено в конверт.

**8.8. Хранение на устройстве.**
- DEK и токен сессии лежат в системном хранилище секретов (Keychain, Credential Manager, Secret Service). На Linux без Secret Service — файл с правами 0600 и предупреждением (тот же подход, что §12.3 для ключа OpenRouter).
- Пароль, `pw_root` и KEK после вывода ключей обнуляются (`sodium_memzero`) и не хранятся.
- Локальная база по-прежнему лежит открытым текстом (§4.1), поэтому DEK в хранилище секретов защиту не ослабляет.

**8.9. Удаление аккаунта.**
- Сервер удаляет строку аккаунта, обе обёртки, хэши, сессии, все конверты и blob'ы: удалить надо данные, а не только ключи (`review-fable` п. 4).
- Обещание пользователю — дословно по §10.3: «бэкапы хранятся N дней и затем ротируются; до ротации данные в них защищены вашим паролем». В бэкапе остаются обёрнутый DEK и соль. Владелец бэкапа может перебирать пароль офлайн по цене Argon2id из 8.2 — слова «защищены паролем» означают ровно это. N — Q14.
- Настоящий crypto-shredding бэкапов (серверный ключ аккаунта вне дампа) — P2.
- Локальные копии на устройствах, Markdown-копия и экспорт не затрагиваются, и это говорится прямо.

### 9. Аутентификация отдельно от шифрования

| Секрет | Видит сервер | Даёт серверу |
|---|---|---|
| пароль, `pw_root`, `KEK_pw`, `KEK_rc`, DEK, `K_*` | нет | — |
| `auth_key`, `rc_auth_key` | да (по TLS), хранит хэш | право войти и получить свою обёртку |
| `wrap_pw`, `wrap_rc`, `salt`, параметры | да | возможность офлайн-перебора пароля (неустранимо при входе по паролю) |
| токен сессии | хэш | доступ к push и pull своего аккаунта |

Утечка базы сервера не даёт ни войти (там хэши), ни прочитать данные (там шифротекст). Злонамеренный администратор может перебирать слабые пароли офлайн, поэтому требования к паролю — часть Q12.
Подменить код может только веб-клиент; для десктопа это закрыто подписью обновлений (§10.3, §12.3).

### 10. Что видит сервер (уточнение §10.3)

**Видит:**
- аккаунт и логин;
- устройства: `device_id` внутри HLC, имена устройств, время сессий;
- тип и id каждой записи, `op_id`;
- **какая группа и когда менялась** (HLC групп в открытом виде — плата за сжатие на сервере);
- факт удаления, восстановления и purge;
- то, что запись — Inbox (константа);
- размеры с точностью до 1 КБ;
- размеры и время загрузки blob'ов;
- связь «вложение ↔ blob» — только при purge.

**Не видит:** текст, названия чатов, `journal_date`, `created_at`, теги, флаги и их значения, связь «сообщение ↔ чат» и «сообщение ↔ вложение / ревизия», содержимое файлов.

**Может:** скрыть или откатить конверты — например, отдавать старое состояние. Защиты от этого нет (см. «Не решается»). Подделать или переставить конверт сервер не может: этому мешает AEAD.

### 11. Примитивы и реализация

Только libsodium. Собственной криптографии нет: собственный здесь только байтовый формат и алгоритм HLC, но не криптография.

| Назначение | Функция libsodium | Константы (проверено по заголовкам `stable`) |
|---|---|---|
| Конверт, обёртка DEK | `crypto_aead_xchacha20poly1305_ietf_encrypt/decrypt` | ключ 32, nonce 24, тег 16 |
| Blob | `crypto_secretstream_xchacha20poly1305_*` | ключ 32, заголовок 24, `ABYTES` 17, `TAG_FINAL = PUSH \| REKEY` |
| Пароль | `crypto_pwhash`, `crypto_pwhash_ALG_ARGON2ID13` | соль 16; `MODERATE` = 3 / 268435456 |
| Подключи | `crypto_kdf_derive_from_key` (BLAKE2b) | мастер-ключ 32, контекст 8 байт, подключ 16–64 |
| Хэши, ключевой PRF | `crypto_generichash` (BLAKE2b) | 32 байта по умолчанию, ключ 16–64 |
| Выравнивание | `sodium_pad` / `sodium_unpad` (ISO/IEC 7816-4) | блок 1024 |
| Случайность, сравнение, обнуление | `randombytes_buf`, `sodium_memcmp`, `sodium_memzero` | — |

Привязка к Rust — см. «Требует решения», п. 1. Тест-векторы — фиксированные ключ, nonce и вход с ожидаемыми байтами для конверта, обёртки, подключей и HLC — коммитятся в S4b, чтобы веб- и мобильный клиенты потом проверялись одной таблицей (`advice-fable` п. 6).

## Последствия для схемы §4.2

§4.2 — черновик для этого ADR. После принятия ADR в слайсе 1 нужно:
- `message_revision`: добавить `hlc_json` (только `core`), `schema_version`, `unknown_json`;
- `attachment`: добавить `blob_key` (BLOB, только в группе `core`) и `unknown_json`;
- новые таблицы `tombstone(entity, id, purged_of, purged_at)`, `quarantine(op_id, entity, entity_id, envelope, reason, created_at)`, `pending_unknown(seq, envelope)`;
- `change_outbox`: добавить `acked_seq INTEGER`;
- `sync_state`: добавить ключи `device_id`, `hlc_l`, `hlc_c`, `generation`, `cursor`, `account_id`, `kdf_params_seen`;
- `hlc_json` — объект `{"группа": "HLC"}`; `unknown_json` — `{"groups": {…}, "fields": {"группа": {…}}}`;
- комментарий у `chat.id` — по решению п. 2 ниже.

В слайсе 1 синхронизации нет, но `hlc_json`, `schema_version = 1`, `device_id` и часы HLC пишутся с первой записи. Тогда данные, накопленные до слайса 11, не придётся мигрировать.

## Требует решения пользователя

1. **Чем вызывать libsodium из Rust.**
   - (A) `libsodium-rs` 0.3.0 — безопасные обёртки автора libsodium поверх `libsodium-sys-stable` 1.24.3. Сборка из исходников с проверкой minisign-подписи. Под WASM — только WASI и только через Zig, `wasm32-unknown-unknown` не упомянут.
   - (B) RustCrypto: `chacha20poly1305` 0.11 (у крейта есть аудит NCC Group), `argon2` 0.6, `blake2` 0.11, `aead-stream` 0.6. Это чистый Rust, но тогда **вместо `secretstream` будет STREAM** — отступление от §10.2 — и вместо `crypto_kdf` понадобится HKDF.
   - (C) `libsodium-sys-stable` напрямую и своя тонкая обёртка из 10 функций.
   - **Рекомендую (A), запасной вариант — (C).** Это ровно то, что названо в ТЗ, одна библиотека и формат, который уже определён libsodium; веб-клиент возьмёт libsodium.js (не проверено). Крипто-код живёт в `kinige-sync`, а `kinige-domain` остаётся без него, так что требование wasm32 из §3.2 не задето. Риск: `libsodium-rs` молод (0.x, вышел в октябре 2026), сведений об аудите обёрток нет.
2. **id у Inbox.** ТЗ: «детерминированный id аккаунта». Но в слайсах 1–10 аккаунта ещё нет, а Inbox уже есть.
   - (A) Одна константа для всех аккаунтов. Записи на сервере и так разделены по аккаунтам, а `account_id` входит в AD. При привязке ничего не переписывается, два Inbox сливаются по группам. Утечка — сервер узнаёт, какой чат Inbox, — пренебрежимая.
   - (B) Id выводится из DEK; при первой привязке локальный Inbox переименовывается в новый id, и все ссылки переписываются.
   - **Рекомендую (A).** Формулировку §4.2 и §10.2 нужно поправить на «фиксированный id».
3. **`remote_blob_id`.** ТЗ: «HMAC от хэша». Вместе с «без дедупликации» и «blob удаляется вместе с вложением» это противоречие: одно и то же фото во двух вложениях получит один id на сервере, и удаление первого вложения сотрёт blob второго.
   - **Рекомендую** `remote_blob_id = hex(BLAKE2b-keyed(K_blobid, attachment_id ‖ sha256))`: id остаётся привязанным к содержимому и ключу пользователя, но уникален для вложения.
   - Дедупликацию вернуть вместе со сборщиком мусора, когда появится массовый импорт (§4.3).
4. **Удаление чата** — ТЗ не определяет (`review-fable` п. 16).
   - **Рекомендую:** удаление ставит `deleted` только у чата; его сообщения скрыты вместе с ним, восстановление чата возвращает их.
   - При purge чата удаляются сообщения, у которых HLC группы `placement` меньше HLC удаления чата.
   - Сообщения, созданные или перенесённые в чат после его удаления, переносятся в Inbox с пометкой: ничего не теряется молча.
5. **Проверки сервера по открытым метаданным.** ТЗ: сервер «не интерпретирует содержимое». Предлагаю разрешить ему две проверки только по заголовку:
   - (а) упорядочивание purge (§3.5): отклонять устаревший `purged` и конверты после `purged`;
   - (б) отклонять push с `wall_ms` больше `server_now + 24 ч` (ответ `clock_skew`). Иначе одно устройство с часами в 2200 году навсегда сдвинет часы всех устройств.
   - **Рекомендую принять обе.** Без (а) гонка «восстановили в последний день корзины, пока другое устройство делало purge» теряет восстановление. Без (б) у ошибки часов нет предела.
6. **Слова ключа восстановления.** В BIP-39 нет русского списка (есть 10 языков, проверено).
   - Варианты: (A) английский список BIP-39, 24 слова; (B) свой русский список — нестандартный; (C) строка base32 вместо слов.
   - **Рекомендую (A):** стандарт, проверенный крейт `bip39` 3.0.0, контрольная сумма ловит опечатки.
7. **Восстановление по словам отзывает все остальные сессии?** **Рекомендую: да.** Восстанавливать может и злоумышленник, укравший слова. Свои устройства просто войдут заново с новым паролем.
8. **Параметры Argon2id.** Рекомендую `MODERATE` (256 МиБ) с нижней границей на клиенте. Цена — вход и смена пароля длятся около секунды. Будущий веб-клиент в WASM будет медленнее: не замерено. Если замер S4b на самой слабой целевой машине покажет больше 2 с — обсудить.

## Не решается в этом ADR

- Онбординг пароля и ключа восстановления, требования к паролю — Q12, S4b.
- HTTP API: эндпоинты, транспортная кодировка, лимиты, частота запросов, форма логина — S4c.
- Ротация DEK, передача ключа по QR, ключ на чат, SQLCipher — P2 (§2.4).
- Crypto-shredding бэкапов — P2; срок N — Q14.
- Защита от сокрытия и отката конвертов злонамеренным сервером (цепочки хэшей, подписанные номера устройств) — не планируется.
- Хранилище и криптобиблиотека веб-клиента — решение перед веб-клиентом (§3.2).
- Синхронизация настроек и эмбеддингов: эмбеддинги в P1 не синхронизируются (§9.2).
- Интерфейс конфликтов, карантина и отметки «есть другая версия» — слайсы 3 и 11.
- Дедупликация вложений и сборщик мусора (§4.3).
- Id импортированных записей (Telegram, §2.1). Ограничение уже сейчас: id не может быть хэшем внешних id без ключа, иначе сервер подберёт id чатов Telegram.

## Не проверено

- `libsodium-rs` 0.3.0: проверены только названия модулей (`crypto_aead::xchacha20poly1305`, `crypto_secretstream::xchacha20poly1305`, `crypto_pwhash`, `crypto_kdf`, `crypto_generichash`, `utils::{pad, unpad, memcmp, memzero}`). Точные сигнатуры, качество обёрток и аудит не проверены.
- Какую версию libsodium собирает `libsodium-sys-stable` 1.24.3 — не проверено (ветка `stable` libsodium — 1.0.22). Сборка на трёх ОС в нашем CI не проверена.
- Совместимость байтов libsodium.js и RustCrypto XChaCha20-Poly1305 с libsodium — не проверена: подтвердят тест-векторы S4b.
- Время `MODERATE` на целевых машинах — не замерено, есть только цифра из документации.
- Сериализация `seq` под блокировкой аккаунта в Postgres — S4c (ТЗ §10.2).
- Механизм обнаружения копии базы (§1) — S4a.
- Сходимость всей схемы — только property-тестами S4a: два и три клиента, дубликаты, перестановки, обрывы, гонка purge и восстановления, `device_id`-близнецы.
