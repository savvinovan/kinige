# ADR-0021: The Bot API client, the TLS provider, the proxy and the bot token

Date: 2026-11-20. Status: **accepted** (KINIG-151, slice 5c; spec `docs/slices/5c-stickers-and-gifs.md`, reviewed by `sync-crypto-guardian` before code). Touches the app's first outbound network request, a secret in the OS store, Tauri commands and capabilities (PRD §12.3) and, through the `sticker` group, ADR-0001 §C.10.

## Context
Slice 5c adds stickers from Telegram packs. No Bot API method lists a user's installed packs, so a pack is added by its link, and downloading it needs a bot token (the user's own bot). The app made no outbound request before this. The token is a secret, the URL of every call holds it, and the web view must not learn it or make the request.

## Decisions

**Where the request is made.** In Rust (`src-tauri/src/stickers/`), by one client. The web view never makes it, so the CSP stays as it was (`connect-src ipc: http://ipc.localhost`; a test pins it). A pack job is one main-window command, `add_sticker_pack`, and one at a time.

**The client.** `reqwest` 0.13.5, `default-features = false`, features `rustls` and `system-proxy` (HTTP/1.1 only; no HTTP/2, `charset`, compression or cookies).
- **TLS provider:** `rustls` with the aws-lc-rs provider and `rustls-platform-verifier`. It was built on the Windows runner first (CI run 44746049939, the `windows` job: clippy and tests green with the dependency in the tree), so the fallback `rustls-no-provider` with `ring` was not needed. That run built the dependency without calling it; the PR's own `windows` job is the check of the linked client.
- **Trust anchors are the operating system's.** A root CA installed on the machine can read the token; PRD §10.3 says so.
- **Host and URLs:** the host is fixed, `api.telegram.org`, https only. Every URL is built with the URL builder (path segments, query pairs), never by concatenation, so a `file_id` with `&`, `#`, `%` or `/` stays inside its own piece. Our input rules (Telegram's are not verified): a pack name `^[A-Za-z0-9_]{1,64}$`, a `file_id` `^[A-Za-z0-9_-]{1,256}$`, a `file_path` `^[A-Za-z0-9_./-]{1,256}$` with no `..` or empty segment and no leading `/`, a token `^[0-9]{1,20}:[A-Za-z0-9_-]{1,100}$`.
- **No redirect is followed** (a 3xx is a bad response). No `Accept-Encoding` is sent; `Content-Encoding: identity` is tolerated and any other value is refused. The request headers are exactly `Host`, `Accept` and `User-Agent: kinige/<version>`, and a test pins the set (CLAUDE.md rule 14 covers development requests; this is the app's own).
- **Timeouts:** 10 s to connect, 30 s a request, 10 min a pack. **Body caps** (counted while streaming, a declared length over the cap is refused before the first chunk): 1 MiB for `getStickerSet`, 16 KiB for `getFile`, 2 MiB a file, 64 MiB a pack; at most 200 stickers. The JSON is read in `kinige-domain` into a validated structure and unknown fields are ignored.
- **Calls:** one `getStickerSet`, then one `getFile` and one download per static sticker, one after another. Rate limits are not verified; a 429 is "wait" and nothing is retried.
- **Errors map by HTTP status** (Telegram's descriptions are not verified): 401 token refused, 400 or 404 no pack (a single file: skipped), 429 wait, anything else a bad response, a failed connection or TLS or a timeout is unreachable. The first step of the mapping is `without_url()`; after it only a category remains and **no error text is formatted, logged or returned**. A test captures every log line at trace level over connect refused, TLS, timeout, redirect, 401, 429 and garbage and finds no token, link, pack name or title in them. The HTTP client's own log stays at `warn` (foreign crates are at `warn` in the log plugin, whatever `KINIGE_LOG` says).
- **The system proxy is honoured**, because the user's network may reach Telegram only through a proxy or a VPN. An HTTP proxy tunnels HTTPS with CONNECT, so the token stays inside TLS. This needs reqwest's `system-proxy` feature: with default features off only environment variables are read, and an app started from Finder has none. SOCKS: **not verified**.
- **Test-only switches:** the base-URL override (`KINIGE_TEST_BOT_API`) and the in-memory token store (`KINIGE_TEST_TOKEN_STORE=memory`) exist only under the cargo feature `test-hooks`; the screens-driver feature turns it on and `scripts/check-test-hooks.sh` finds the marker `kinige-bot-test-hooks-5c` in a binary and refuses it unless `KINIGE_ALLOW_SCREENS_DRIVER=1` (controls in `check-test-hooks.test.sh`). Tests never talk to `api.telegram.org`; a fake server on localhost serves them, and the test tokens do not have the real token shape (gitleaks flags it).

**Where the token lives: the OS secret store, as PRD §9.2 rules for secrets.** macOS: a generic-password item, service `me.savvinov.kinige` (`me.savvinov.kinige.dev` in a debug build, so a development run never touches the real item), account `telegram-bot-token`, not synchronizable (`security-framework`). Windows: Credential Manager under the same names (`keyring` 3.x, `windows-native` only). Linux: none yet, there is **no file fallback**, so the token cannot be saved there until the Linux build (slice 10). Never in `app_setting` (the database goes into the daily backups), the log, `settings.json`, MCP, the capture window or the main window. `app_setting.telegram_token_saved` is a plain flag that can disagree with the store (a restored database); the next read by a job corrects it.
- **The token is read only when a pack is downloaded**: never at startup, never on opening Settings or the panel. The settings window writes it (`set_telegram_bot_token`, `clear_telegram_bot_token`) and reads back only `{saved}`. A test counts the calls of a counting store: none until a job.
- **The read never runs on the main thread.** Commands run on the runtime's pool; the job reads the token once at its start and a prompt that is dismissed or denied ends the job with its own error category, `secret_store_denied`, and writes nothing. A refused or locked keychain is `secret_store_unavailable`.
- **Remove:** `clear_telegram_bot_token` clears the flag first and always deletes the item whatever the flag says. An item that another build owns cannot be deleted by this one (see the finding below); that is not an error there, because saving a new token replaces it.

**Finding: the keychain across two ad-hoc-signed builds (KINIG-151, 2026-11-20).** The app is signed ad hoc (ADR-0003, ADR-0012), so every build has its own code hash and is a different program to the keychain. `spikes/5c-keychain` (a program that does what the secret store does, built twice with different tags and signed ad hoc like the app) was run on the macos-15 runner, CI runs 44747551144, 44749318159 and 44749995262, with a 20 s alarm in place of a person at the prompt:
1. build A writes the item and reads it back: fine;
2. **build B reads A's item: it blocks on the keychain prompt** (headless, the alarm fired, status 142), so B cannot read it without a person answering;
3. B writes over A's item: succeeds without a prompt and moves the item's ownership to B (A is then blocked and B's delete fails with -25244, "Invalid attempt to change the owner of this item");
4. an item made with `security add-generic-password -A` (any application) does not lift the prompt, for A or B (probably the partition list of macOS 15);
5. signing both builds with one self-signed certificate was **not verified**: `codesign` found no identity and both builds stayed ad hoc.

**Ruling (the coordinator, 2026-11-20, reversible, the user is told): accept the prompt** (option a). The token is read only when a pack is downloaded, which is rare, so the dialog appears at most once per update and only for someone adding a pack; the Settings note already says macOS may ask once after an update. The default `security-framework` item is used. A dismissed or denied prompt is `secret_store_denied`, and its text tells the user to press "Remove" and save the token again (point 3). Stable signing (option b) is out of scope here: it belongs to ADR-0012 and the updater of slice 10.

## Not verified
- The prompt on a real desktop: its text, its "Always Allow", and that a person's answer lets the job read the item.
- "Always Allow" across a real update (the new build's cdhash is new).
- A stable signing identity (Developer ID or a self-signed certificate kept by the release workflow) making the prompt disappear.
- SOCKS proxies and PAC files; HTTP and HTTPS proxies from the system settings are expected to work and are not tested on a machine behind one.
- Telegram's own limits and rate limits, and the exact format of a token or a pack name (our rules are looser or stricter on purpose and say so).
- The Windows link of the TLS provider before the PR's `windows` job; the Credential Manager code, which no job on this machine runs.
- WebKit's memory for large GIFs (`docs/screens/5c/gif-memory.txt` holds the measurement taken on the runner).
