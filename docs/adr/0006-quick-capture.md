# ADR-0006: Quick capture — window, hotkeys, tray, append, drafts

Date: 2026-10-22. Status: **accepted** (slice 2). PRD §1.1, §2.1, §3.2, §5, §5.1, §9.3, §12.3, §15; ADR-0001 §3.3, §3.4, §4, appendix §A.0.

## Context
Slice 2 adds a second window (quick capture), two global shortcuts, an icon in the menu bar, the "window closed, app alive" lifecycle, drafts, and the first rewrite of a single group (`body`) — appending to the latest entry.

## Decision

**Window.** A second Tauri window `capture`, declared in `tauri.conf.json` and created hidden at startup: no title bar, **transparent and without the system shadow**, above all windows, on all desktops, 584 px wide (tokens `layout.capture.*`), height by content (see "Look" below). The page is the same (`index.html#capture`); the app picks the component by the hash. The window has its own capability `capture-window`: six commands `capture_state`, `capture_send`, `capture_append`, `capture_save_draft`, `capture_hide`, `capture_resize` — without `chat_id` (Inbox only), without reading the feed, without `core:*`, without events and plugins. The main window gets `get_draft`, `save_draft`, `set_shortcut`, `reset_shortcut`, `shortcut_recording` and `core:event:allow-listen` / `allow-unlisten` (the "entries changed" event). Negative tests — `src-tauri/tests/ipc.rs`, `tests/config.rs`.
- **Look (user acceptance on 22.10.2026: the previous window was "too angular", did not look like an app).** The window is a compact floating "pill" in the spirit of Gemini and ChatGPT. The OS window is transparent (`transparent: true`; on macOS this needs `macOSPrivateApi`, which is already on for the sake of NSPanel) and without the system shadow (`shadow: false`); the visible shape is drawn by CSS: corner radius `radius.floating` (1.5 rem, 19.5 px), the paper fill, a thin light outline (`opacity.panel-edge` of the body text color), shadow `shadow.overlay`. Around the panel there is a transparent margin `layout.capture.shadow-margin` (32 px) for the shadow: the window is larger than the panel, window width = panel width (520 px) + two margins (checked by `tests/config.rs`). With no entries for today, the window is a single field line; with entries, up to three faded bubbles above it inside the same panel; the "Send" button is inside the field; the hint "⌘Enter — append" and the error are one line **below** the field (Composer `floating`). The panel's inner padding is uniform, `space.4` (13 px) on all sides, so nothing enters the rounded-corner zone; the bubble text, the field text and the hint stand on one left line (9.75 px from the bubble edge: `layout.message.padding-inline`). The "Send" button appears when the field has text, as in the main window's composer; in an empty panel it is not there. The field has no focus line of its own: there is one field and it is always focused (an accent-colored caret). There is one theme (graphite): there is no "light" one.
  - **Height by content — the `capture_resize(height)` command** (the window's sixth command). The page watches the panel's height (`ResizeObserver`) and reports it to Rust; Rust clamps it to `layout.capture.window-min-height … window-max-height` (100 … 480 px; the Rust constants are checked against the tokens in `tests/config.rs`), rounds it, skips a repeat of the same height, sets the size `LogicalSize(584, h)` and **pins the bottom edge** (`set_position` after `set_size` from the show anchor: `setContentSize` does not promise which corner stays, and a window size read after a deferred `set_size` may be stale). The page cannot change the width or the position: the command takes only a number, and `plugin:window|set_size`, `set_position`, `set_min_size`, `set_max_size`, `set_resizable` are denied to the capture window (negative tests in `tests/ipc.rs`).
  - **Position — at the bottom of the screen, the bottom edge pinned (acceptance on 27.10.2026: a window at 28% of the screen height from the top covered what the person wants to write about; the previous decision "top pinned" is canceled).** The panel is centered horizontally on the screen with the cursor, with the panel's bottom edge 12% of the monitor's **work area** height above its bottom (`Monitor::work_area` in tauri 2.12.4 — on macOS `NSScreen.visibleFrame`, that is, without the Dock and the menu bar; verified in the sources of `tauri-runtime-wry` 2.12.2; the constant `BOTTOM_FRACTION` sits next to the others in `capture.rs` and was not moved into the tokens: the position of an OS window is not layout). The window extends below the panel by the shadow margin (32 px). The anchor `(x, bottom edge of the window)` is remembered on show; `capture_resize` puts the window top at `anchor − height`, so the context and multi-line text grow **upward**, as in a chat, while the input field (and the hint and error below it) stays in one place at any height and when shown again with a different height. The page is pinned to the bottom of the window (`#root` is flex, `justify-content: flex-end`): while the window catches up with the content (one frame), the field does not jump. The formulas are the pure functions `anchor_for` and `top_for_bottom` (tests in `tests/config.rs`: center, a shifted work area, retina, one bottom edge for heights 122…480).
  - The NSPanel system corner rounding and shadow are removed: a transparent window without `hasShadow`. The system window effects (vibrancy/`windowEffects`) are not used: they were not tested, and an opaque surface from the tokens gives a clean look.
- Rust tells the capture window about showing and about the request to hide via `WebviewWindow::eval` (a DOM event), not a Tauri event: the window has no permission to listen to events. The "entries changed" event goes to the main window via `emit_to("main")`.
- Showing: the window is placed on the screen with the cursor (`cursor_position` + `monitor_from_point`). Hiding: the hotkey while the window is open, Esc, loss of key status (a click in another window or app) and closing the window ask the page to save the draft and call `capture_hide`; if the page has not answered within 600 ms, the window is hidden forcibly.
- **macOS: the capture window is a non-activating NSPanel (`tauri-nspanel` 2.1.1). Status: accepted** (the product owner's decision of 22.10.2026: the Mac App Store is not planned; behavior as in Spotlight and Raycast).
  - **Why.** A panel with the `NonactivatingPanel` flag becomes key without activating the app: the previous app stays active and keeps focus by itself after the panel is hidden, the main window does not pop up, and `AppHandle::hide` and its side effect (all of the app's windows are hidden) are not needed. This is a product property, not a workaround for a failure.
  - **What the original justification did not prove.** The first implementation (an ordinary window, `show` + `set_focus`) on macOS 26.5 in a live check sometimes got input and sometimes did not: the window got key status and lost it after 1–10 ms (`windowDidBecomeKey` → `windowDidResignKey`), and keystrokes did not go to the page. At the time this was explained by the "cooperative activation" of macOS 14+. **This explanation is not confirmed and is discarded**: on the test machine ⌥Space is taken by ChatGPT (`KeyboardShortcuts_toggleLauncher`), and ⌥⇧Space is intercepted by Gemini; every press also opened their window, which activated and took focus, so the loss of key status was a consequence of the shortcut conflict. An ordinary Tauri window with a free shortcut **was not rechecked**, so it cannot be claimed that it is "unreliable". NSPanel is accepted as Spotlight- and Raycast-level behavior (the reasons are in the "Why" item), not as a workaround for a failure.
  - **Cost.** The `macOSPrivateApi` flag in `tauri.conf.json` (a private API; it rules out the Mac App Store, which is not planned) and a third-party crate (2.1.1, checked in its sources: the window class is swapped for an `NSPanel` subclass; a conversion failure is a startup error, not silent degradation). Rollback is one commit (`665302e`).
  - **All AppKit calls are on the main thread** (`run_on_main_thread`): showing and hiding the panel. Calling `show_and_make_key` / `hide` from the clipboard hotkey handler thread and from the fallback hide timer crashed the app (SIGTRAP, found in review).
  - **The key status restore loop (`rekey`) is removed.** It gave the panel back the status the system took away in the first 300 ms after showing. A live run on a free shortcut (22.10.2026 around 14:50 MSK, a temporary database, ⌃⌥⇧K over Finder and over Telegram, 12 shows each): 0 status losses out of 24, all "show, type, hide" cycles normal. The cause of the losses was the conflict of ⌥Space with ChatGPT and Gemini (see above). Now any loss of key status means the user has left: the window hides and saves the draft.
- On Windows and Linux (slice 10) an ordinary window with `show` + `set_focus` remains.

**Append — the first group rewrite** (`kinige_domain::append`, ADR-0001 §3.3, §3.4, §4).
- Target: the latest non-deleted entry of Inbox, `origin = 'user'`, `created_at` no older than 10 minutes (the boundary inclusive), `journal_date` = today, all groups in a supported `sv` (otherwise the entry is read-only, ADR §4 item 4). A damaged `hlc_json` is an error, not "not allowed". Rust decides the rule in the same transaction as the write.
- Text: `old + "\n\n" + new` (a new paragraph; `breaks: true` would glue the lines); the 512 KiB limit is on the canonical group bytes after joining (`message_too_large`, nothing written, and no new entry is created instead of the refusal).
- The `body` group is rewritten as canonical bytes with a new HLC strictly greater than the previous one: `edited_at = now`; `base`/`supersedes` per §3.4 — the server confirmed the version (`server_known = 1`): `base = hlc(V)`, `supersedes = []`; the device's own unconfirmed version: `base = V.base`, `supersedes = V.supersedes ∪ {hlc(V)}`, no more than 64 (the oldest are dropped). Other groups, unknown groups, unknown fields of `body` and extra fields of the `hlc_json` entries are preserved verbatim; `schema_version` is the maximum `sv` over groups. The `body` HLC is one write to `sync_state` in the same transaction.
- **No `edit` revision:** the old text is a prefix of the new one, nothing is lost. The revisions table is slice 3.
- `created_at` and `journal_date` do not change; the entry stays in its place in the feed; `mirror_dirty` for the entry's day.

**Drafts.** Migration 2: a local non-synchronized table `draft(key, body, updated_at)`; keys `capture` and `chat:<id>`. The frontend saves with a 300 ms delay and on hide; Rust clears the draft in the send transaction (each path has its own key: the clipboard hotkey does not touch drafts). The limit is 1 MiB. Drafts do not go into the Markdown copy or into the entry tables.

**Shortcuts.** The canonical notation `Ctrl+Alt+Shift+Cmd+<KeyboardEvent.code>` (`kinige_domain::shortcuts`): `global-hotkey` understands the same names, and the keyboard layout does not matter. Ctrl, Alt or Cmd is required; ⌘Q/W/H/M/Space are reserved. Defaults are ⌃⌥N (capture) and ⌥⇧V (clipboard) — the user's decision of 22.10.2026; **⌃⌥N is temporary instead of ⌥Space** (named in the PRD): ⌥Space and ⌥⇧Space are intercepted by ChatGPT and Gemini, ⌃Space and ⌃⌥Space are taken by input source switching (`symbolichotkeys` 60/61), ⌘Space by Raycast; they are stored in `app_setting` and not synchronized. Changing: check the notation and a clash with another action (nothing changes) → register the new one in the system (refusal — `shortcut_taken`, the previous one keeps working) → save (on failure the new one is unregistered) → unregister the previous one. A shortcut the system did not accept at startup is shown in "Settings" as "not assigned"; everything else works. While a new shortcut is being recorded, hotkeys do not fire (otherwise one could not press an already assigned one).

**Clipboard hotkey.** Text from the clipboard is read by `arboard` 3.7 (`get_text`) only from Rust, on a separate thread; not text or empty — nothing; success — an entry in Inbox, an event to the main window and a double blink of the menu bar icon (160 / 110 ms, no sound and no window); a write failure — the capture window with the clipboard text in the field and an error (the text goes into the draft and into memory).

**Tray and lifecycle.** The Tauri core, feature `tray-icon`: a template icon (`web/src/ui/icons/tray/*.svg` → PNG), the menu "New note" / "Inbox" / "Quit Kinige"; the strings come from `web/src/locales/{en,ru}.json` (`include_str!`). Closing the main window hides it; the Dock (`RunEvent::Reopen`), the tray menu and a second launch (`tauri-plugin-single-instance`, registered first) show it; ⌘Q and "Quit Kinige" quit.

  - **Emoji (addition, slice 3 acceptance, 27.10.2026).** The window's field has an "emoji" button and the same picker as in the main window, but embedded in the panel's flow between the context and the field (a popover does not work: the window has no room beyond its edges). The panel with the picker is taller, and `capture_resize` grows the window upward with the bottom edge pinned; the limit `window-max-height` 480 → 640 px (the constant `MAX_HEIGHT` and the test `tests/config.rs` are updated), `field-max-share` 0.45 → 0.325 (the field limit is the same, 187 px); with the picker open the field shows no more than three lines. Esc first closes the picker, then the window. "Recent" is shared: `CaptureState.recentEmoji` comes with every show, and a choice is written by **the window's seventh command `capture_add_recent_emoji(emoji)`** (no chat, no entry; the same rules as `add_recent_emoji`); without it, a choice from the capture window would not get into the shared list. The window's other commands are the same; the negative tests in `ipc.rs` are updated to seven.

## Dependencies
`tauri` 2.12.4 + features `tray-icon`, `image-png`; `tauri-plugin-global-shortcut` 2.4.1 (pulls in `global-hotkey` 0.8.0, on macOS Carbon `RegisterEventHotKey`); `tauri-plugin-single-instance` 2.5.4; `tauri-nspanel` 2.1.1 (macOS only; requires the `macos-private-api` feature of `tauri` and `macOSPrivateApi: true` in the config); `arboard` 3.7.0 without the `image-data` feature. The latest on crates.io is `3.0.0-alpha.3` for both plugins (for Tauri 3), so the latest stable 2.x branch was taken.

## Rejected
- An ordinary Tauri window for capture on macOS: it activates the app (raises the main window, needs `AppHandle::hide` to return focus). It was not rejected as "unreliable" — that is not proven (see above); it was rejected as not Spotlight-like. It remains the fallback on Windows and Linux.
- Detecting "the shortcut is taken by another app" on macOS (`CopySymbolicHotKeys` for system shortcuts; other apps' shortcuts via `RegisterEventHotKey` are not visible): **postponed**, it is not in this slice; the "not assigned" state works in the data, the UI and the tests.
- Choosing a chat in the capture window, ⌘Enter in the main window, recent chats other than Inbox — slice 3.
- An `edit` revision on append — an extra record when the text only grows (slice 3 introduces revisions for edits).
- The JS clipboard plugin and the JS shortcut plugin: windows get no permissions for plugins, everything goes through our commands (§12.3).

## Consequences
For `sync-crypto-guardian`: migration 2 (`draft`), the rewrite of `body` with `base`/`supersedes`, preserving unknown groups and fields. The tests postponed from slice 1 (an unknown group, extra `hlc_json` fields, a strictly increasing HLC, damaged JSON, a write refusal) are back: `crates/kinige-domain/src/append.rs`, `crates/kinige-store/tests/capture_*.rs` (the file `capture.rs` was later split); the deletion test helpers (`mark_deleted`) set `deleted_at` together with a consistent `deleted` group and its HLC, not with a direct `UPDATE` of the column.
