# ADR-0022: Settings only in SQLite, read and partly changed by agents through MCP (supersedes ADR-0010)

Date: 2026-11-20. Status: **proposed** (KINIG-160, slice 5d; the spec `docs/slices/5d-settings-through-mcp.md` was reviewed by `sync-crypto-guardian` on 20.11.2026, "rework", and its rules are in the text; the guardian reviews the PR again, the user accepts). PRD §2.1, §5.1, §9.2, §9.3, §11.3, §12.3; ADR-0001 appendix §C.4, ADR-0005, -0006, -0009, -0010.

## Context
ADR-0010 made `settings.json` the input and `app_setting` the state, so a person or an agent could edit settings "from outside". The file brought a polling thread, a safe reader, an atomic writer, a reconciler, an error page and a mark in the tree, and it was the one path by which an agent could switch its own access on. The user's decision of 20.11.2026: the file goes, everything lives in SQLite, and agents change settings through MCP, not by editing a database file.

## Decision
- **Settings live only in `app_setting`.** Nothing is read from a file at start or later. The user's old `settings.json` is never opened, read, written, renamed or deleted, and the settings window says nothing about it (the release note: "Kinige no longer reads settings.json; you may delete it, it may hold chat titles").
- **Two MCP tools** through the single entry point `Store::agent_call`, one log row per call:
  - `get_settings` (any mode, `readOnlyHint`). Its reply is built from its own struct (`kinige_domain::agent_prefs::SettingsReply`), never from the window's `Settings`: `text_size`, `shortcuts.{capture,clipboard}` as `{value, default}`, `markdown_copy` (`default_folder`, `chosen_folder` or `off`, never a path), `agent_access.{mode, visible_chat_ids}` (ids selected with ADR-0009's visibility predicate, no titles) and `writable`. A test pins the key set.
  - `set_setting(key, value)` ("Read and write" only). One writable setting: `text_size`, `normal` or `large`. The key is mapped to a fixed Rust enum, so no input string becomes an `app_setting` key. The other six known names (`shortcuts.capture`, `shortcuts.clipboard`, `agent_access.enabled`, `agent_access.mode`, `agent_access.chats`, `mirror.folder`) get the new `setting_not_writable`; any other key, including raw `app_setting` names and case or space variants, and any wrong value, get `invalid_argument`. A refused call writes nothing. The access check is repeated inside the writer transaction that writes the setting and its log row (ADR-0009).
- **The allowlist of `app_setting`.** Readable and writable: `text_size`. Readable, changed only in the settings window: both shortcuts. Readable only in part: the copy folder (the state, not the path) and agent access (the mode and the visible chat ids; that access is on is implied by the call). Neither read nor written: window state (`sidebar_collapsed`, `recent_emoji`, `forest_*`, `on_this_day_dismissed`), `search_index_version`, the retired `settings_file_hash`, and every key a later slice adds until this list names it.
- **Why shortcuts are read-only for agents** (the guardian's ruling). `Cmd+KeyV` passes `is_reserved` (it refuses only Cmd+Q and unshifted Cmd+W, H, M and Space) and would register. From then on every Cmd+V in any app would save the clipboard to Inbox, with only a blink of the tray icon, and an agent that sees Inbox would read the copied passwords and codes. `shortcuts.capture` is read-only too: it is a system-wide key grab that steals focus. The user may later allow it with Ctrl+Alt combinations only.
- **Why an agent cannot widen its own access** (this answers ADR-0010's "rejected: an MCP tool for settings"). The tool exists, but the permission settings are not in its allowlist: access on or off, the mode, the visible chats and the copy folder change only through the settings window's commands, which MCP cannot reach, and no switch inside the app (a variable, a flag, a test hook, a driver step) turns access on for tests; `sqlite3` on a throwaway database is the only test path. Accepted, as PRD §4.1: a process of the user that writes the database file itself.
- **The log.** `args_json` of `set_setting` holds `key` (one of the seven known names, otherwise `"other"`) and, on success only, `value` (the canonical text size); `get_settings` has `{}`. A new outcome `not_writable` (`outcome` is plain `TEXT`: no migration). The access log shows "read the settings", "changed a setting: text size" and "denied: settings window only". Rows `tool = 'settings_file'` from 4b to 5c keep their label until rotation drops them.
- **The windows.** After a change the Tauri layer sends `settings-changed` to `main` and `settings` (`notify_changed`), as after a click. No tool shows, raises or focuses a window (rule 11). The settings window's commands call `Store` and `Hotkeys` directly; on Windows the `set_agent_*` commands still answer `unsupported`.
- **The `Hotkeys` change lock.** The window is still a caller (two quick `set_shortcut` or `reset_shortcut` calls), and no file thread queues its edits any more, so the change lock stays: a second mutex, separate from `inner`, held over check, register, save and release. `inner` is never held across `register`, so `on_shortcut` and `overlay` never wait for a change. The two commands stay `async`: a pool thread that holds the lock waits for the main thread inside `register`, and a sync command waiting for the lock there would deadlock.
- **Restore can only narrow access.** The restore transaction sets `mcp_enabled = 0`, `mcp_chats = []` and `mcp_mode = 'read'`, whatever the backup held: without the file, a backup's `read_write` would become effective for the first time, and its list may hold chats removed since. The copy folder is the backup's own (the folder that was there moves aside to `…-before-restore-…`, as before); the second move-aside for a folder named in the file is gone.
- **The `settings_file_hash` row stays, inert.** No code reads, writes or deletes it, start-up and restore included. The slice has no migration, so 0.9.2 can still open the database after a downgrade, and in 0.9.2 a missing or different hash means "apply the file", which would switch access back on from a stale `settings.json`. With the row kept the hash matches and 0.9.2 rewrites the file from the database. Accepted in words: a restore followed by a downgrade may still apply the stale file.
- **Clean-up.** At every start one idempotent step removes Kinige's own leftovers: regular files in the data directory named exactly `.settings.json.` + 32 lowercase hex characters + `.tmp` (what the atomic writer of 4b made). A hyphenated look-alike, a symlink and a directory are kept, no link is followed, an error is skipped and the log gets only a count. It never touches `settings.json` or `app_setting`.
- **Removed.** `crates/kinige-store/src/settings_file/` and `crates/kinige-domain/src/settings_file.rs` with their generated types, `get_settings_file` (all three windows' lists, `build.rs`, the capability and its permission file), `HotkeyBridge`, the file page, the "Changed via settings.json" line and the tree's error mark.

## Rejected
- **Keeping the file as an optional input.** It is the path that switched access on without the warning, and the user asked for it to go.
- **A generic `set_setting` over every `app_setting` key.** The key set grows with every slice; an allowlist of one is the only form that cannot widen by accident.
- **Letting an agent change the shortcuts, with a reserved-key list.** The list would have to be complete for every app on the machine. The guardian's ruling stands until the user decides otherwise.
- **A migration that drops `settings_file_hash`.** It would break the downgrade.

## Consequences
- ADR-0010 is superseded. ADR-0009 gains two tools; ADR-0001 appendix §C.4 gains the `args_json` rule and the outcome; ADR-0011's only `unsafe` (`geteuid` in the settings file reader) is gone with it.
- `tools/list` has 6 tools in "Read only" and 10 in "Read and write"; a client sees the old list until it reconnects (no `tools/list_changed`, as before).
- Syncing settings between devices is still not settled (ADR-0001, "Not settled").
