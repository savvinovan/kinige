# ADR-0013: Forest grid and renderer (spike S3)

Date: 2026-11-02. Status: **accepted** (KINIG-14; the user chose grid B on 02.11.2026). Evidence: `spikes/S3-forest/README.md`, `spikes/S3-forest/results/`, `docs/screens/S3/`. PRD v0.16 (§7.1, Q4, §14) was brought in line.

## Context
Spike S3 compared two boards (A: 12 × 31 month × day; B: 7 × 53 weekday × week) and two renderers (Canvas 2D; PixiJS v8) on GitHub runners in headless Chromium and WebKit. A gives bigger trees (a 55 px tile against 40 px at 1280 × 800) and reads dates directly. The user chose B anyway, for the weekday rhythm and the continuous "river" of the year.

## Decisions

**Grid B.** Seven rows are the weekdays counted from the first weekday, one column per week. The board width is a function of the year: `cols = ceil((january_offset + days_in_year) / 7)`, where `january_offset` (0..6) is how many cells sit above 1 January in the first column. That is 53 columns, and **54** in a leap year whose 1 January is the last day of the week: 2012, 2040, 2068, 2096 with a Monday start; 2000, 2028, 2056, 2084 with a Sunday start. Cells around the year are empty ground without interaction. Grid A is documented only in the spike.

**First weekday follows the system locale; Monday by default.** Read it with `new Intl.Locale(navigator.language).getWeekInfo()` (`firstDay` is 1..7, 7 = Sunday) and fall back to the older `weekInfo` property, then to Monday. This is expected from the Intl spec and was not verified in this spike (no probe is recorded in `results/`); slice 6 adds a probe for the real WKWebView, WebKitGTK and WebView2 (older engines may lack `getWeekInfo`), and the Monday fallback covers them. A user setting can come later.

**Rendering: Canvas 2D with a layer cache, no PixiJS.** Pan and zoom blit a cached bitmap of the board (re-rendered when content changes, 140 ms after the camera rests, or when the view leaves it), the hover outline is drawn over it. Three levels of detail by tile width: dot below 14 px, simplified below 32 px, detailed from 32 px. Measured (worst of pan, zoom, pan+zoom, grid B unless noted): macOS WebKit 58..60 FPS plain and cached; Linux Chromium 60 at 1x; Linux WebKit without GPU raster 50 plain and 61 cached at 1x but 20 plain and 24 cached on a 2x screen (an empty canvas gets 44..48); Chromium with software GL 5..13 plain, 29..60 cached. The cases below 60 are floors of a software path; WebGL on those machines goes through the same software path (the Linux Chromium WebGL renderer is SwiftShader, WebKit hides it), so PixiJS would not fix them. PixiJS was never built or measured; revisit only if the final art needs many animated sprites per frame.

**Hit-test by the inverse of the projection** (point → world → cell), never by sprites; a tall tree overlaps neighbours but does not take their click. 21,900 real clicks, 0 misses. A `NaN` point must give no cell.

**`crates/kinige-domain/src/forest.rs` is the single source of truth for slice 6:** `day_position`, `date_at_cell`, `grid_dims`, `season_of_month`, `day_weight`, `stage_of` (PRD §7.2, §7.3). It holds only grid B. The TypeScript copy in `spikes/S3-forest/src/calendar.ts` stays in the spike; slice 6 decides how the frontend gets the rules (a wasm build or a generated table) and adds the IPC shape and ts-rs types.

**Collapsed strip: a flat heat map (slice 6).** A board in a 250 px high strip is 11 px tiles (dots), so the collapsed forest is a flat weekday × week heat map like GitHub's (user decision, 02.11.2026); the board opens above the feed when the strip is expanded.

## Not verified
- Real hardware: WKWebView inside Tauri, WebKitGTK, WebView2. The macOS and Linux runners are VMs without a GPU and headless.
- Linux WebKit on a 2x screen without a GPU (24..26 FPS cached): check on a real machine before slice 6 closes.
- Trackpad pinch through `gesturechange` (Safari, WKWebView): written from the API, never run.
- Real sprites: a scaled bitmap costs more than vector shapes in Chromium's CPU path; atlases should be close to the drawn size.

## Slice 6: how the frontend gets the rules (02.11.2026)

**A year table from Rust, no wasm and no TypeScript copy.** `forest_year::year_table(year, first_weekday, stats)` builds every day of a year once (date, row, column, season, notes, stage, excerpt) from `forest.rs`, and `get_forest_year` returns it with `cols`, `min_year` and the current journal day. TypeScript keeps only geometry (the projection, the hit-test point → cell, cell → day by lookup in the table). The cost is one query per year and a table of 365 or 366 small rows (the query is below); a wasm build of `kinige-domain` was not needed, and the two ways the rules could drift apart (a TypeScript calendar, a wasm artifact in the bundle) do not exist. The mock used in tests and stories has a short layout function of its own; `forestLayout.test.ts` checks it against year tables generated by the real `year_table` (`crates/kinige-domain/tests/forest_fixtures.rs`).

**First weekday.** The window reads it once (`getWeekInfo()`, then `weekInfo`, then Monday) and passes it as an argument; the first request of a session also carries which of the three answered (`weekday_source`), and the app writes that to the debug log with the result. The runner scenarios (macOS WKWebView, Windows WebView2) put that line into `week-info.txt`; the result is in `docs/screens/6/`.

**Measured on the 100,000-entry bench** (`docs/screens/6/bench.txt` as committed by each runner run; macOS runner, Apple M1 VM; the budget is `get_forest_year` p95 < 100 ms). `get_forest_year` over 2018..2023, about 16,700 entries a year, p50 / p95 / max:

- Row-by-row scan in Rust (reads `journal_date, created_at, id, body_md` over `message_day`, weighs each day with the domain `day_weight`): commit d1fe4dc 62 / 88 / 159 ms; c711f0b 81 / 159 / 267 ms; 85406d1 (the code that stays) 94 / 182 / 259 ms.
- One SQL `GROUP BY journal_date` aggregate (weight with `length()`, first entry by `MIN(printf(...))`, a NUL special case): 0e77bce 135 / 244 / 466 ms; 7febbf8 138 / 290 / 348 ms.

The aggregate was reverted because it was slower on this bench, and it needed a NUL special path and a SQL-versus-domain equivalence test that the scan does not. The runs of the two versions do not overlap (p50 62..94 ms against 135..138 ms), but one run on the VM varies a lot by itself: the three scan runs span 62..94 ms at p50. p95 is under the budget in one of the three scan runs and over it in two. `forest_day_target` takes 0.2..0.5 ms in every run. The user decided (03.11.2026) to keep the scan and judge the speed on the real Mac at acceptance; if it is noticeable, a per-day stats table maintained on write (KINIG-47) replaces it.

**Cold start** (`cold-start.txt`, empty database, up to the page `load` event, so without the forest query): on the last runner run the median is 1441 ms (min 1320, max 1712), under the 1500 ms target. Earlier runs of this branch gave medians of 1374, 1430, 1675 and 1549 ms, and slice 5 measured 1356 ms on the same kind of VM, so the target is met in some runs and missed in others. The real-hardware number comes from the development Mac (about 400 ms in slices 0-3) and is checked at acceptance.

**Projection (slice 6, found on the first real-window screenshots).** The 45-degree isometry of the spike laid the 53 weeks along a diagonal: in a 1014 x 360 px pane the whole year was a thin ribbon on a third of the width with 17 px tiles, and the bounding box could not be fitted any better. The board is now drawn in an oblique projection (a week is `COL` = (64, 12) world units, a weekday `ROW` = (-26, 50), a cell is a parallelogram, trees stand upright; `web/src/ui/forest/iso.ts`), so the year runs along the width and the whole-year view is limited by the pane's width: the 53 weeks are about 18 px each in a 1280 px window (pane 1014 px) and about 13 px each in a 1024 px window, so the whole year is dots and small shapes and the season buttons are what makes it a forest (the tile there is 40 px or more). The PRD §7.5 render script has to match this projection. Grid B, Canvas 2D and the layer cache are unchanged; the hit-test is the inverse of the 2 x 2 matrix, and the click-through test still shows 0 misses over every day of 2026 and 2028.
