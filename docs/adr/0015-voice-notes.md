# ADR-0015: Voice notes

Date: 2026-11-04. Status: **accepted** (KINIG-16, slice 7a; the product decisions of the slice were made by the coordinator on 04.11.2026 and are reviewed by the user). The synced part is unchanged: a voice note is an `audio` attachment (ADR-0001 appendix §C.6, ADR-0014). The `sync-crypto-guardian` pre-review of the spec is folded in.

## Context
Slice 7a records a voice note from the microphone button, stores it as an attachment of a new entry and plays voice notes (the recorder's and the Telegram import's) in the feed. The open question was where recording should live: in the web view (`getUserMedia` and `MediaRecorder`) or natively. The probe on both runners (`docs/screens/7a-probe*/formats.txt`) decided it.

## Decisions

**Recording in the web view.** `getUserMedia({audio: true})` is called on the first click on the microphone, never at startup (PRD §15). `MediaRecorder` takes the first supported of `audio/mp4;codecs=mp4a.40.2`, `audio/mp4`, `audio/webm;codecs=opus`, with `audioBitsPerSecond` 64 000 and a 1 s `timeslice`; the chunks stay in memory until Send. The probe shows both web views record AAC in MP4 (WKWebView `ftypiso5` fragments, WebView2 `ftypisom`) and that neither honours the 64 kb/s hint with a tone input (measured 3.2 kB/s on WKWebView, 12.5 kB/s on WebView2), so the recorder also sends at 48 MiB. The container is decided in Rust from the first bytes (`ftyp` at offset 4 is `audio/mp4` `.m4a`, the EBML header is `audio/webm` `.webm`, anything else is `attachment_unreadable`), never from what the recorder says. The duration is the recorder's own clock.
**Finding that nearly stopped the slice.** On macOS the page sees `navigator.mediaDevices` only when the bundle's `Info.plist` has `NSMicrophoneUsageDescription`: the first probe, built without the key, reported `mediaDevices: false` on `tauri://localhost` (`isSecureContext` was true), and the second, with the key, `true`. The key therefore ships in `src-tauri/Info.plist` and `build-app.sh` asserts it.
**Alternative not taken:** native recording (`cpal` plus an encoder). Opus needs the C libopus on both OSes, a pure-Rust AAC encoder is not verified to exist, Rust would need its own TCC path, and the web view would still have to play the file.

**Permissions.** `NSMicrophoneUsageDescription` (English) in `src-tauri/Info.plist`; `com.apple.security.device.audio-input` in `src-tauri/Entitlements.plist` (`bundle.macOS.entitlements`); `build-app.sh` asserts both in the built bundle. `tauri::Builder::on_permission_request`: Microphone from the webview `main` is `Allow`; Camera, DisplayCapture and Geolocation are `Deny` for every window, and Microphone from any other label too; everything else is `Default` (which keeps wry's clipboard-read allowance on Windows). Without a handler wry on macOS grants every capture request, camera included. **The deny is not enforced everywhere:** on macOS only camera and microphone requests reach the handler (verified in wry 0.57.0), so Geolocation and DisplayCapture are refused on Windows and Linux only. A page that asks for audio and video together is answered by two handler calls; Allow plus Deny is a Deny. The OS privacy switches stay in force; `NotAllowedError` becomes "Microphone access is off" with "Open settings" (`open_microphone_settings`, a fixed URL: `x-apple.systempreferences:com.apple.preference.security?Privacy_Microphone` or `ms-settings:privacy-microphone`, no argument). TCC likely asks again after every ad-hoc-signed update (not verified).

**`send_voice`.** One raw-body IPC command for the main window (`x-chat-id`, `x-duration-ms`, `x-reply-to`). The store copies the bytes through the attachment pipeline (stage 1) and one writer job inserts the entry (empty body), renames the file, runs the `after_rename` fault hook, inserts the `attachment` and `attachment_local` rows with `duration_ms`, reindexes, marks the day dirty, clears the draft's reply line only when the note took that very reply (`UPDATE draft SET reply_to_id = NULL WHERE key = ? AND reply_to_id = ?` then `delete_empty_draft`; a note sent without a reply, because the target is in the trash, leaves the line as the person had it, so a draft that holds tiles survives) and commits. The microphone is hidden while the draft has tiles. The product limits (1 s to 30 min plus 5 s: `voice_too_short`, `voice_too_long`; 64 MiB) live in `send_voice` only. The domain rule for `attachment.duration_ms` is the one every writer already satisfies: `null` or `0..=4 294 967 295 000` and only for `audio` and `video` (the Telegram import maps a `u32` of seconds); the import now drops a duration from a file whose kind is neither, so a guessed kind cannot fail a batch. The recorder file is named `voice-YYYY-MM-DD-HHMMSS.<ext>` in local time and its search text is the single word `voice` (the date in the name would match "11" or "2026").

**The `audio` route.** `kinige-media://localhost/audio/<uuid>` answers only `main`, only `GET`, only `kind = 'audio'` rows in state `local`. Content type from an allowlist (`audio/mp4 aac mpeg ogg opus wav flac webm`); the first 12 bytes of the file must fit that container (`audio_head_matches`). A row or a file over 64 MiB, an empty file, a purged id or a `missing` file is 404 (the responder holds a whole body in memory). No `Range` (or another unit): 200 with `Content-Length` and `Accept-Ranges: bytes`. One range: 206 with `Content-Range` and an explicit `Content-Length`, at most 1 MiB per answer. Out of bounds, empty suffix, multi-range, or a file that changed under the handler (a short read): 416. Arithmetic is `u64` with `checked_*`. Headers: `nosniff`, the sandbox CSP, no `Access-Control-Allow-Origin`. CSP `media-src 'self' kinige-media: http://kinige-media.localhost`. The player sets `src` only on the first Play. Whether a fragmented MP4 (`ftypiso5`, what both web views record) seeks well over these ranges is **not verified**: no runner scenario seeks, and playback from the start is what the runs prove (the log shows the web view's range requests and their answers).

**Fake microphone for the runners.** `web/vite.config.ts` reads `process.env.KINIGE_FAKE_MIC` (Vite does not put `.env` files there) and aliases `virtual:kinige-mic` to `scripts/screens/fake-mic.ts` (an oscillator into a `MediaStreamAudioDestinationNode`) or to the real module; the probe (`KINIGE_PROBE`) is aliased the same way. The fake file carries a string-literal marker; `scripts/check-fake-mic.sh` fails `build-app.sh` and `build-windows.sh` (so `release.yml` too) when the marker is in `web/dist` unless `KINIGE_ALLOW_FAKE_MIC=1`, which only `screens.yml` sets; the 7a scenarios run the same script with `--expect` as a positive control, and `scripts/check-fake-mic.test.sh` (CI) is the negative control.

**Privacy.** A device label (`MediaDeviceInfo.label`, `track.label`) is never read: not by the recorder, not in the console, a string, the log, Rust or a runner text file. The log gets the status and size of an audio answer at debug level, no ids.

**Limits that stay.** A recording running at `kill -9` or ⌘Q is lost, as in Telegram. No preview, no pause (the waveform came in round 2, below), no hold gesture, no hotkey, no transcription (P2). The Markdown copy writes ` (m:ss)` after an audio link; day files written before 7a keep the old line until the day is next marked dirty (harmless).

**Save errors in the window (round 1 of the review).** The recorder's duration is clamped to 30:00 when the recording is finished, so a late auto-send tick can never meet `voice_too_long` (the store allows 30:05). What a second try cannot change gets no Retry: `voice_too_short` and `voice_too_long` end the recording with a line above the field ("Too short to save", "Too long to save"); `reply_target_not_found` sends the note once more with no reply (the recording is kept, the quote is dropped); `chat_not_found`, `attachment_unreadable` and a reply error with no reply left leave Discard only, with the reason in words; everything else (a full disk) keeps the bytes for Retry. A device lost mid-recording whose bytes cannot be read ends with "The microphone is unavailable", never a stuck bar.

**Player (product decisions of 04.11.2026; the layout was replaced in round 2 below, the speed rule stands).** The speed (1× → 1.5× → 2× → 1×) is **one setting for all voice notes**, as in Telegram, for the session and not saved: every chip shows it, pressing any chip cycles it for all of them and a note that is playing follows at once. At rest the time slot holds only the total ("0:40") and the seek bar takes the room (player width 22rem = 286 px at a 13 px root, about 160 px of seek bar); once a note has been started the slot widens to "0:12 / 0:40", so the bar changes width once, on the first Play, and then stays still.

## Round 2 (05.11.2026, acceptance feedback): the Telegram-like voice UI, a local waveform, smooth progress

The user rejected the first design ("very weak, like an old app") and asked for Telegram desktop's voice messages. Three changes, with the decisions that go with them. **Decision 5 of the slice ("no waveform: it needs a synced field or a decoder") is replaced** by the first of them.

**A waveform that is local to the device.** A voice note has 64 peaks (0 to 255, the loudest part 255). They are stored in one new nullable column, `attachment_local.waveform` (migration 8, `ALTER TABLE .. ADD COLUMN`, no default, a metadata change). `attachment_local` is where ADR-0014 puts what only this device knows (the state and the stored file name); the synced `attachment` row, its `core` group and ADR-0001 appendix §C.6 do not change (a test compares every column of every synced row before and after a save, and another that the migration changes none). Three values: `NULL` is not known yet, an empty blob means "the decoder could not read this file, do not try again", and 64 bytes are the peaks. A migration runs in one transaction with `user_version`, so a kill during it leaves version 7 and an intact database; tests: an upgrade from a slice 7 database keeps every row and the note still plays, running it again changes nothing, a child process that dies by `abort` right after a save finds the waveform after a restart. A waveform is cosmetic and bounded (64 bytes, hex on the wire), so a wrong one is dropped, never a reason to lose a note: `send_voice` ignores an `x-waveform` header that does not read as 64 peaks and saves the note without it.
- *Source (a), the recorder.* The analyser the recorder already had (now 2048 samples, read every 50 ms, one level per read; a timer that fires late, as in a hidden window, still gets a level for every missed period) gives the levels. They draw the live waveform and, at the end, become the 64 peaks (the loudest level of each bar's share of the recording, scaled so the loudest is 255) that go with `send_voice` in the `x-waveform` header. A recording with no analyser, or in total silence, sends none.
- *Source (b), the lazy decoder.* A note with no waveform in its row (a Telegram import, a note from before this round) is decoded when its player first shows on screen (an `IntersectionObserver`): `OfflineAudioContext` at 8 kHz (no audio device needed, a 30 minute note takes 58 MB), one decode at a time for the whole window, the loudest window of 50 ms for each bar. Files over 16 MiB or notes over 20 minutes are not read at all and get the empty marker; a file the web view cannot decode (probably Ogg Opus in WKWebView) gets the empty marker too; a read that fails now (the file is gone for the moment) saves nothing and is tried again the next time the note shows. Until peaks exist the player draws neutral placeholder bars of the same layout, so the bubble never changes size.
- *Two IPC commands, `main` only.* `read_voice_for_waveform` (a raw answer with the stored bytes: every check of the `audio` route, plus the 16 MiB cap) and `set_attachment_waveform` (64 bytes as hex, or empty; the first value wins so two renders cannot fight; wrong length is `attachment_unreadable`, an id that is not a live `audio` row with a local row is `attachment_not_found`). **A deviation from the first design:** the decoder does not `fetch` the `audio` route. That route is deliberately not cross-origin readable and the page's CSP `connect-src` is `ipc:` only; opening both for one cosmetic feature, in two web views whose behavior for custom schemes could only be seen on the runners, was a wider change than one more main-only command. Tests (`src-tauri/tests/ipc_waveform.rs`, `crates/kinige-store/tests/voice_waveform.rs`): the other windows are refused, garbage hex, wrong lengths, bad ids, wrong argument shapes and a non-audio attachment are errors that write nothing. The test of the first command found that the handle the route's checks return has already read the first 12 bytes; `audio_for_waveform` seeks back to the start (the doc of `AudioFile` now says so).

**The player (`VoicePlayer`).** A 41 px round accent button; to its right 64 bars 2 px wide with 1.4 px gaps (about 225 px), played bars in the accent, the rest in a new muted token `color.voice.unplayed` (clearly muted, as in Telegram: 3.3:1 away from the accent of the played bars, a UI-threshold pair in the contrast tests, so the edge of the fill is obvious; the first try, 2.0:1 away, made the fill invisible in the real window, found by the coordinator in `05-playing.png`; against the plate 2.2:1, a new `graphic` threshold of 2:1, and 1.6:1 on the highlighted plate, a short-lived jump target). The fill itself renders in WKWebView: `clip-path: inset()` on a layer of plain spans, no mask, no `background-clip`, no custom property inside a gradient (the custom property only sets the inset), and the macOS shot shows the cut; under the waveform the meta line, the total ("0:40") at rest and the elapsed time while playing, then ", 20.7 kB"; the small speed chip appears on that line once the note has been started and stays (the scenarios press it after a note may have ended); the bubble's time sits at the bottom right on the same line (a voice note with no text reserves no extra line for it). The waveform is a slider: click or drag seeks (the fill follows the pointer at once, the file moves when the button is released), the arrow keys move by 5 s, Home and End jump; role `slider`, value text "0:12 of 0:40", name "Position". The bars are two layers of the same spans (muted below, accent above cut by `clip-path`), so the fill stops inside a bar, not only between bars.
- *Smooth progress.* While a note plays, one `requestAnimationFrame` after another reads `audio.currentTime` and writes `--voice-progress` straight into the waveform element (the `timeupdate` event fires about four times a second, which was the choppiness). The text and the slider value are state, changed only when the whole second changes. The loop stops on pause, on `ended`, on unmount and while the page is hidden (`visibilitychange`), and starts again when it shows. Only the player re-renders, never the feed; vitest covers the loop (it runs while playing, stops on pause, end, unmount and a hidden page, and moves the fill by a part of a bar between two frames).

**The recording bar.** A canvas fills the whole middle of the bar between the timer and Send; new bars enter from the right and scroll left. It draws on its own animation frames from the recorder (`levels(count)`, never React state: the feed does not re-render, the render-count tests still pass); the sub-bar offset is the time since the newest level, so a new sample continues exactly where the last frame ended. Lengths come from the tokens (`layout.voice.rec-wave-*`, read from the computed style), the colour from CSS. With Reduce Motion the strip does not slide: it steps ten times a second. The first design hid the meter under Reduce Motion; the waveform is the microphone's level, information and not decoration, so it stays. The palette has one theme (dark), so there was no light theme to check.

**The fake microphone** now swings the tone's gain through silence with three slow oscillators, so the recording bar and the recorded note have a varied waveform on the runners. The production code no longer reads marks off the stream (`withoutMeter`, `maxRecordingMs`): the real analyser runs on the fake source, and the 14 second limit of the scenario is a typed export of the virtual module (`recordingLimitMs`, `null` in a normal build).
