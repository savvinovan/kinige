# ADR-0009: MCP — сервер в процессе приложения, `kinige-mcp` — мост stdio ↔ сокет

Дата: 2026-10-28. Статус: **предложено** (перед слайсом 4a). ТЗ §3.2 («один писатель»), §4.1, §9.3, §10, §12.3; ADR-0001 (`origin`, §2, §4, «Не решается»), ADR-0006, ADR-0008; спецификация `docs/slices/4a-mcp.md`.

## Контекст
ТЗ §9.3 требует отдельный бинарник `kinige-mcp` с транспортом stdio: его запускает MCP-клиент (Claude Desktop, Claude Code). Главный вопрос — как этот процесс и приложение делят базу. Правило ТЗ §3.2: все записи идут через один поток-владелец соединения. Сейчас `Store::open` делает больше, чем открывает файл. Он запускает миграции с копией перед ними, создаёт `device_id`, перестраивает индекс поиска, поднимает поток Markdown-копии, обслуживание (корзина, `integrity_check`, копия дня) и хук повреждения. Восстановление из копии переименовывает файл базы (`recovery.rs`).

## Решение
**Сервер MCP работает внутри приложения. `kinige-mcp` — глупый мост:** строки JSON-RPC из stdin он пересылает в Unix-сокет приложения, ответы — обратно в stdout. Базу мост не открывает. Ни `kinige-store`, ни `kinige-domain` он не знает. Из MCP ему известно только поле `id` запроса.
- **Сокет:** `<каталог данных>/mcp/kinige.sock`. Папка `mcp/` с правами 0700, старый файл сокета удаляется перед `bind`. Длина пути ограничена: на macOS `sun_path` — 104 байта (по памяти; в single-instance 2.5.4 есть комментарий «socket path must be shorter than 100 chars»). Путь длиннее 100 байт — MCP недоступен с явной ошибкой в настройках. Приложение слушает сокет, пока журнал открыт (`start_services`), при любом положении переключателя: выключенный доступ отвечает отказом на каждый вызов. Это не сетевой порт. Подключиться может только тот же пользователь, а он и так читает файл базы (§4.1).
- **Кадрирование** — как у stdio-транспорта MCP: одно сообщение JSON-RPC на строку, без переводов строки внутри (по памяти о спецификации, сверить). Тот же формат идёт и по сокету, поэтому своего протокола IPC нет.
- **Приложение не запущено.** Что делать — вопрос 1 спецификации. Рекомендация: мост запускает Kinige в фоне (`open -g -a <свой бандл> --args --background`) и ждёт сокет до 10 с. Не дождался — отвечает на каждый запрос ошибкой JSON-RPC с тем же `id` и понятным текстом. При обрыве мост переподключается и повторяет сохранённый `initialize` клиента, ответ на повтор не пересылается.
- **Права проверяет Rust приложения в каждом вызове:** включён ли доступ, режим, разрешённые чаты, `ai_excluded`, корзина. Клиенту и мосту не доверяем.

**Отклонено:**
- *Свой писатель в `kinige-mcp` под блокировкой файла.* Второй экземпляр должен был бы повторить всё, что делает `Store::open`. Без этого Markdown-копия и лента главного окна не узнают о записи агента. Мост из другой версии мог бы мигрировать базу. Соединение, открытое во время восстановления, писало бы в переименованный файл, и запись терялась бы молча. Правила доступа существовали бы в двух копиях.
- *Чтение напрямую из файла, запись через приложение.* Журнал обращений требует записи и при чтении (§12.3: «каждое обращение пишется в журнал»). Получились бы два пути с разными отказами, а читатель зависел бы от версии схемы.

**Крейт MCP — `rmcp`** (официальный Rust SDK, `github.com/modelcontextprotocol/rust-sdk`). Он ставится только в `src-tauri`: сервер с транспортом поверх `tokio::net::UnixStream`. Мост обходится стандартной библиотекой, без зависимостей. Версия, лицензия (по памяти MIT или Apache-2.0), транспорт поверх произвольного `AsyncRead + AsyncWrite`, нужен ли `schemars` — **не проверено**: в этой сессии не было доступа к crates.io и docs.rs, локального кэша крейта нет. Сверка в первый час слайса, результат записывается сюда. Критерии отказа:
- лицензия не MIT и не Apache;
- последний релиз младше двух недель (правило ADR-0007);
- нельзя отключить HTTP-транспорты;
- не собирается на нашем toolchain.

При отказе пишем свой минимальный сервер на `serde_json`: `initialize`, `ping`, `tools/list`, `tools/call`, `notifications/initialized`. `tokio` уже в дереве (1.54). `tokio::net::UnixListener` использует `tauri-plugin-single-instance` 2.5.4 — проверено по исходникам.

**Настройки и журнал обращений — локальные, не синхронизируются.** Настройки — ключи `app_setting` `mcp_enabled`, `mcp_mode`, `mcp_chats` (JSON-массив id). Журнал — таблица `mcp_log`, миграция 5, хранится 90 дней. Агент работает на этом компьютере (§9.3 «локально»). Синхронизация настроек вынесена из ADR-0001 («Не решается»). В outbox и в конверты ни то ни другое не попадает. Id чатов стабильны, поэтому синхронизацию настроек можно добавить позже без переделки. Если запись меняет данные, строка журнала пишется в той же транзакции.

**`origin = 'agent'`.** Новое значение неизменяемого `core.origin` аддитивно, `sv` не повышается (ADR-0001, «origin»). Запись строится тем же `groups::new_message`, но с другим происхождением, без `ext`. Имя клиента (`clientInfo` из `initialize`, клиент сообщает его сам) хранится только в журнале, не в `core`. Байты дописываются в приложение ADR-0001, §C.4.

**Пометка «текст уйдёт провайдеру модели».** В MCP такого поля нет. Гарантия — предупреждение Kinige при включении (ТЗ §9.3). В протоколе остаётся только информация без гарантии показа: `instructions` в ответе `initialize`, описания инструментов, `readOnlyHint` у инструментов чтения. Поле `instructions` и аннотации есть в спецификации с ревизии 2025-03-26, по памяти. Показывают ли их клиенты — не проверено.

**Сборка.** `kinige-mcp` — член workspace `crates/kinige-mcp`. В бандл он попадает через `bundle.externalBin` (`binaries/kinige-mcp-<target-triple>`; шаблон имени проверен по `tauri-utils` 2.10.2). Ожидаемое место — `Kinige.app/Contents/MacOS/kinige-mcp` (не проверено). Покрывает ли ad-hoc-подпись вложенный бинарник, покажет `codesign --verify --deep` в `scripts/build-app.sh`.

## Последствия
- Агент работает, только пока Kinige запущен или его можно запустить. Из-за этого записи агента сразу видны в ленте, а копия, обслуживание и восстановление остаются одним путём.
- Windows (слайс 10): Unix-сокета в std там нет, нужен именованный канал. На Linux — тот же сокет.
- Мост не знает версий MCP, их согласует сервер в приложении.
- Не проверено: `rmcp` (версия, лицензия, API), кадрирование stdio по тексту спецификации, путь вложенного бинарника и подпись, синтаксис `claude mcp add` и путь `~/Library/Application Support/Claude/claude_desktop_config.json` (по памяти), что `open --args` передаёт аргументы, только когда приложение запускается, а не уже запущенному (по памяти; на этом держится запуск в фоне: запущенное приложение получит повторный запуск через single-instance).
