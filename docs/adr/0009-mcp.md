# ADR-0009: MCP — the server inside the app process, `kinige-mcp` as a stdio ↔ socket bridge

Date: 2026-10-28. Status: **accepted** (slice 4a implemented, awaiting acceptance). Revision 4 — the follow-up after the reviews of `sync-crypto-guardian` and `slice-reviewer` (panics, protocol version, the "reconnected" row, the log's entry counter, activation policy); revision 3 — after the second round of the `sync-crypto-guardian` review (targeted); revision 2 — after the first one ("needs work").

Basis:
- PRD §3.2 ("one writer"), §4.1, §9.3, §10, §12.3;
- ADR-0001 (`origin`, §2, §4, "Not settled"), ADR-0006, ADR-0008;
- the spec `docs/slices/4a-mcp.md`.

## Context
PRD §9.3 requires a separate binary `kinige-mcp` with the stdio transport. It is launched by the MCP client: Claude Desktop or Claude Code. The main question is how this process and the app share the database. By the rule of PRD §3.2, all writes go through one thread that owns the connection.

`Store::open` does more than open the file:
- it runs migrations and takes a backup before them;
- it creates `device_id`;
- it rebuilds the search index;
- it starts the Markdown copy thread, maintenance (trash, `integrity_check`, daily backup) and the corruption hook.

Restoring from a backup renames the database file (`recovery.rs`).

## Decision
**The MCP server runs inside the app. `kinige-mcp` is a bridge:** it forwards JSON-RPC lines from stdin to the app's Unix socket, and the responses back to stdout.
- The bridge does not open the database. It knows neither `kinige-store` nor `kinige-domain`.
- From each message the bridge reads only `id` and `method`. It needs nothing else to answer on a disconnect and to repeat the handshake.

**The bridge and a lost connection.**
- **Unanswered requests.** The bridge remembers the client's unanswered requests. A request is a message that has both `method` and `id`. A message with `id` but without `method` is the client's response to a server request, not a request: it does not go into the table.
- **Disconnect.** On a disconnect the bridge answers each unanswered request with the JSON-RPC error «соединение с Kinige потеряно, проверьте журнал обращений» ("connection to Kinige lost; check the access log"). It **never resends** requests: an `add_entry` in flight may already have been written. A server request to the client that arrived before the disconnect is lost together with the connection.
- **Handshake.** The bridge saves the client's `initialize` and `notifications/initialized`. After reconnecting it repeats both and does not forward the response to the repeated `initialize` to the client. Prototype 4a.0 showed: `rmcp` 3.5.1 accepts calls even **without** `notifications/initialized`, but does **not** accept them without `initialize` (an error about missing `_meta` fields). Repeating `initialize` is mandatory; the bridge repeats the notification to comply with the MCP spec and to be independent of the SDK's behavior.
- **Before the handshake.** If the client has not sent `initialize` yet, there is nothing to repeat: the very first request goes into the new connection as is.
- **Reconnect marker.** The bridge starts a new connection after a disconnect with the line `{"jsonrpc":"2.0","method":"kinige/reconnect"}`, before the repeated `initialize`. The server reads it up to the first `\n` (it may arrive in parts; no more than its length is read, the rest is handed to the service as the beginning of the stream), and it does not reach the service. The log writes one "reconnected" row (`tool = 'reconnect'`) instead of a second "connected"; before it, the previous open session of the same client is closed with a "disconnected" row. If the handshake on the new connection did not write the row (the client sent a call without `initialize`, and the bridge repeated it to no effect), the row is written lazily on the first `tools/call`.
- **Protocol version, and `initialize` is mandatory.** `rmcp` 3.5.1 understands a "built-in lifecycle" (`_meta.protocolVersion` in the request itself instead of `initialize`), and then `tools/call` and `tools/list` go through without a handshake, without a client name and without a "connected" row. Restricting the list of versions (`supported_protocol_versions` → `known_up_to(V_2025_11_25)`) is not enough: guardian verified that the version `2025-11-25` in `_meta` is in the list and lets the call through (the entry was created, `unknown` in the log). So `list_tools` and `call_tool` themselves require that the connection has had `initialize` (the client is named); otherwise the response is `ErrorData::invalid_request` without touching the database or the log. Test — versions `2026-07-28` and `2025-11-25` in `_meta`: an error, no entry, the log did not grow, and an ordinary handshake works afterwards. `rmcp` serves `server/discover` (`DiscoverRequest`) only from `get_info` before the version check: the server name and `instructions`, no data.
- **The bridge's own errors.** A client line that is not a JSON object gets a −32700 response with `id: null` and is not forwarded anywhere (the app is not launched because of garbage). A line longer than 4 MiB gets an error with the real `id` if it is within the first 64 KiB, otherwise with `null`.

**The app is not running** (the user's decision, 28.10.2026). The bridge launches Kinige in the background itself:
1. First it checks whether there is an app process from its own bundle.
   - The process exists but there is no socket — it waits for the socket the same 10 s: the app may still be starting. If it does not get it — `journal_unavailable` (recovery, a startup failure). `open` is not called: a running app would receive it as Reopen and show the main window.
2. There is no process — `open -g -a <own bundle> --args --background`, waiting for the socket up to 10 s.
3. If it does not get it — every request gets a JSON-RPC error with the same `id` and the text «Откройте Kinige» ("Open Kinige").

**No Dock icon.** Launching with `--background` sets the Accessory activation policy (`App::set_activation_policy` before `run`; verified against `tauri-2.12.4/src/app.rs` and `tao-0.37.1`): no window, no Dock icon, only the menu bar icon. Any showing of the main window (the tray menu, Reopen, a second launch without the flag) first sets the Regular policy, and the icon appears. Hiding the window does not touch the policy: the icon stays, as with an app launched normally.

**Failures of background threads are not silent.** The release profile is built without `panic = "abort"`. The socket listener, database reads (`read_unnoted`), the Markdown copy thread and the maintenance thread catch panics (`catch_unwind` or `JoinHandle`), write `log::error!`, put the error into the state (the "AI agent access" window, "Settings"), and the thread keeps working or the listener rebinds. A first failed `bind` is not the end either: binding is retried once per check interval, and the error is cleared on success.

The main window in `tauri.conf.json` is `visible: false`. `setup` shows it itself if `--background` is not among the arguments. In Tauri 2.12.4 (the version in `Cargo.lock`), windows from the config are created before the user's `setup` — verified against the sources (`tauri-2.12.4/src/app.rs`, the function `setup`).

**Socket.**
- **Path** — `<data directory>/mcp/kinige.sock`.
- **A long path.** If the path is longer than 104 bytes (`sun_path` on macOS; single-instance 2.5.4 has the comment "socket path must be shorter than 100 chars"), a fallback path `$TMPDIR/kinige-mcp/<short hash of the data directory>.sock` is used. The folder `kinige-mcp/` gets the same checks as `mcp/` (below). The path goes into the connection snippet. macOS may clean old files out of `$TMPDIR` (not verified). So every 10 minutes the listener checks that its socket file is in place, and if it is gone, rebinds to the same path with the same checks.
- **Folder.** `mcp/` is checked via `symlink_metadata`: it is not a symlink, the owner is the current user, the permissions are 0700. If not, MCP is unavailable, and the error is visible in the settings.
- **A second Kinige.** Before deleting an old socket file, the app tries to connect to it. If it answered, this is a second Kinige on the same data: it does not start its own server, and this is reported in the settings. If it did not answer, the file is deleted, then `bind` and `chmod 0600`.
- **Another user.** `peer_cred()` is checked for every incoming connection: if the uid is not ours, the connection is closed.
- **Frame limit.** One frame line is no more than 4 MiB: on the server `JsonRpcMessageCodec::new_with_max_length`, in the bridge the same limit. Longer — an error, the connection is closed.
- **Startup order.** The listener starts **last** in `start_services`, after `app.manage(store)`. The socket is deleted in `RunEvent::Exit`.
- **A socket failure does not stop the journal.** If `bind` failed, `start_services` still completes successfully: the journal works, and the socket error is visible in `get_agent_access`. If `chmod` after `bind` failed, the socket file is deleted, with the same error.
- **The store in every call.** Every call takes `app.try_state::<Store>()` anew and checks `Recovery::corruption_found()`. No clone of `Store` is kept in the server's tasks: a restore from a backup must not run into a live writer handle.
- **When `journal_unavailable`.** Only in two cases:
  - the journal was not opened at startup (recovery mode) — then there is no listener, and the bridge gives this response;
  - `corruption_found()`.

This is not a network port. Only the same user can connect, and that user reads the database file anyway (§4.1).

**What is visible while access is off.** The app listens in any position of the switch. The client sees:
- the server name and version;
- `instructions`;
- the names and descriptions of the tools.

No data is visible: every tool call gets `mcp_disabled`.

**Framing.** MCP 2025-06-18: one JSON-RPC message per line, without newlines inside. The same format goes over the socket, so there is no IPC protocol of our own.

**Permissions are checked by the app's Rust in every call. We do not trust the client, the bridge or `clientInfo.name`.**
- The visible set of chats: the chat is in `mcp_chats`, it does not have `ai_excluded`, and it is not deleted.
- **The predicate in every statement.** Every read statement of the agent carries the visible-set predicate itself: `json_each` over the `app_setting` value. The chat list for the "Chats" row in search is a separate statement with the same predicate, not a filter in Rust as `search_query.rs` does now. Between the statements of one call the set may change — this is acceptable, each statement is checked. For a write, the check happens inside the writer transaction.
- **A single `not_found`.** Any `chat_id` or `id` outside the set gets the same `not_found` in all tools, as a non-existent one would. This applies to a closed chat, to `ai_excluded`, to a deleted one — and to Inbox by default, if it is not marked.
- **The value of `mcp_chats`.** No key — the set is empty. Damaged JSON — an error without data. Ids that are not in the database (for example, after a restore from a backup) are silently ignored.

**Do not write content to logs.** Neither the bridge nor the app writes frames, arguments or texts to stderr or the log. Logs contain only error categories and the request `id`. The app follows the project-wide rule: output via `log`, `print_stdout`/`print_stderr` = deny. The rule is introduced by a separate PR. The bridge has no dependencies, so it has one function for output to stderr with a deliberate `#[allow]` and a comment.

**Rejected.**
- *A writer of its own in `kinige-mcp` under a file lock.* The second process would have to repeat everything `Store::open` does:
  - without it, the Markdown copy and the main window's feed would not learn about the agent's entry;
  - a bridge of a different version could migrate the database;
  - a connection opened during a restore would write into the renamed file, and the entry would be lost silently;
  - the access rules would exist in two copies.
- *Reading directly from the file, writing through the app.* The access log is written on reads as well (§12.3). There would be two paths with different failures, and the reader would depend on the schema version.

**The MCP crate is `rmcp` 3.5.1** (2026-10-05, Apache-2.0). It is the official Rust SDK, `github.com/modelcontextprotocol/rust-sdk`; guardian checked the facts.
- The latest release is 3.8.0 of 2026-10-26. It is younger than two weeks, so it is not taken (the rule of ADR-0007).
- Default features: `default = ["base64", "macros", "server"]`. We take `default-features = false, features = ["server"]`: the `#[tool]` macros are not needed (the tools are described by hand), and the HTTP transports are separate features, which are off. The version is pinned with `=3.5.1`.
- `IntoTransport` is implemented for any `AsyncRead + AsyncWrite`, including `tokio::net::UnixStream`.
- The MCP 2025-06-18 schema has `instructions` and `readOnlyHint`.
- It is added only to `src-tauri`. The bridge is std only.
- `tokio` is already in the tree (1.54). `tokio::net::UnixListener` is used by `tauri-plugin-single-instance` 2.5.4 — verified against the sources.
- **Verified in 4a.0 (28.10.2026), a prototype outside the repository:**
  - `rmcp` 3.5.1 with the default features builds on toolchain 1.94.0 (a cold build of 21 s in dev).
  - The server over `tokio::net::UnixStream` works: `initialize` → `tools/list` → `tools/call`, `clientInfo` is visible in `peer.peer_info()`, `readOnlyHint` goes into `tools/list`.
  - **Frame limit.** `AsyncRwTransport` (what `UnixStream` turns into) does **not use** the `JsonRpcMessageCodec::new_with_max_length` limit: it reads a line via `read_until` without a bound. So the 4 MiB limit is set by a wrapper over the reading half of the socket, which counts the bytes since the last `\n` and returns an I/O error; the service then exits, and the connection is closed.

**Settings and the access log are local and not synchronized.**
- Settings are the `app_setting` keys: `mcp_enabled`, `mcp_mode`, `mcp_chats` (a JSON array of ids).
- The log is the tables `mcp_log` and `mcp_log_message`, migration 5.
- Why local:
  - the agent works on this computer (§9.3 "locally");
  - settings sync is out of ADR-0001's scope ("Not settled");
  - neither the settings nor the log go into the outbox and envelopes;
  - chat ids are stable, so sync can be added later without rework.

The log stores **the fact of a request, not the content**:
- `args_json` — only `chat_id`, dates, limits, flags, the item number `item` (`set_task_done`) and `query`, truncated to 128 characters. The `text` field and the item's text are never there.
- `set_task_done(id, done, item?, item_text?)`: item numbers shift if the user edits the entry after it was read, so the tool description asks to pass `item_text` (the item's text, as `tasks` returns it) together with `item`. If it does not match the text of the item under that number — `invalid_argument` "checklist item changed; re-read the entry", nothing written; without `item_text` the number is accepted as is. The `item_text` itself lives only in the call's memory and does not go into `args_json`. The responses of the write tools, like `get_entry`, go through `fit_entries` (no more than 1 MiB).
- The ids of the affected entries are in the child table `mcp_log_message(log_id, message_id)` with an index on `message_id`. Deleting an entry forever (`purge`) deletes its rows from `mcp_log_message` in the same transaction. The fact of the request stays, and **so does the request's entry count**: it is in the column `mcp_log.entry_count`, written by the same transaction as the log row, and `purge` does not touch it. The window shows the number from it; expanding shows the remaining entries and the row "N more deleted forever" (N = `entry_count` minus the number remaining). Otherwise deleting an entry would rewrite history: "search · 2 entries" would become "1 entry".
- Retention: 90 days **and** no more than 20,000 rows — whichever comes first. Rotation deletes, in the same transaction, the `mcp_log_message` rows of the deleted log rows: no orphans are left.
- `client` is what the client said about itself: truncated to 64 characters, control characters removed. In the window this name is not presented as verified.
- Transactions:
  - a data change and the log rows are one transaction;
  - a read goes in steps:
    1. the query on the read connection;
    2. one writer transaction with the `mcp_log` row and the `mcp_log_message` rows;
    3. commit;
    4. the response to the agent.

    If the commit fails, the agent gets an error, no data.
- **What counts as a request** (§12.3: "every request is written to the log"): a tool call (`tools/call`) and a connection. A connection is written as one row on `initialize` with the sanitized `client`, a disconnection as one row. `ping`, `tools/list` and a repeated `initialize` from the bridge do not produce rows of their own.

**`origin = 'agent'`.**
- This is a new value of the immutable `core.origin`. It is additive; `sv` is not bumped (ADR-0001, "origin").
- The entry is built by the shared `groups` builder with a different origin, without `ext`.
- **Append.** The agent's "own" entry is any entry with `origin = 'agent'`, from any client. The append target is the latest live entry of the chat in `(journal_date, created_at, id)` order. If its `origin ≠ 'agent'`, it is not from today, or it is older than 10 minutes — the response is `no_agent_entry`.
- **Revision.** An agent's append writes an `edit` revision, unlike ⌘Enter: the user may have edited the entry.
- **ADR-0001 appendix, §C.4.** The bytes of `core` and of `flags` with `task = true` are added there, as well as the exception to §A.0 — an `edit` revision on an agent's append.

**The note "the text goes to the model provider".** MCP has no such field. The guarantee is Kinige's warning when access is turned on (PRD §9.3). The protocol has only information the client may not show: `instructions`, tool descriptions, `readOnlyHint` on read tools. Whether clients show them is not verified.

**Build.**
- `kinige-mcp` is a workspace member `crates/kinige-mcp`.
- It gets into the bundle via `bundle.externalBin` (`binaries/kinige-mcp-<target-triple>`; the name template is verified against `tauri-utils` 2.10.2).
- Its place in the built `.app` is `Kinige.app/Contents/MacOS/kinige-mcp`: verified by a build in 4a.6 (in the project the bridge binary is called `kinige-mcp-bridge` and is renamed during packaging so that the name does not clash with the cargo binary).
- The ad-hoc signature of the nested binary is checked by `codesign --verify --deep` in `scripts/build-app.sh`; the check passes on the built bundle.

## Consequences
- The agent works only while Kinige is running or can be launched. In return, the agent's entries are immediately visible in the feed, and the copy, maintenance and restore stay on one path.
- There is no `notifications/tools/list_changed`. After a mode change, the client shows the old tool list until it reconnects; the access window says so.
- The first write of the Markdown copy during a background launch may trigger the system request for access to the "Documents" folder without an open window. This is known behavior and is not fixed.
- Windows (slice 10): std has no Unix socket there; a named pipe is needed. On Linux — the same socket.
- The bridge does not know MCP versions; the server in the app negotiates them.
- Verified in 4a.0: the `rmcp` 3.5.1 build; repeating `initialize` is mandatory, repeating `notifications/initialized` is not (see above); the syntax `claude mcp add [options] <name> <commandOrUrl> [args...]` (Claude Code 2.1.312, `claude mcp add --help`; the default scope `local` is the current project only, hence `--scope user` in the snippet); Claude Code has the flags `--mcp-config <files…>` and `--strict-mcp-config`; the file `~/Library/Application Support/Claude/claude_desktop_config.json` exists on this Mac (its contents were not read).
- Not verified:
  - whether macOS cleans sockets out of `$TMPDIR` (hence the check every 10 minutes);
  - the path of the nested binary and the signature (task 4a.6; verified, see "Build");
  - whether real clients show `instructions`, descriptions and `readOnlyHint`; how Claude Desktop behaves on a disconnect (the user will check at acceptance).
