# ADR-0009: MCP — сервер в процессе приложения, `kinige-mcp` — мост stdio ↔ сокет

Дата: 2026-10-28. Статус: **предложено** (перед слайсом 4a). Ревизия 2 — по ревью `sync-crypto-guardian` («доработать»).

Основа:
- ТЗ §3.2 («один писатель»), §4.1, §9.3, §10, §12.3;
- ADR-0001 (`origin`, §2, §4, «Не решается»), ADR-0006, ADR-0008;
- спецификация `docs/slices/4a-mcp.md`.

## Контекст
ТЗ §9.3 требует отдельный бинарник `kinige-mcp` с транспортом stdio. Его запускает MCP-клиент: Claude Desktop или Claude Code. Главный вопрос — как этот процесс и приложение делят базу. По правилу ТЗ §3.2 все записи идут через один поток, который владеет соединением.

`Store::open` делает больше, чем открывает файл:
- запускает миграции и снимает копию перед ними;
- создаёт `device_id`;
- перестраивает индекс поиска;
- поднимает поток Markdown-копии, обслуживание (корзина, `integrity_check`, копия дня) и хук повреждения.

Восстановление из копии переименовывает файл базы (`recovery.rs`).

## Решение
**Сервер MCP работает внутри приложения. `kinige-mcp` — мост:** строки JSON-RPC из stdin он пересылает в Unix-сокет приложения, ответы — обратно в stdout.
- Базу мост не открывает. Ни `kinige-store`, ни `kinige-domain` он не знает.
- Из каждого сообщения мост читает только `id` и `method`. Больше ему ничего не нужно, чтобы отвечать на обрыв и повторять `initialize`.

**Мост и обрыв связи.**
- Мост помнит `id` неотвеченных запросов. При обрыве он отвечает на каждый из них ошибкой JSON-RPC «соединение с Kinige потеряно, проверьте журнал обращений». Запросы он **никогда не отправляет повторно**: `add_entry` в полёте мог уже записаться.
- После переподключения мост повторяет только сохранённый `initialize`. Ответ на повтор клиенту не пересылается.
- Если клиент ещё не прислал `initialize`, повторять нечего: первый же запрос идёт в новое соединение как есть.

**Приложение не запущено** (решение пользователя, 28.10.2026). Мост сам запускает Kinige в фоне:
1. Сначала проверяет, есть ли процесс приложения из своего бандла.
   - Процесс есть, а сокет не отвечает — журнал недоступен (восстановление, сбой запуска). Мост отвечает `journal_unavailable` и `open` не вызывает. Иначе `open` пришёл бы запущенному приложению как Reopen и показал бы главное окно.
2. Процесса нет — `open -g -a <свой бандл> --args --background`, ожидание сокета до 10 с.
3. Не дождался — на каждый запрос ошибка JSON-RPC с тем же `id` и текстом «Откройте Kinige».

Главное окно в `tauri.conf.json` — `visible: false`. Tauri 2.12.5 создаёт окна до `setup`, поэтому `setup` показывает окно сам, если в аргументах нет `--background`.

**Сокет.**
- **Путь** — `<каталог данных>/mcp/kinige.sock`.
- **Длинный путь.** Если путь длиннее 104 байт (`sun_path` на macOS; в single-instance 2.5.4 есть комментарий «socket path must be shorter than 100 chars»), берётся запасной путь `$TMPDIR/kinige-mcp/<короткий хэш каталога данных>.sock`. Для папки `kinige-mcp/` действуют те же проверки, что для `mcp/` (ниже). Путь попадает во фрагмент подключения.
- **Папка.** `mcp/` проверяется через `symlink_metadata`: это не симлинк, владелец — текущий пользователь, права 0700. Если это не так, MCP недоступен, ошибка видна в настройках.
- **Второй Kinige.** Перед удалением старого файла сокета приложение пробует к нему подключиться. Если ответил — это второй Kinige на тех же данных: свой сервер не поднимается, об этом сообщается в настройках. Если не ответил — файл удаляется, затем `bind` и `chmod 0600`.
- **Чужой пользователь.** У каждого входящего соединения проверяется `peer_cred()`: uid не свой — соединение закрывается.
- **Предел кадра.** Одна строка кадра — не больше 4 МиБ: на сервере `JsonRpcMessageCodec::new_with_max_length`, в мосте — тот же предел. Длиннее — ошибка, соединение закрывается.
- **Порядок запуска.** Слушатель стартует **последним** в `start_services`, после `app.manage(store)`. Сокет удаляется в `RunEvent::Exit`.
- **Хранилище в каждом вызове.** Каждый вызов заново берёт `app.try_state::<Store>()` и проверяет `Recovery::corruption_found()`. Хранилища нет или стоит флаг — ответ `journal_unavailable`. Клон `Store` в задачах сервера не хранится: восстановление из копии не должно застать живой дескриптор писателя.

Это не сетевой порт. Подключиться может только тот же пользователь, а он и так читает файл базы (§4.1).

**Что видно, пока доступ выключен.** Приложение слушает при любом положении переключателя. Клиент видит:
- имя и версию сервера;
- `instructions`;
- имена и описания инструментов.

Данных не видно: каждый вызов инструмента получает `mcp_disabled`.

**Кадрирование.** MCP 2025-06-18: одно сообщение JSON-RPC на строку, без переводов строки внутри. Тот же формат идёт по сокету, поэтому своего протокола IPC нет.

**Права проверяет Rust приложения в каждом вызове. Клиенту, мосту и `clientInfo.name` не доверяем.**
- Видимое множество чатов: чат есть в `mcp_chats`, у него нет `ai_excluded`, и он не удалён.
- Множество считается в SQL **в том же операторе**, что и выборка: `json_each` по значению `app_setting`. У записи — внутри транзакции писателя.
- Любой `chat_id` или `id` вне множества — один и тот же `not_found` во всех инструментах, как для несуществующего. Это относится и к закрытому чату, и к `ai_excluded`, и к удалённому.
- Id в `mcp_chats`, которых нет в базе (например, после восстановления из копии), молча игнорируются.

**Не писать содержимое в логи.** Ни мост, ни приложение не пишут в stderr или лог кадры, аргументы и тексты. В логах только категории ошибок и `id` запроса. Приложение пишет через `log`: `eprintln!` в проекте заменяется, `print_stdout`/`print_stderr` = deny. В мосте — тоже `log`, либо одна функция вывода в stderr с осознанным `#[allow]` и комментарием.

**Отклонено.**
- *Свой писатель в `kinige-mcp` под блокировкой файла.* Второй процесс должен был бы повторить всё, что делает `Store::open`:
  - без этого Markdown-копия и лента главного окна не узнают о записи агента;
  - мост другой версии мог бы мигрировать базу;
  - соединение, открытое во время восстановления, писало бы в переименованный файл, и запись терялась бы молча;
  - правила доступа существовали бы в двух копиях.
- *Чтение напрямую из файла, запись через приложение.* Журнал обращений пишется и при чтении (§12.3). Получились бы два пути с разными отказами, а читатель зависел бы от версии схемы.

**Крейт MCP — `rmcp` 3.5.1** (2026-10-05, Apache-2.0). Это официальный Rust SDK, `github.com/modelcontextprotocol/rust-sdk`; факты сверил guardian.
- Последний релиз — 3.8.0 от 2026-10-26. Он младше двух недель, поэтому не берётся (правило ADR-0007).
- Фичи по умолчанию: `default = ["base64", "macros", "server"]`. HTTP-транспорты — отдельные фичи, они выключены.
- `IntoTransport` реализован для любого `AsyncRead + AsyncWrite`, в том числе для `tokio::net::UnixStream`.
- В схеме MCP 2025-06-18 есть `instructions` и `readOnlyHint`.
- Ставится только в `src-tauri`. Мост — только std.
- `tokio` уже в дереве (1.54). `tokio::net::UnixListener` использует `tauri-plugin-single-instance` 2.5.4 — проверено по исходникам.
- Сборку на нашем toolchain проверяет задача 4a.0. Если не соберётся — свой минимальный сервер на `serde_json`: `initialize`, `ping`, `tools/list`, `tools/call`, `notifications/initialized`.

**Настройки и журнал обращений — локальные, не синхронизируются.**
- Настройки — ключи `app_setting`: `mcp_enabled`, `mcp_mode`, `mcp_chats` (JSON-массив id).
- Журнал — таблицы `mcp_log` и `mcp_log_message`, миграция 5.
- Почему локально:
  - агент работает на этом компьютере (§9.3 «локально»);
  - синхронизация настроек вынесена из ADR-0001 («Не решается»);
  - в outbox и конверты ни настройки, ни журнал не попадают;
  - id чатов стабильны, поэтому синхронизацию можно добавить позже без переделки.

Журнал хранит **факт обращения, а не содержимое**:
- `args_json` — только `chat_id`, даты, лимиты, флаги и `query`, обрезанный до 128 знаков. Поля `text` нет никогда.
- Id затронутых записей — в дочерней таблице `mcp_log_message(log_id, message_id)` с индексом по `message_id`. Удаление записи навсегда (`purge`) в той же транзакции удаляет её строки из `mcp_log_message`. Сам факт обращения остаётся.
- Хранение: 90 дней **и** не больше 20 000 строк — что наступит раньше.
- `client` — то, что клиент сообщил о себе: обрезается до 64 знаков, управляющие символы убираются. В окне это имя не выдаётся за проверенное.
- Транзакции:
  - изменение данных и строка журнала — одна транзакция;
  - чтение: сначала одна запись писателя со строкой журнала и исходом, данные агент получает только после её успешного commit.
- Не журналируются `ping`, `initialize` и `tools/list`. Подключение и отключение клиента — по одной строке.

**`origin = 'agent'`.**
- Это новое значение неизменяемого `core.origin`. Оно аддитивно, `sv` не повышается (ADR-0001, «origin»).
- Запись строится общей сборкой `groups` с другим происхождением, без `ext`.
- «Своя» запись агента — любая с `origin = 'agent'`, от любого клиента.
- Байты (`core`, `flags` при `task = true`) дописываются в приложение ADR-0001, §C.4.

**Пометка «текст уйдёт провайдеру модели».** Такого поля в MCP нет. Гарантия — предупреждение Kinige при включении (ТЗ §9.3). В протоколе есть только сведения, которые клиент может и не показать: `instructions`, описания инструментов, `readOnlyHint` у инструментов чтения. Показывают ли их клиенты — не проверено.

**Сборка.**
- `kinige-mcp` — член workspace `crates/kinige-mcp`.
- В бандл он попадает через `bundle.externalBin` (`binaries/kinige-mcp-<target-triple>`; шаблон имени проверен по `tauri-utils` 2.10.2).
- Ожидаемое место — `Kinige.app/Contents/MacOS/kinige-mcp`, не проверено.
- Ad-hoc-подпись вложенного бинарника проверяет `codesign --verify --deep` в `scripts/build-app.sh`.

## Последствия
- Агент работает, только пока Kinige запущен или его можно запустить. Зато записи агента сразу видны в ленте, а копия, обслуживание и восстановление остаются одним путём.
- `notifications/tools/list_changed` нет. После смены режима клиент показывает старый список инструментов до переподключения; окно доступа говорит об этом.
- Первая запись Markdown-копии при запуске в фоне может вызвать системный запрос доступа к папке «Документы» без открытого окна. Это известное поведение, не исправляется.
- Windows (слайс 10): Unix-сокета в std там нет, нужен именованный канал. На Linux — тот же сокет.
- Мост не знает версий MCP, их согласует сервер в приложении.
- Не проверено:
  - сборка `rmcp` 3.5.1 на нашем toolchain;
  - путь вложенного бинарника и подпись;
  - синтаксис `claude mcp add` и путь `~/Library/Application Support/Claude/claude_desktop_config.json` (по памяти);
  - есть ли у Claude Code флаг `--mcp-config`.
