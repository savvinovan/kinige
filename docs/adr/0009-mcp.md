# ADR-0009: MCP — сервер в процессе приложения, `kinige-mcp` — мост stdio ↔ сокет

Дата: 2026-10-28. Статус: **принято** (слайс 4a реализован, ждёт приёмки). Ревизия 4 — по доработке после ревью `sync-crypto-guardian` и `slice-reviewer` (паники, версия протокола, строка «переподключение», счётчик записей журнала, политика активации); ревизия 3 — по второму кругу ревью `sync-crypto-guardian` (точечно); ревизия 2 — по первому («доработать»).

Основа:
- ТЗ §3.2 («один писатель»), §4.1, §9.3, §10, §12.3;
- ADR-0001 (`origin`, §2, §4, «Не решается»), ADR-0006, ADR-0008;
- спецификация `docs/slices/4a-mcp.md`.

## Контекст
ТЗ §9.3 требует отдельный бинарник `kinige-mcp` с транспортом stdio. Его запускает MCP-клиент: Claude Desktop или Claude Code. Главный вопрос — как этот процесс и приложение делят базу. По правилу ТЗ §3.2 все записи идут через один поток, который владеет соединением.

`Store::open` делает больше, чем открывает файл:
- запускает миграции и снимает копию перед ними;
- создаёт `device_id`;
- перестраивает индекс поиска;
- поднимает поток Markdown-копии, обслуживание (корзина, `integrity_check`, копия дня) и хук повреждения.

Восстановление из копии переименовывает файл базы (`recovery.rs`).

## Решение
**Сервер MCP работает внутри приложения. `kinige-mcp` — мост:** строки JSON-RPC из stdin он пересылает в Unix-сокет приложения, ответы — обратно в stdout.
- Базу мост не открывает. Ни `kinige-store`, ни `kinige-domain` он не знает.
- Из каждого сообщения мост читает только `id` и `method`. Больше ему ничего не нужно, чтобы отвечать на обрыв и повторять рукопожатие.

**Мост и обрыв связи.**
- **Неотвеченные запросы.** Мост запоминает неотвеченные запросы клиента. Запрос — сообщение, у которого есть и `method`, и `id`. Сообщение с `id` без `method` — это ответ клиента на запрос сервера, а не запрос: в таблицу оно не попадает.
- **Обрыв.** При обрыве мост отвечает на каждый неотвеченный запрос ошибкой JSON-RPC «соединение с Kinige потеряно, проверьте журнал обращений». Запросы он **никогда не отправляет повторно**: `add_entry` в полёте мог уже записаться. Запрос сервера к клиенту, который пришёл до обрыва, теряется вместе с соединением.
- **Рукопожатие.** Мост сохраняет `initialize` и `notifications/initialized` клиента. После переподключения он повторяет оба, ответ на повторный `initialize` клиенту не пересылает. Прототип 4a.0 показал: `rmcp` 3.5.1 принимает вызовы и **без** `notifications/initialized`, но **не** принимает их без `initialize` (ошибка про недостающие поля `_meta`). Повтор `initialize` обязателен; повтор уведомления мост делает для соответствия спецификации MCP и независимости от поведения SDK.
- **До рукопожатия.** Если клиент ещё не прислал `initialize`, повторять нечего: первый же запрос идёт в новое соединение как есть.
- **Маркер переподключения.** Новое соединение после обрыва мост начинает строкой `{"jsonrpc":"2.0","method":"kinige/reconnect"}`, до повторного `initialize`. Сервер читает её до первого `\n` (она может прийти частями; читается не больше её длины, остальное отдаётся сервису как начало потока), в сервис она не попадает. Журнал пишет одну строку «переподключение» (`tool = 'reconnect'`) вместо второго «подключения»; перед ней закрывается прошлый открытый сеанс того же клиента строкой «отключение». Если рукопожатие в новом соединении не записало строку (клиент прислал вызов без `initialize`, мост повторил его вхолостую), строка пишется лениво при первом `tools/call`.
- **Версия протокола.** `rmcp` 3.5.1 понимает «встроенный жизненный цикл» (`_meta.protocolVersion = "2026-07-28"` в запросе вместо `initialize`), и тогда вызов проходит без рукопожатия и без строки «подключение». Сервер объявляет только версии до 2025-11-25 включительно (`supported_protocol_versions` → `ProtocolVersion::known_up_to(V_2025_11_25)`); запрос без `initialize` с такой отметкой получает ошибку, сеанс не начинается (тест).
- **Ошибки самого моста.** Строка клиента, не являющаяся объектом JSON, получает ответ −32700 с `id: null` и никуда не пересылается (приложение из-за мусора не запускается). Строка длиннее 4 МиБ получает ошибку с настоящим `id`, если он стоит в первых 64 КиБ, иначе с `null`.

**Приложение не запущено** (решение пользователя, 28.10.2026). Мост сам запускает Kinige в фоне:
1. Сначала проверяет, есть ли процесс приложения из своего бандла.
   - Процесс есть, а сокета нет — ждёт сокет те же 10 с: приложение может ещё стартовать. Не дождался — `journal_unavailable` (восстановление, сбой запуска). `open` не вызывается: запущенному приложению он пришёл бы как Reopen и показал бы главное окно.
2. Процесса нет — `open -g -a <свой бандл> --args --background`, ожидание сокета до 10 с.
3. Не дождался — на каждый запрос ошибка JSON-RPC с тем же `id` и текстом «Откройте Kinige».

**Без значка в Dock.** Запуск с `--background` ставит политику активации Accessory (`App::set_activation_policy` до `run`; проверено по `tauri-2.12.4/src/app.rs` и `tao-0.37.1`): ни окна, ни значка в Dock, только значок в menu bar. Любой показ главного окна (меню трея, Reopen, второй запуск без флага) сначала ставит политику Regular, значок появляется. Скрытие окна политику не трогает: значок остаётся, как у приложения, запущенного обычно.

**Сбои фоновых потоков не молчат.** Профиль release собирается без `panic = "abort"`. Слушатель сокета, чтение базы (`read_unnoted`), поток Markdown-копии и поток обслуживания ловят панику (`catch_unwind` или `JoinHandle`), пишут `log::error!`, ставят ошибку в состояние (окно «Доступ ИИ-агентов», «Настройки»), поток продолжает работу или слушатель перепривязывается. Первый неудачный `bind` тоже не конец: привязка повторяется раз в интервал проверки, ошибка снимается при успехе.

Главное окно в `tauri.conf.json` — `visible: false`. `setup` показывает его сам, если в аргументах нет `--background`. В Tauri 2.12.4 (версия в `Cargo.lock`) окна из конфига создаются до пользовательского `setup` — проверено по исходникам (`tauri-2.12.4/src/app.rs`, функция `setup`).

**Сокет.**
- **Путь** — `<каталог данных>/mcp/kinige.sock`.
- **Длинный путь.** Если путь длиннее 104 байт (`sun_path` на macOS; в single-instance 2.5.4 есть комментарий «socket path must be shorter than 100 chars»), берётся запасной путь `$TMPDIR/kinige-mcp/<короткий хэш каталога данных>.sock`. Для папки `kinige-mcp/` действуют те же проверки, что для `mcp/` (ниже). Путь попадает во фрагмент подключения. macOS может вычищать старые файлы в `$TMPDIR` (не проверено). Поэтому слушатель раз в 10 минут проверяет, что его файл сокета на месте, и при пропаже перепривязывается к тому же пути с теми же проверками.
- **Папка.** `mcp/` проверяется через `symlink_metadata`: это не симлинк, владелец — текущий пользователь, права 0700. Если это не так, MCP недоступен, ошибка видна в настройках.
- **Второй Kinige.** Перед удалением старого файла сокета приложение пробует к нему подключиться. Если ответил — это второй Kinige на тех же данных: свой сервер не поднимается, об этом сообщается в настройках. Если не ответил — файл удаляется, затем `bind` и `chmod 0600`.
- **Чужой пользователь.** У каждого входящего соединения проверяется `peer_cred()`: uid не свой — соединение закрывается.
- **Предел кадра.** Одна строка кадра — не больше 4 МиБ: на сервере `JsonRpcMessageCodec::new_with_max_length`, в мосте — тот же предел. Длиннее — ошибка, соединение закрывается.
- **Порядок запуска.** Слушатель стартует **последним** в `start_services`, после `app.manage(store)`. Сокет удаляется в `RunEvent::Exit`.
- **Сбой сокета журнал не останавливает.** Не удался `bind` — `start_services` всё равно завершается успешно: журнал работает, ошибка сокета видна в `get_agent_access`. Не удался `chmod` после `bind` — файл сокета удаляется, ошибка та же.
- **Хранилище в каждом вызове.** Каждый вызов заново берёт `app.try_state::<Store>()` и проверяет `Recovery::corruption_found()`. Клон `Store` в задачах сервера не хранится: восстановление из копии не должно застать живой дескриптор писателя.
- **Когда `journal_unavailable`.** Только в двух случаях:
  - журнал не открыт при старте (режим восстановления) — тогда слушателя нет, и этот ответ даёт мост;
  - `corruption_found()`.

Это не сетевой порт. Подключиться может только тот же пользователь, а он и так читает файл базы (§4.1).

**Что видно, пока доступ выключен.** Приложение слушает при любом положении переключателя. Клиент видит:
- имя и версию сервера;
- `instructions`;
- имена и описания инструментов.

Данных не видно: каждый вызов инструмента получает `mcp_disabled`.

**Кадрирование.** MCP 2025-06-18: одно сообщение JSON-RPC на строку, без переводов строки внутри. Тот же формат идёт по сокету, поэтому своего протокола IPC нет.

**Права проверяет Rust приложения в каждом вызове. Клиенту, мосту и `clientInfo.name` не доверяем.**
- Видимое множество чатов: чат есть в `mcp_chats`, у него нет `ai_excluded`, и он не удалён.
- **Предикат в каждом операторе.** Каждый оператор чтения агента сам несёт предикат видимого множества: `json_each` по значению `app_setting`. Список чатов для строки «Чаты» в поиске — отдельный оператор с тем же предикатом, а не фильтр в Rust, как сейчас в `search_query.rs`. Между операторами одного вызова множество может измениться — это допустимо, каждый оператор проверен. У записи проверка идёт внутри транзакции писателя.
- **Единый `not_found`.** Любой `chat_id` или `id` вне множества получает один и тот же `not_found` во всех инструментах, как несуществующий. Это относится к закрытому чату, к `ai_excluded`, к удалённому — и к Inbox по умолчанию, если он не отмечен.
- **Значение `mcp_chats`.** Ключа нет — множество пустое. JSON повреждён — ошибка без данных. Id, которых нет в базе (например, после восстановления из копии), молча игнорируются.

**Не писать содержимое в логи.** Ни мост, ни приложение не пишут в stderr или лог кадры, аргументы и тексты. В логах только категории ошибок и `id` запроса. Приложение следует общему правилу проекта: вывод через `log`, `print_stdout`/`print_stderr` = deny. Правило вводится отдельным PR. У моста зависимостей нет, поэтому у него одна функция вывода в stderr с осознанным `#[allow]` и комментарием.

**Отклонено.**
- *Свой писатель в `kinige-mcp` под блокировкой файла.* Второй процесс должен был бы повторить всё, что делает `Store::open`:
  - без этого Markdown-копия и лента главного окна не узнают о записи агента;
  - мост другой версии мог бы мигрировать базу;
  - соединение, открытое во время восстановления, писало бы в переименованный файл, и запись терялась бы молча;
  - правила доступа существовали бы в двух копиях.
- *Чтение напрямую из файла, запись через приложение.* Журнал обращений пишется и при чтении (§12.3). Получились бы два пути с разными отказами, а читатель зависел бы от версии схемы.

**Крейт MCP — `rmcp` 3.5.1** (2026-10-05, Apache-2.0). Это официальный Rust SDK, `github.com/modelcontextprotocol/rust-sdk`; факты сверил guardian.
- Последний релиз — 3.8.0 от 2026-10-26. Он младше двух недель, поэтому не берётся (правило ADR-0007).
- Фичи по умолчанию: `default = ["base64", "macros", "server"]`. Берутся `default-features = false, features = ["server"]`: макросы `#[tool]` не нужны (инструменты описаны вручную), HTTP-транспорты — отдельные фичи, они выключены. Версия закреплена `=3.5.1`.
- `IntoTransport` реализован для любого `AsyncRead + AsyncWrite`, в том числе для `tokio::net::UnixStream`.
- В схеме MCP 2025-06-18 есть `instructions` и `readOnlyHint`.
- Ставится только в `src-tauri`. Мост — только std.
- `tokio` уже в дереве (1.54). `tokio::net::UnixListener` использует `tauri-plugin-single-instance` 2.5.4 — проверено по исходникам.
- **Проверено в 4a.0 (28.10.2026), прототип вне репозитория:**
  - `rmcp` 3.5.1 с фичами по умолчанию собирается на toolchain 1.94.0 (холодная сборка 21 с в dev).
  - Сервер поверх `tokio::net::UnixStream` работает: `initialize` → `tools/list` → `tools/call`, `clientInfo` виден в `peer.peer_info()`, `readOnlyHint` уходит в `tools/list`.
  - **Предел кадра.** `AsyncRwTransport` (то, во что превращается `UnixStream`) предел `JsonRpcMessageCodec::new_with_max_length` **не использует**: он читает строку через `read_until` без границы. Поэтому предел 4 МиБ ставит обёртка над читающей половиной сокета, которая считает байты с последнего `\n` и отдаёт ошибку ввода-вывода; сервис при этом завершается, соединение закрывается.

**Настройки и журнал обращений — локальные, не синхронизируются.**
- Настройки — ключи `app_setting`: `mcp_enabled`, `mcp_mode`, `mcp_chats` (JSON-массив id).
- Журнал — таблицы `mcp_log` и `mcp_log_message`, миграция 5.
- Почему локально:
  - агент работает на этом компьютере (§9.3 «локально»);
  - синхронизация настроек вынесена из ADR-0001 («Не решается»);
  - в outbox и конверты ни настройки, ни журнал не попадают;
  - id чатов стабильны, поэтому синхронизацию можно добавить позже без переделки.

Журнал хранит **факт обращения, а не содержимое**:
- `args_json` — только `chat_id`, даты, лимиты, флаги и `query`, обрезанный до 128 знаков. Поля `text` нет никогда.
- Id затронутых записей — в дочерней таблице `mcp_log_message(log_id, message_id)` с индексом по `message_id`. Удаление записи навсегда (`purge`) в той же транзакции удаляет её строки из `mcp_log_message`. Сам факт обращения остаётся, и **число записей обращения тоже**: оно лежит в колонке `mcp_log.entry_count`, которую пишет та же транзакция, что и строку журнала, и `purge` её не трогает. Окно показывает число из неё; раскрытие показывает оставшиеся записи и строку «ещё N удалены навсегда» (N = `entry_count` минус число оставшихся). Иначе удаление записи переписывало бы историю: «поиск · 2 записи» стало бы «1 запись».
- Хранение: 90 дней **и** не больше 20 000 строк — что наступит раньше. Ротация в той же транзакции удаляет строки `mcp_log_message` удалённых строк журнала: сирот не остаётся.
- `client` — то, что клиент сообщил о себе: обрезается до 64 знаков, управляющие символы убираются. В окне это имя не выдаётся за проверенное.
- Транзакции:
  - изменение данных и строки журнала — одна транзакция;
  - чтение идёт по шагам:
    1. выборка на соединении чтения;
    2. одна транзакция писателя со строкой `mcp_log` и строками `mcp_log_message`;
    3. commit;
    4. ответ агенту.

    Сбой commit — агент получает ошибку, данных нет.
- **Что считается обращением** (§12.3: «каждое обращение пишется в журнал»): вызов инструмента (`tools/call`) и подключение. Подключение пишется одной строкой при `initialize` с очищенным `client`, отключение — одной строкой. `ping`, `tools/list` и повторный `initialize` от моста отдельных строк не дают.

**`origin = 'agent'`.**
- Это новое значение неизменяемого `core.origin`. Оно аддитивно, `sv` не повышается (ADR-0001, «origin»).
- Запись строится общей сборкой `groups` с другим происхождением, без `ext`.
- **Дописывание.** «Своя» запись агента — любая с `origin = 'agent'`, от любого клиента. Цель дописывания — последняя живая запись чата в порядке `(journal_date, created_at, id)`. Если у неё `origin ≠ 'agent'`, она не сегодняшняя или старше 10 минут — ответ `no_agent_entry`.
- **Ревизия.** Дописывание агента пишет ревизию `edit`, в отличие от ⌘Enter: запись мог поправить пользователь.
- **Приложение ADR-0001, §C.4.** Сюда дописываются байты `core` и `flags` при `task = true`, а также исключение из §A.0 — ревизия `edit` при дописывании агентом.

**Пометка «текст уйдёт провайдеру модели».** Такого поля в MCP нет. Гарантия — предупреждение Kinige при включении (ТЗ §9.3). В протоколе есть только сведения, которые клиент может и не показать: `instructions`, описания инструментов, `readOnlyHint` у инструментов чтения. Показывают ли их клиенты — не проверено.

**Сборка.**
- `kinige-mcp` — член workspace `crates/kinige-mcp`.
- В бандл он попадает через `bundle.externalBin` (`binaries/kinige-mcp-<target-triple>`; шаблон имени проверен по `tauri-utils` 2.10.2).
- Место в собранном `.app` — `Kinige.app/Contents/MacOS/kinige-mcp`: проверено сборкой в 4a.6 (в проекте бинарник моста называется `kinige-mcp-bridge` и переименовывается при упаковке, чтобы имя не столкнулось с cargo-бинарником).
- Ad-hoc-подпись вложенного бинарника проверяет `codesign --verify --deep` в `scripts/build-app.sh`; на собранном бандле проверка проходит.

## Последствия
- Агент работает, только пока Kinige запущен или его можно запустить. Зато записи агента сразу видны в ленте, а копия, обслуживание и восстановление остаются одним путём.
- `notifications/tools/list_changed` нет. После смены режима клиент показывает старый список инструментов до переподключения; окно доступа говорит об этом.
- Первая запись Markdown-копии при запуске в фоне может вызвать системный запрос доступа к папке «Документы» без открытого окна. Это известное поведение, не исправляется.
- Windows (слайс 10): Unix-сокета в std там нет, нужен именованный канал. На Linux — тот же сокет.
- Мост не знает версий MCP, их согласует сервер в приложении.
