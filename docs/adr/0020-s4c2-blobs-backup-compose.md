# ADR-0020: S4c-2 results, blobs, backup and restore, docker compose

Date: 2026-11-06. Status: **accepted** after the review of `sync-crypto-guardian` (three rounds) and `slice-reviewer` (KINIG-99; spec `docs/slices/S4c2-blobs-backup-compose.md`, code `server/` and `deploy/`, simulation in `spikes/S4a-sync`). **Trimmed under KINIG-102** to the decisions and the rules the reviews produced; the full text, with the review rounds that code comments cite as "round N", is at commit `684551a` (`git show 684551a:docs/adr/0020-s4c2-blobs-backup-compose.md`). Changes ADR-0001 (revision 11; each change is marked "S4c, 2026-11-06" there) and the PRD (v0.25: Q9 and Q14 closed, §10.3 reads "30 days"); no change to the app's schema, `kinige-store` or `kinige-crypto`.

## What was proven
- **Blobs** (§7, §A.2) by `(account_id, remote_blob_id)`: resumable upload by offset, publication that checks the length framing only, "already exists" as success, range download, delete, a quota and the 2 GiB cap judged before a byte is stored, every request authenticated first. The suites run on a disk store and on an S3-compatible one.
- **A blob is never lost while a backup refers to it, and a backup taken during writes restores.** A blob is immutable once published. Deleting only marks it; the object leaves the store after the backup retention plus one backup interval, so a restorable backup finds its objects. The cut time is read with the backup lock held exclusively and the snapshot opened before it is let go; a compaction, an account deletion and a credential change take the lock shared, first, and read the clock after (a stamp read before the commit is not a cut time). A stamp below the cut time then means "inside the snapshot", at or above means "not"; a tie counts as missed (`>=`).
- **Restore**, in place or into a clean installation, by one code path: what needs no database is judged first, blobs are copied, then **one transaction** loads the tables and appends a generation cut at the backup's time. The objects a failed restore put are removed. S4a runs property 8, the restore mixes and the directed scenarios against the real server, each restore a real dump into a clean database, with a client-side control that must fail.
- **The stack** (`deploy/`): a pinned non-root Dockerfile (SIGTERM exits 0), compose with Postgres 17, healthchecks and Caddy with TLS. CI's `compose` job registers, pushes, uploads, pulls through the proxy, backs up, restores into a second stack and compares cursor, envelopes and blob.

## The S3 test target
Checked from their own sources (06.11.2026). **MinIO** is archived and "NO LONGER MAINTAINED", source only: not a target. **Garage** (v2.5.0) needs a `garage.toml` that a GitHub `services:` container cannot mount, and passes the same suites. **SeaweedFS** (4.52, Apache-2.0) is configured by environment alone and passes them. **Choice: SeaweedFS**, pinned by digest. The store is `object_store` 0.14.2 (MIT OR Apache-2.0): `AmazonS3` with path-style addressing, `LocalFileSystem` with `fsync` for the disk. Its tree adds `reqwest`, `rustls` with `aws-lc-rs` and `webpki-root-certs`; `cargo deny` passes with `CDLA-Permissive-2.0` added.

## Decisions and rules
- **Placement by the fork.** A device keeps the lineage of its last `GenerationChanged` and sends it with each pull; the server uses the cut time of the **fork**, the first foreign entry after the first shared one. A lineage sharing nothing gets cut 0 (everything missed); one not ending with the cursor's generation is `400 lineage`; a push sends the three-part cursor header and no lineage; the lineage is capped at 64. The cut time of the device's own generation is the wrong key: after a restore from a backup of a branch it belongs to another history. The rule is conservative, not exact.
- **Sessions are not in a backup**: a restore would bring back a session that a logout, a password change or a recovery ended. Devices log in again; slice 11 handles `401` after a generation change.
- **Journals.** The deletion journal holds `generichash(account_id)` and the time; a deleted id is never registered again (`409 account_id_taken`), so one entry per account is enough. The credential journal is written in the transaction of every password change, recovery and new words, under the shared backup lock, its stamp raised above the account's newest entry (two changes in one millisecond are two entries). A restore reads both journals from the backup, the installation being replaced (before it is emptied) and the newest neighbouring backup (only if its files match its manifest), and applies entries at or after the cut time. The sweep removes retired credential entries after the retention plus one interval, **but the newest entry of each account stays**: it holds what the account row holds, and a stopped cron would otherwise bring back the old password. The newest backup is kept until the next one; a deleted account's blobs stay the retention plus one interval.
- **Stamps and ages.** `compacted_ms`, `deleted_ms`, `changed_ms` and the cut are the database's `clock_timestamp()`, floored at the newest lineage cut plus one (`lock::stamp`). Ages (the 180 days, the sweep, journal pruning) use the unfloored `lock::now`. A cut more than an hour ahead of the clock is logged as an error (kind only).
- **A purge reaches the blob through the open header** (`"blob"` of a `purged`, ADR-0001 §5.2), in the transaction that accepts it. `DELETE /v1/blobs/{id}` stays for re-upload after `missing`. Blobs published after a backup become deleted blobs after a restore and devices upload them again under new ids; a deleted id is never published again, because a content check is impossible on ciphertext. `publish` never deletes the object of an existing row.
- **Unfinished uploads are local files**, also with S3 (a part is at least 5 MiB, an upload resumes at any offset); publication copies the file to the store. Price: a second write; gain: nothing in a backup is half a file.
- **Damaged backup files.** A blob file is hashed before it is hard-linked from the earlier backup. The restore compares objects by hash and replaces a damaged one. A blob whose backup file is missing or damaged is marked deleted only if the store holds no object with the manifest's hash; the command logs the category (never an id) and exits non-zero.
- **The dump is text `COPY` per table**, not `pg_dump`: no client of the server's major version, no binary format. The manifest names the schema and another schema is refused; slice 11 handles N to N+1 with the migration list. A scan error after the commit is a warning.
- **A restore under a running server is refused** (`ServerRunning`): `serve` holds a session advisory lock and `restore` tries it with `pg_try_advisory_lock`. A session lock dies with its connection, so `serve` takes it again, and if a restore got it in the gap, `serve` exits with an error.
- **The restore's lock and its transaction share one connection** (KINIG-102). A loss before the `COMMIT` is "lost its lock": nothing is replaced and the copied objects are removed. A loss during the `COMMIT` is an unknown outcome: the copied objects are kept (a rerun finds them by hash, the sweep adopts the unreferenced). A lost connection is told by a probe statement, not `Client::is_closed`, which stayed false in 38 of 40 runs after the backend was terminated. The orphan scan after the commit runs on the same connection, so a loss there ends only the scan (`orphan_scan_failed`).
- **Quota** is reserved atomically under a row lock. No id reaches a log through an error.
- **Compose on a remote Docker daemon.** `file:` secrets and configs are bind mounts of daemon-side paths, and Compose writes a secret into the container before it starts, which a read-only root refuses. So the secret comes from `.env`, the Caddyfile is baked into the proxy image, and the server's root is writable (all capabilities dropped, `no-new-privileges`).
- **A random search cannot find the late hole**: once the purging device is back, its tombstone purges again and all converge; the hole is that device gone for good. Proof is the directed schedule and scenario with its control, on both servers.

## What is left
- **Slice 11:** the client side of all of it, the re-upload trigger (§7), real rate-limit numbers, session expiry, metrics, exposing the server to the internet (the rest of Q9). A `purged` never pushed leaves a blob only the account's deletion removes (a device cannot list its blobs).
- **Known limits:**
  - one server process (an upload's busy flag and the staging directory are local); a first backup of a large store copies every object;
  - after a restore from a backup cut in the future the stamps run ahead of real time until the clock catches up, and a drop stamped in the future counts as "after" every earlier cut, so older branches are told they missed it (the safe side);
  - the supervised server lock covers a restore that still holds the lock when the server reconnects; a connection lost for longer than a whole restore is a gap in which a restore can start (the server then stops);
  - **the copy residue (accepted):** until its first database statement after the blob copy, the restore puts objects into the store and removes them if it stops. It touches only keys whose object was absent or did not match the manifest's hash. It can un-repair a blob whose object was already missing or damaged, and delete the object of a blob published in that window under a key that is also in the backup, which needs a reused blob id or the same account id registered again on a clean installation;
  - a credential change that no source of a restore knew of is lost; a backup kept alone cannot know of deletions made after it;
  - the S3 paths are tested against SeaweedFS and Garage, not Amazon; no test of Caddy's certificate issuance.
- **Not verified:** Garage's licence from its own source; the throughput of a 2 GiB upload through the proxy; the Windows and macOS builds (the crate is Linux first); restore on a Postgres other than 17.
