# ADR-0020: S4c-2 results, blobs, backup and restore, docker compose

Date: 2026-11-06. Status: **proposed**, to become accepted after the review of `sync-crypto-guardian` and `slice-reviewer` (KINIG-99; spec `docs/slices/S4c2-blobs-backup-compose.md`, code `server/` and `deploy/`, the simulation in `spikes/S4a-sync`). Changes ADR-0001 (revision 11, each change marked "S4c, 2026-11-06") and the PRD (v0.25: Q9 and Q14 closed, §10.3 reads "30 days"); no change to the schema of the app, to `kinige-store` or to the formats of `kinige-crypto`.

## What was proven
The server keeps its promises about files and about restore, and one `docker compose up` runs it.
- **Blobs** (§7, §A.2) by `(account_id, remote_blob_id)`: resumable upload by offset, an unfinished upload overwritten, publication that checks the length framing and nothing else, "already exists" as success, download with a range, delete, a quota and the 2 GiB cap judged before a byte is stored, every request authenticated first. The same suites run on a disk store and on an S3-compatible store.
- **A blob is never lost while a backup refers to it, and a backup taken during writes restores.** The argument, which a test runs: (1) a blob is immutable after publication; (2) deleting only marks it, and the object leaves the store after the backup retention plus one backup interval, so every object that a row of any restorable backup refers to is still there when that backup copies it, and a blob published after the snapshot is not in it; (3) the cut time is read with the backup lock held exclusively and the snapshot opened before it is let go, and a compaction, an account deletion and a credential change take it shared and read the clock after, so a stamp below the cut time means "inside the snapshot" and a stamp at or above means "not" (`store/lock.rs`; the stamp is the database's `clock_timestamp()`, never below one more than the newest cut time of the lineage). `backup_restore::a_backup_taken_during_writes_restores_and_its_cut_time_separates_the_drops` runs writers (envelopes, blob publishes and deletes, purges, compactions with the clock jumping) against five backups, restores each into a clean installation and checks that the head, the log and the `op_id` index agree, that every drop is on the right side of the cut time and that every live blob downloads as uploaded; a second test pins the lock in both directions.
- **Restore** in place and into a clean installation by one code path (`kinige-server restore`): everything is checked against the manifest before anything changes, the load is one transaction, a fresh generation is appended with the backup's cut time, the objects the restore put are removed again if it fails. The S4a simulation now runs property 8, the restore mixes and the directed restore scenarios against the real server, **each restore a real dump loaded into a clean database**, with a client-side control that must fail.
- **The branch-cut rule of ADR-0017** (by the cut time of the **fork** of the device's lineage, round 1) is built in the real server and in the in-memory one, and the `review_round_3_*` scenarios went from "pins today's limitation" to "passes" (with a switch that restores the old placement, so that the scenario keeps showing what it fixed); a second directed schedule, a branch restored from a backup of a branch, runs on both servers with a switch for the first version of the rule.
- **Account deletion** with a journal of `generichash(account_id)` and the time, and a **credential journal** (password change, recovery, new words); a restore re-applies the entries at or after the cut time; a deleted account id is never registered again; "delete, restore an older backup, the account is gone" and "change the password, restore an older backup, the new password still works" are tests, and so are their limits.
- **The stack** (`deploy/`): a pinned multi-stage Dockerfile (non-root, SIGTERM exits 0), compose with Postgres 17, volumes, healthchecks and Caddy with TLS, `.env.example` with placeholders, a cron example. CI's `compose` job (`deploy/smoke.sh`) registers, pushes, uploads a blob and pulls through the proxy, takes a backup, restores it into a second fresh stack and checks the old cursor, the envelopes and the blob byte for byte. It also ran against a remote Docker daemon, which found two things (below).

## The S3 test target
MinIO, Garage and SeaweedFS were checked from their own sources (06.11.2026).
- **MinIO:** the README of `github.com/minio/minio` opens with "THIS REPOSITORY IS NO LONGER MAINTAINED", says the community edition is "distributed as source code only" (no pre-compiled binaries or images), points to the commercial AIStor, and the repository is archived on GitHub (25 Apr 2026). The PRD's claim holds, and more: not a target for a new test.
- **Garage** (`dxflrs/garage:v2.5.0`, 69 MB, 8 MiB of RAM at rest): `--single-node --default-bucket` with environment variables makes the key and the bucket, but it needs a `garage.toml`, and a GitHub `services:` container cannot mount a file from the repository. **It passes the same suites** (run here). Its licence could not be read from its own source from here (the git site refused the request): not verified.
- **SeaweedFS** (`chrislusf/seaweedfs:4.52`, Apache-2.0 by its LICENSE file, release 4.52 on its releases page, images pushed to Docker Hub on 2026-11-05): `weed mini` is the image's default command, one container configured by environment alone (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_BUCKET`), so a `services:` container works. 780 MB, about 200 MiB of RAM. **It passes the same suites.**
**Choice: SeaweedFS** as the CI target, pinned by digest, because it is the one that needs no file and no step after start, and is permissively licensed and maintained. Garage is the smaller alternative and the suites run against either (`KINIGE_TEST_S3_*`). Nothing in the server is specific to either: the store is `object_store`'s (0.14.2, MIT OR Apache-2.0, Apache Arrow project, 106 million downloads), `AmazonS3` with path-style addressing for any S3-compatible store and `LocalFileSystem` with `fsync` (a temporary file, synced, renamed, the directory synced) for the disk. Its tree brings `reqwest`, `rustls` with `aws-lc-rs` (C code built by the `cc` crate) and `webpki-root-certs`; `cargo deny` passes with one addition, `CDLA-Permissive-2.0` (the root list as data), and the spike's tree passes too.

## What was found
1. **A stamp read before the commit is not a cut time.** A compaction (or a deletion) that read 10:00:00, a backup that cut at 10:00:01 and opened its snapshot, and a commit after that: the stamp says "inside the backup" and it is not. The advisory lock above closes it; the clock is read after the lock in the server, and the compaction takes the clock and not a number for that reason.
2. **A tie must count as missed.** A drop stamped at the cut time may or may not be in the backup, so the rule is `>=` (a test in the simulation and one in the unit tests pin it), and the property tests compare with `<=` on the other side.
3. **Sessions must not be in a backup.** A restore would bring back a session that a logout, a password change or a recovery had ended, undoing a response to a theft. So every device logs in again after a restore: slice 11 must handle `401` after a generation change. (The first version let credentials revert to the backup's, so a password changed after it was the old one again; round 1 replaced that with the credential journal, below.)
4. **A purge reaches the blob through the open header, not a request.** `remote_blob_id` is in the encrypted `core`, but ADR-0001 §5.2 already puts `"blob"` in the open header of a `purged` attachment (the code had the field). The push marks the pusher's own account's blob in the transaction that accepts the `purged`. `DELETE /v1/blobs/{id}` stays for the re-upload after `missing`.
5. **A restore costs re-uploads.** The blobs published after the backup are not in the restored data; their objects become deleted blobs and the devices upload them again under new ids (a deleted id is never published again). Allowing a deleted id to come back needs a content check the server cannot make on ciphertext.
6. **Unfinished uploads are local files, also with S3.** An S3 multipart part is at least 5 MiB, an upload resumes at any offset, so the staging area is a directory (`blobs/staging`) and a publication copies the file to the store. The price is a second write of the bytes; the gain is that nothing in a backup is half a file.
7. **Verify, then copy, then load; clean up on failure.** A restore that copied the blobs first and failed in the database left objects in the store. The checks that need no database (hashes, the lineage and journal files) come first, and the objects a failed restore put are deleted again.
8. **A random search cannot find the round 3 hole, by the property's own design.** Once the purging device is back, its tombstone purges the record again and everyone converges; the hole is that device being gone for good. The proof is the directed schedule and the scenario with its control, which run on both servers.
9. **A remote Docker daemon exposed two compose traps.** `file:` secrets and configs are bind mounts of paths on the machine that runs the command (they do not exist on the daemon's), and Compose writes a secret into the container's file system before it starts, which a read-only root refuses. The server secret now comes from `.env` as an environment secret and the Caddyfile is baked into the proxy image; the server's root is not read-only (it drops all capabilities and `no-new-privileges`).
10. **The dump is text `COPY` per table, not `pg_dump`.** A restore then needs no client of the server's major version in the image and no binary format; the price is that the dump knows this schema and the manifest names it (a restore of another schema is refused).

## Review round 1 (guardian and slice-reviewer)
What the review found, and what changed (the tests are named in `server/README.md`):
1. **The cut time of the device's own generation is the wrong key (critical).** After a restore from a backup of a branch, it is a time on another branch's clock of events. The device now keeps the **lineage** of the last `GenerationChanged` and sends it with each pull; the server takes the cut time of the **fork** (the first generation the device has and the server does not). A push sends no lineage (three-part cursor header). The lineage is capped at 64. Real and in-memory servers, a directed schedule on both (`branch_of_a_branch_schedule`), a unit test with the numbers of the review (lineage `[1, 3]`, device cut 300, drop at 150, fork at 100: stale), and `branch_by_own_cut` as a negative control.
2. **A restore brought back old credentials (critical).** The new credential journal is written in the transaction of every password change, recovery and new words, under the shared backup lock; it is dumped and a restore re-applies the newest entry at or after the cut time, from the same three sources as the deletion journal. A password changed after a backup works after the restore.
3. **A deleted account id could be registered again (critical).** Registration refuses it (`409 account_id_taken`), so one journal entry per account is enough.
4. **An in-place restore left a damaged object of the right size.** It now compares by hash and replaces, not by size.
5. **A backup linked a damaged file.** A blob file is hashed before it is hard-linked from the earlier backup. A restore turns a blob whose file does not match into a deleted row, logs the category, and the command exits non-zero; the rest of the restore is not blocked.
6. **The stamps came from the application's clock.** They come from the database's `clock_timestamp()` read in the locked transaction, never below the newest cut time of the lineage plus one; the injectable clock of the tests feeds the same floor. A test with the clock behind the cut.
7. **A restore under a running server.** `serve` holds a session advisory lock for its life, and `restore` takes it with `pg_try_advisory_lock` and refuses (`ServerRunning`). `publish` never deletes the object of a row that exists.
8. **Documentation:** the newest backup is kept until the next one is made (§8.9, PRD §10.3, `deploy/backup.cron.example`); the blobs of a deleted account stay the retention plus one interval; the re-upload trigger for slice 11 (§7).
9. **Smaller:** the quota is reserved atomically under a row lock (a test that fails without it); an error after the commit of an orphan scan is a warning, not a failure of a finished restore; the journals of the neighbouring backup are read only if they verify against its manifest; the schema 2 to 3 step is a migration, and slice 11 handles an N to N+1 schema with the migration list (a restore of an older schema is refused today); no id reaches the log through `Missing` or `Hash`; the test files are split by topic.

## Review round 2 (guardian)
The three criticals of round 1 were verified closed; five findings and one small item remained, all fixed in the same PR.
1. **The fork of a trimmed lineage.** The fork is the first foreign entry **after the first shared one**; a lineage that shares nothing with the server's gets cut 0 (everything missed), because the cut time of its first entry belongs to a history the server has trimmed and the true fork is earlier. A non-empty lineage must end with the cursor's generation (`400 lineage`). The rule is described as conservative, not exact. A test with a first entry of non-zero cut that shares nothing (unit and over HTTP) and the trimmed-prefix case.
2. **Two changes, one key.** The credential entry's stamp is read after the account's row lock and raised above the account's newest entry; the insert replaces on a key conflict. A test with a clock that does not move: two reissues, a password change and a reissue; after a restore the latest password and words work and the superseded ones do not.
3. **Retired credentials.** The sweep removes entries older than retention plus one interval. **One deviation from the finding as written:** the newest entry of each account stays. It holds what the account's row holds, so it exposes nothing more, and it is what the newest backup needs when that backup is older than the window (rotation keeps the newest backup whatever its age); deleting it would bring back the old password in exactly the case of a stopped cron. Old wraps live for retention plus one interval, like a deleted blob's object. Tests: after the window the retired entry is gone and the newest stays; a restore inside the window applies its entries; a restore of a backup older than the window lands on the newest password.
4. **A damaged backup file in place.** The row is marked deleted only when the store holds no object with the manifest's hash either. Test: damaged and missing backup files, intact store objects, the blobs are still downloadable; a blob that exists nowhere is still marked.
5. **The floor and the ages.** `lock::stamp` (floored) is used only for `compacted_ms`, `deleted_ms` and `changed_ms`; `lock::now` (the database's clock, unfloored) is used for the 180-day plan, the sweep and the journal pruning. A restore logs an error (kind only) when the cut time is more than an hour ahead of the database's clock. Test: after a restore from a backup cut 1000 days ahead, a purge 11 days old is not dropped; at 182 days it is, and its drop is stamped above the cut.
6. **The server lock is supervised.** A session lock dies with its connection. `serve` now takes it again when the connection ends; if a restore got it in the gap, `serve` exits with an error and stops serving. If the database is unreachable the supervisor retries (nothing is served meanwhile). Tests: the backend holding the lock is terminated, the lock comes back on a new session and a restore is refused again; with a widened gap a restore takes the lock and the server is told to stop.

## What is left
- **Slice 11:** the client side of all of it. Real rate-limit numbers, session expiry, metrics, exposing the server to the internet (the rest of Q9). A `purged` that was never pushed leaves a blob only the account's deletion removes (no list endpoint was added; a device cannot enumerate its blobs).
- **Known limits:** one server process (the busy flag of an upload and the staging directory are local); a first backup of a large store copies every object (later ones link to the earlier backup's files); the stamps (`compacted_ms`, `deleted_ms`, `changed_ms`, the cut of a backup) are the database server's clock, floored at the newest cut of the lineage, so after a restore from a backup cut in the future they run ahead of real time until the clock catches up (ages do not: they use the unfloored clock; a restore logs an error for a cut more than an hour ahead). A consequence: a drop stamped in the future counts as "after" every backup cut before it, so devices on older branches are told they missed it, which is the safe side; the server lock is retaken by itself, but a connection lost for longer than a restore takes is a gap in which a restore can start (the server then stops); a credential change that no source of a restore knew of is lost; a backup kept alone cannot know about deletions made after it (the journal needs a later backup or the installation); the S3 paths are tested against SeaweedFS and Garage, not Amazon; no test of Caddy's certificate issuance.
- **Not verified:** Garage's licence from its own source; the throughput of a 2 GiB upload through the proxy; the Windows and macOS builds (the crate is Linux first); restore on a Postgres other than 17.
