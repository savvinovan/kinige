# ADR-0010: The settings window and the `settings.json` file — the file as input, `app_setting` as state

Date: 2026-10-30. Status: **proposed** (slice 4b; revision 2 — after the `sync-crypto-guardian` review of 30.10.2026, "accept with changes"; guardian will check the full PR again, the user accepts). PRD §2.1, §5.1, §9.3, §11.3, §12.3; ADR-0005, -0006, -0009; the spec `docs/slices/4b-settings.md`.

## Context
Settings live in the `app_setting` table and are changed only by the window. The user wants (KINIG-39) settings as a separate window with a tree of sections, and a file that can be edited in an editor or handed to an agent — "everything, including AI access". This is the first path by which the agent's access to the journal (ADR-0009) is turned on not by a click in the Kinige window but by a write to a file.

## Decision

**File.** `<data directory>/settings.json` (in tests `$KINIGE_DATA_DIR/settings.json`). Strict JSON (no comments and no trailing commas), UTF-8 without BOM, mode 0600, no more than 1 MiB. A top-level object; the keys:

| Key                    | Values                                                       | Default                       |
|------------------------|--------------------------------------------------------------|-------------------------------|
| `text_size`            | `"normal"` or `"large"`                                      | `"normal"`                    |
| `shortcuts.capture`    | a canonical shortcut (ADR-0006), `Ctrl+Alt+KeyN`             | `"Ctrl+Alt+KeyN"`             |
| `shortcuts.clipboard`  | the same                                                     | `"Alt+Shift+KeyV"`            |
| `mirror.folder`        | an absolute path to an existing folder                       | `null` (`~/Documents/Kinige`) |
| `agent_access.enabled` | `true` or `false`                                            | `false`                       |
| `agent_access.mode`    | `"read"` or `"read_write"`                                   | `"read"`                      |
| `agent_access.chats`   | an array of `{"id", "title"}`; without `id` — by exact title | `[]`                          |

The file contains chat titles (`agent_access.chats`), so it must not be shared blindly. The file does not get `sidebar_collapsed`, `recent_emoji`, the copy state and the language (from the system, ADR-0005): these are not settings but window or system state.

**"No key" and `null`.** No key — the value does not change. `null` — the default value. The app writes all keys with their effective values; the exception is that the default `mirror.folder` is written as `null`, so that a personal path does not get into a file that is shared.

**The file is input, `app_setting` is state.** The effective values still live in `app_setting`; the agent's chat visibility predicate (ADR-0009) stays SQL and does not read the file. Applying the file is one writer transaction (per key: valid keys are applied, invalid ones give an error for that key and change nothing), then the shortcuts are re-registered and a `settings-changed` event goes to the windows. Shortcuts are not part of the transaction: each goes through the same steps as a change in the window (check, registration in the system, saving; ADR-0006), and at startup, while there are no windows and no system shortcuts yet, — check and save, and `register_saved` registers. A shortcut the system did not accept is an error for that key, and the previous one keeps working; the file is not rewritten right away, so as not to erase the user's edit, — the error is visible until the next edit from the window or a re-read of the file under the "hash matched" rule (below), which will rewrite the file from the database.

**One thread.** Everything that concerns the file is done by one thread: reading, parsing, applying, writing. An edit from the window runs in the same thread, as a job: (1) re-read the file and apply an external edit if the file has changed; (2) perform the window's edit (the same `Store` methods as before); (3) write the file. The last edit wins; the "window ↔ file" race reduces to the order in the thread's queue.
- **Watching — polling once per 1 s**, without `notify` (a new dependency, platform differences and the semantics of editors that save via `rename`). The change signature: `mtime`, size, mode, inode, "is a symlink" and, for a symlink, the target's `mtime` and size (an edit of the target is visible to polling). The signature is taken before `open` and after reading; if they do not match, the file changed during the read, the signature is empty, and the next poll reads it again. If the signature changed, the file is read and parsed. A broken, unsafe or unreadable file is re-read only when it has changed, not on every poll. **The "unsafe" check and showing it run on every read, regardless of the hash.**
- **Writing** — to a temporary file in the same directory (`.settings.json.<random>.tmp`, `O_EXCL`, 0600), `fsync`, `rename`, `fsync` of the directory. A reader sees the file either entirely old or entirely new. Abandoned temporary files are removed at startup.
- **Reading.** The file is opened once (`O_NOFOLLOW | O_NONBLOCK`), and all checks go through the descriptor. Not a regular file (FIFO, device) — `unsafe` without reading the content; a symlink is read through to its target (`O_NOFOLLOW` gives `ELOOP`, the second open goes without it), but is considered unsafe as a whole; a size by `fstat` greater than 1 MiB — an error without reading; it is read via `take(1 MiB + 1)` so that a file that grew between the check and the read is rejected too.
- **What is written.** All known keys with effective values; the chat titles in `agent_access.chats` are the current ones. Unknown keys and values of other blocks are preserved as is (the key order is ours and is not preserved).
- **The last-sync hash and the rule "hash matched — the database wins".** `settings_file_hash` lives in `app_setting` (it does not go into the file) and is computed **from the written bytes**, not from the re-read file: an edit made between the app's `rename` and the hash step gives a different hash and is applied. The rule applies **on every read**, not only at startup:
  - the file's hash does not match the saved one — this is an external edit, and the file is applied;
  - the hash matched — there is no external edit, and the database wins; if the file is safe and parses but differs from what the app would write from the database (or the "write postponed" flag is set after an unsafe state or a failed write), the file is rewritten from the database.

  This closes two ways of losing a window edit: `kill -9` between the commit of the edit and the file write (at startup the file matches the saved hash, and the database is newer), and the sequence "the file is unsafe, access is turned off in the window (the file is not rewritten), the permissions are fixed, an agent edits only `text_size`": the file with the stale `enabled: true` is not applied as a whole but is rewritten from the database. The hash is written in one transaction with applying an external edit, and as a separate short step after a file write; a crash between them is harmless (the file matches the database, re-applying changes nothing and writes nothing to the log).
- **One transaction.** For a change of `agent_access.*` from the file, one writer transaction holds: the "before/after" comparison, the write of the keys `mcp_enabled`, `mcp_mode`, `mcp_chats`, `settings_file_hash` and the `mcp_log` row (`insert_log` takes a transaction). The log rows are labeled by `tool = 'settings_file'`, not by `client`: an MCP client names itself whatever it wants, including `settings.json`.
- **Order.** At startup the file is applied before `register_saved` and before the MCP listener. No file — it is created from the current state (also on the first launch of this version); deleting the file does not reset the settings. After `restore_backup` the file is applied unconditionally on top of the restored database (the hash from the backup is not compared), and **before applying, `mcp_enabled = 0` and `mcp_chats = []` are reset in the same transaction** (the mode stays from the backup): the result is access exactly as in the file, and if the file is unsafe or does not parse — off, not as in the backup.
- **`restore_backup` and `mirror.folder`.** Applying the file sets the copy folder via `set_mirror_dir` and marks all days for rewriting; the copy writer deletes from the folder the day files that are not in the database. If a backup with folder `/A` were restored while the file has `/B`, the days that appeared after the snapshot would vanish from `/B`. So before moving the database, `restore_backup` reads `mirror.folder` from `settings.json` (read only, the same safety checks and the same value rules) and, if that folder exists and differs from the folder in the backup, moves it to `…-before-restore-…` the same way as the folder from the backup. If the file is unsafe or the value is invalid, the folder from the file is neither taken nor applied.
- **The file cannot be parsed or is unsafe** — the app does not overwrite it, the window's changes go only into the database, the error is visible (the "Settings file" section and a mark on the tree item), there are no toasts. A file write failure (disk, directory permissions) — the same: the database is correct, the error is visible, and the write is retried with a pause of 2, 4, … 60 seconds, not on every poll. A warning is written to the process log once per change of the kind and category of the error (without paths and data), so a persistent error does not flood the log.

**Parsing and errors (no panics).**
- Outside parsing: larger than 1 MiB, not UTF-8, BOM, not JSON, not an object, deeper than the `serde_json` limit (128) — a file error "line N, column M" (where available), and no setting changes. A duplicate key — the last one wins (as in `serde_json`).
- An unknown key — a warning; the key stays in the file. A wrong type or a disallowed value — an error for that key, the previous value stays; the others are applied.
- `mirror.folder`: not absolute, does not exist, not a folder, or inside the data directory — refused.
- `agent_access.chats`: an element with `id` — by `id` (the title is for reference); an `id` that does not exist is an error for the element, **without falling back to the title**, even if the title exists. Without `id` — by title after `normalize_title`, among chats with `deleted_at IS NULL` (archived ones take part). In the database Inbox has `title = ""` (`groups.rs`): Inbox is matched by id and by the title `Inbox` in any language, and the app writes `"title": "Inbox"`; a user chat titled "Inbox" makes it ambiguous — an error for the element. A chat not found, deleted, an ambiguous title, or an `ai_excluded` chat — an error for that element, which is not included; the other elements are applied. Errors only narrow access, they never widen it.
- File errors are a structured `enum` with `category()` (`parse`, `type`, `value`, `unsafe`, `io`) and a position (`line`, `column`). The text of a `serde` error may contain values from the file, so its `Display` goes neither into `log::*` nor into IPC. The log gets event kinds and categories, never paths, chat titles or file contents. `src-tauri/tests/log_privacy.rs` is extended with markers in an unknown key, a chat title, a disallowed value and the `mirror.folder` path.
- A duplicate key: the file is parsed into `serde_json::Value`, and the last one wins; this is the chosen implementation, and there is a test for it (parsing via `derive` would give a `duplicate field` error).

**Accepted risk: a write to the file = agent access to the journal.** Any process of the user with write permission on the data directory can turn on `agent_access` and thereby give MCP clients read (and write) access to the journal. The decision does not undo this: such a process can read the database itself and the Markdown copy without the file (PRD §4.1), and MCP gives agents only what they could do anyway; the goal was to give the user and the user's agent one way to configure everything. Mitigations:
- **An unsafe file.** The file is opened with `O_NOFOLLOW`, the checks go through the descriptor (`fstat`), without a race between the check and the read. Not a regular file (a symlink), the owner is not the current user, the mode allows writing by the group or by everyone (`mode & 0o022`), or the data directory is writable by the group or by everyone (checks only under `#[cfg(unix)]`) — the keys `agent_access.*` and `mirror.folder` are not applied, and the error is visible; the other keys are applied. A permission change via `chmod` changes the polling signature — a re-read within a second, but content seen with unsafe permissions does not become trusted (the hash matches, the database wins): after `chmod 600` the file must be **saved again**, and then it is applied as a whole. The window's hint says so as well.
- **The log.** Every change of `agent_access.*` that came from the file (by comparing the effective state before and after, in the same transaction as the write of the keys) is an `mcp_log` row: `client = "settings.json"`, `tool = 'settings_file'`, `args_json` — the flag, the mode and the number of chats, without titles, `outcome = 'ok'`. No migration: `tool` is a text column without an enumeration; the window shows "settings.json · access changed" by `tool`, not by the client name. Changes from the window do not need the log: the user makes them.
- **Visibility.** Next to a section changed by the file — "Changed via settings.json · time" (in memory; for `mirror.folder` too). The model provider warning when access is turned on from the window stays; when it is turned on by the file there is nobody to show it to — hence both the log row and the mark.
- `mirror.folder` from the file is a risk too (the plain text of the copy in an arbitrary folder): so it is under the same checks.

**Locality.** The file and `settings_file_hash` are not synchronized, do not go into envelopes or the outbox, and are not written to the Markdown copy. Syncing settings between devices is still out of ADR-0001's scope ("Not settled"); the stable chat ids in `agent_access.chats` keep it possible.

**The data directory** is created with mode 0700 (like `mcp/`); an existing one is not touched. Otherwise with umask 002 (Linux) the directory would be writable by the group, and the access keys from the file would never be applied.

**Window.** A separate Tauri window `settings`, created on first opening (`index.html#settings`); closing destroys it. The file thread itself waits for the main thread (registering shortcuts in `tauri-plugin-global-shortcut` 2.4.1 goes through `run_main_thread!` and blocks until it finishes), but there is no deadlock: all commands that call `edit` (and wait for the file thread) are `async` and run in the thread pool, while the main-thread commands (`open_settings`, `shortcut_recording`, `get_settings_file`) do not wait for the file thread; events to the windows are sent from the thread without waiting; ⌘, and "Settings…" in the icon menu. It has its own capability: `get_language`, `get_settings`, `set_text_size`, `choose_mirror_folder`, `set_shortcut`, `reset_shortcut`, `shortcut_recording`, the six access commands of 4a, the new `get_settings_file` and `settings_open_entry`, `core:event:allow-listen` / `allow-unlisten`. There is no reading of the feed, search, writing or import. Through `list_agent_log_entries` the window sees the texts of the entries the agent touched (deliberately, like the "Access log" section in 4a; PRD §12.3). `main` loses the moved commands (it keeps `get_settings`, the `settings-changed` event and the new command `open_settings` for the profile's "Settings" item; it listens to the `open-message` and `settings-changed` events); the capture window still has exactly seven. Negative tests — `src-tauri/tests/ipc.rs`.

## Rejected
- **JSONC.** The app rewrites the file; the user's comments would vanish on the first edit from the window. Editing while preserving the formatting is separate work that is not needed now.
- **Dropping `app_setting`** (the file as the only store). The chat visibility predicate (ADR-0009) must stay SQL in one transaction with the journal read; a broken or unavailable file must not change permissions.
- **An MCP tool for settings.** The agent would change its own permissions over the protocol that Rust checks precisely against it. The file system is a path the agent either has or does not have.
- **`notify`.** See above.

## Consequences
- There are no new crates in the tree: `kinige-store` takes as direct dependencies `sha2` 0.10 (the file hash) and `libc` 0.2 (`geteuid`, `O_NOFOLLOW`), both already in `Cargo.lock` transitively. If the user objects to direct dependencies, the fallback is to compare with the saved content instead of a hash, and to check the file owner against the owner of the data directory.
- **The "window ↔ agent" race.** If an external process replaced the file (`rename`) between the re-read in the thread and the app's `rename`, its edit is lost. Accepted: the window re-reads the file before its edit, the interval is milliseconds, the last write wins.
- **The "commit → shortcut" window.** The file is applied in a transaction, and the system accepts the shortcuts only after it. A process death between them loses only the shortcut edit from the file: the hash is already written, so at the next launch the file is considered synchronized, and the database keeps the previous shortcut (at launch the file is rewritten from the database). Accepted: a shortcut edit is rare and visible to the user.
- A copy folder change that arrived during a pass of the copy writer is not lost: the pass starts over with the new folder (`mirror.rs`), and all days are marked again.
- Changes beyond 1–2 s are applied with the polling delay; an edit and a revert within the same second with the same size and `mtime` are theoretically invisible. Accepted.
- For `sync-crypto-guardian`: the order of applying at startup and after a restore, the unsafe-file checks, the `mcp_log` row with a new `tool` value (without a migration), the IPC matrix of the new window. The SQLite schema, the sync protocol and the encryption do not change.
