# ADR-0010: Окно настроек и файл `settings.json` — файл как вход, `app_setting` как состояние

Дата: 2026-10-30. Статус: **предложено** (слайс 4b; ревизия 2 — по ревью `sync-crypto-guardian` 30.10.2026 «принять с правками»; полный PR guardian проверит повторно, принимает пользователь). ТЗ §2.1, §5.1, §9.3, §11.3, §12.3; ADR-0005, -0006, -0009; спецификация `docs/slices/4b-settings.md`.

## Контекст
Настройки живут в таблице `app_setting` и меняются только окном. Пользователь хочет (KINIG-39) окно настроек как отдельное окно с деревом разделов и файл, который можно править в редакторе или поручить агенту — «всё, включая доступ ИИ». Это первый путь, по которому доступ агента к журналу (ADR-0009) включается не кликом в окне Kinige, а записью в файл.

## Решение

**Файл.** `<каталог данных>/settings.json` (в тестах `$KINIGE_DATA_DIR/settings.json`). Строгий JSON (без комментариев и хвостовых запятых), UTF-8 без BOM, права 0600, не больше 1 МиБ. Объект верхнего уровня; ключи:

| Ключ                   | Значения                                                 | По умолчанию                  |
|------------------------|----------------------------------------------------------|-------------------------------|
| `text_size`            | `"normal"` или `"large"`                                 | `"normal"`                    |
| `shortcuts.capture`    | каноничное сочетание (ADR-0006), `Ctrl+Alt+KeyN`         | `"Ctrl+Alt+KeyN"`             |
| `shortcuts.clipboard`  | то же                                                    | `"Alt+Shift+KeyV"`            |
| `mirror.folder`        | абсолютный путь к существующей папке                     | `null` (`~/Documents/Kinige`) |
| `agent_access.enabled` | `true` или `false`                                       | `false`                       |
| `agent_access.mode`    | `"read"` или `"read_write"`                              | `"read"`                      |
| `agent_access.chats`   | массив `{"id", "title"}`; без `id` — по точному названию | `[]`                          |

Файл содержит названия чатов (`agent_access.chats`), поэтому им нельзя делиться вслепую. В файл не идут `sidebar_collapsed`, `recent_emoji`, состояние копии и язык (по системе, ADR-0005): это не настройки, а состояние окна или системы.

**«Нет ключа» и `null`.** Ключа нет — значение не меняется. `null` — значение по умолчанию. Приложение пишет все ключи с действующими значениями; исключение — `mirror.folder` по умолчанию записывается как `null`, чтобы личный путь не попадал в файл, которым делятся.

**Файл — вход, `app_setting` — состояние.** Действующие значения по-прежнему лежат в `app_setting`; предикат видимости чатов агенту (ADR-0009) остаётся SQL и файл не читает. Применение файла — одна транзакция писателя (по ключам: годные ключи применяются, негодные дают ошибку этого ключа и не меняют ничего), затем перерегистрация сочетаний и событие `settings-changed` окнам. Сочетания в транзакцию не входят: каждое проходит те же шаги, что смена в окне (проверка, регистрация в системе, сохранение; ADR-0006), а при запуске, пока окон и системных сочетаний ещё нет, — проверка и сохранение, регистрирует `register_saved`. Сочетание, которое система не приняла, — ошибка ключа, прежнее продолжает работать; файл при этом сразу не переписывается, чтобы не стирать правку пользователя, — ошибка видна до следующей правки из окна или перечитывания файла по правилу «хэш совпал» (ниже), которые перепишут файл из базы.

**Один поток.** Всё, что касается файла, делает один поток: чтение, разбор, применение, запись. Правка из окна выполняется в нём же, как задание: (1) перечитать файл и применить внешнюю правку, если файл изменился; (2) выполнить правку окна (те же методы `Store`, что и раньше); (3) записать файл. Побеждает последняя правка; гонка «окно ↔ файл» сводится к порядку в очереди потока.
- **Наблюдение — опрос раз в 1 с**, без `notify` (новая зависимость, различия платформ и семантика редакторов, сохраняющих через `rename`). Признак изменения: `mtime`, размер, режим, inode, «это симлинк» и у симлинка — `mtime` и размер цели (правка цели видна опросу). Признак снимается до `open` и после чтения; не совпали — файл менялся во время чтения, признак пустой, и следующий опрос прочитает его заново. Изменился признак — файл читается и разбирается. Битый, небезопасный или нечитаемый файл перечитывается только когда он изменился, а не на каждом опросе. **Проверка «небезопасен» и её показ идут при каждом чтении, независимо от хэша.**
- **Запись** — во временный файл в том же каталоге (`.settings.json.<случайное>.tmp`, `O_EXCL`, 0600), `fsync`, `rename`, `fsync` каталога. Читатель видит файл целиком старым или целиком новым. Брошенные временные файлы убираются при старте.
- **Чтение.** Файл открывается один раз (`O_NOFOLLOW | O_NONBLOCK`), все проверки идут по дескриптору. Не обычный файл (FIFO, устройство) — `unsafe` без чтения содержимого; симлинк читается по цели (`O_NOFOLLOW` даёт `ELOOP`, второе открытие идёт без него), но целиком считается небезопасным; размер по `fstat` больше 1 МиБ — ошибка без чтения; читается через `take(1 МиБ + 1)`, чтобы файл, выросший между проверкой и чтением, тоже был отвергнут.
- **Что пишется.** Все известные ключи с действующими значениями, названия чатов в `agent_access.chats` — текущие. Неизвестные ключи и значения чужих блоков сохраняются как есть (порядок ключей — наш, не сохраняется).
- **Хэш последней синхронизации и правило «хэш совпал — побеждает база».** `settings_file_hash` лежит в `app_setting` (в файл не идёт) и считается **от записанных байтов**, а не от перечитанного файла: правка, сделанная между `rename` приложения и шагом хэша, даёт другой хэш и применяется. Правило действует **при каждом чтении**, а не только при старте:
  - хэш файла не совпал с сохранённым — это внешняя правка, файл применяется;
  - хэш совпал — внешней правки нет, база выигрывает; если файл безопасен и разбирается, но отличается от того, что приложение записало бы из базы (или стоит флаг «запись отложена» после небезопасного или не записавшегося состояния), файл переписывается из базы.

  Так закрыты два пути потери правки окна: `kill -9` между коммитом правки и записью файла (при старте файл совпадает с сохранённым хэшем, база новее) и последовательность «файл небезопасен, в окне выключили доступ (файл не переписан), права исправлены, агент правит только `text_size`»: файл с устаревшим `enabled: true` не применяется целиком, а переписывается из базы. Хэш пишется в одной транзакции с применением внешней правки и отдельным коротким шагом после записи файла; обрыв между ними безвреден (файл совпадает с базой, повторное применение ничего не меняет и в журнал не пишет).
- **Одна транзакция.** Для изменения `agent_access.*` из файла в одной транзакции писателя лежат: сравнение «до/после», запись ключей `mcp_enabled`, `mcp_mode`, `mcp_chats`, `settings_file_hash` и строка `mcp_log` (`insert_log` принимает транзакцию). Строки журнала подписываются по `tool = 'settings_file'`, а не по `client`: клиент MCP сам называет себя как хочет, в том числе `settings.json`.
- **Порядок.** При старте файл применяется до `register_saved` и до слушателя MCP. Файла нет — он создаётся из текущего состояния (первый запуск этой версии тоже); удаление файла настройки не сбрасывает. После `restore_backup` файл применяется безусловно поверх восстановленной базы (хэш из копии не сравнивается), а **перед применением в той же транзакции сбрасываются `mcp_enabled = 0` и `mcp_chats = []`** (режим остаётся из копии): итог — доступ ровно как в файле, а если файл небезопасен или не разбирается — выключен, а не как в копии.
- **`restore_backup` и `mirror.folder`.** Применение файла ставит папку копии через `set_mirror_dir` и помечает все дни для перезаписи; писатель копии удаляет в папке файлы дней, которых нет в базе. Если восстановить копию с папкой `/A` при файле с `/B`, в `/B` пропали бы дни, появившиеся после снимка. Поэтому `restore_backup` до переноса базы читает `mirror.folder` из `settings.json` (только чтение, те же проверки безопасности и те же правила значения) и, если эта папка существует и отличается от папки из копии, уводит её в `…-before-restore-…` так же, как папку из копии. Если файл небезопасен или значение негодно, папка из файла не берётся и не применяется.
- **Файл нельзя разобрать или он небезопасен** — приложение его не перезаписывает, изменения окна идут только в базу, ошибка видна (раздел «Файл настроек» и метка у пункта дерева), тостов нет. Сбой записи файла (диск, права каталога) — то же: база верна, ошибка видна, запись повторяется с паузой 2, 4, … 60 секунд, а не на каждом опросе. В журнал процесса предупреждение пишется один раз на смену вида и категории ошибки (без путей и данных), поэтому постоянная ошибка не засоряет журнал.

**Разбор и ошибки (без паник).**
- Вне разбора: больше 1 МиБ, не UTF-8, BOM, не JSON, не объект, глубже предела `serde_json` (128) — ошибка файла «строка N, столбец M» (где есть), ни одна настройка не меняется. Дубликат ключа — побеждает последний (как в `serde_json`).
- Неизвестный ключ — предупреждение, ключ остаётся в файле. Неверный тип или недопустимое значение — ошибка этого ключа, остаётся прежнее; остальные применяются.
- `mirror.folder`: не абсолютный, не существует, не папка или внутри каталога данных — отказ.
- `agent_access.chats`: элемент с `id` — по `id` (название справочное); `id`, которого нет, — ошибка элемента, **без отката на название**, даже если название существует. Без `id` — по названию после `normalize_title`, среди чатов с `deleted_at IS NULL` (архивные участвуют). В базе у Inbox `title = ""` (`groups.rs`): Inbox сопоставляется по id и по названию `Inbox` при любом языке, приложение пишет `"title": "Inbox"`; пользовательский чат с названием «Inbox» даёт неоднозначность — ошибка элемента. Чат не найден, удалён, название неоднозначно или чат `ai_excluded` — ошибка этого элемента, он не включается; остальные элементы применяются. Ошибки только сужают доступ, не расширяют.
- Ошибки файла — структурированный `enum` с `category()` (`parse`, `type`, `value`, `unsafe`, `io`) и позицией (`line`, `column`). Текст ошибки `serde` может содержать значения из файла, поэтому его `Display` не попадает ни в `log::*`, ни в IPC. В лог идут виды событий и категории, никогда пути, названия чатов и содержимое файла. `src-tauri/tests/log_privacy.rs` расширен маркерами в неизвестном ключе, названии чата, недопустимом значении и пути `mirror.folder`.
- Дубликат ключа: файл разбирается в `serde_json::Value`, побеждает последний; это выбранная реализация, на неё есть тест (разбор через `derive` дал бы ошибку `duplicate field`).

**Принятый риск: запись в файл = доступ агента к журналу.** Любой процесс пользователя с правом записи в каталог данных может включить `agent_access` и тем самым дать MCP-клиентам чтение (и запись) журнала. Решение это не отменяет: такой процесс и без файла читает саму базу и Markdown-копию (ТЗ §4.1), а MCP добавляет агентам только то, что они и так могли; целью было дать пользователю и его агенту один способ настраивать всё. Смягчения:
- **Небезопасный файл.** Файл открывается с `O_NOFOLLOW`, проверки идут по дескриптору (`fstat`), без гонки между проверкой и чтением. Не обычный файл (симлинк), владелец не текущий пользователь, режим допускает запись группе или всем (`mode & 0o022`), либо каталог данных доступен на запись группе или всем (проверки только под `#[cfg(unix)]`) — ключи `agent_access.*` и `mirror.folder` не применяются, ошибка видна; остальные ключи применяются. Права по `chmod` меняют признак опроса — перечитывание за секунду, но содержимое, увиденное при небезопасных правах, не становится доверенным (хэш совпадает, база выигрывает): после `chmod 600` файл нужно **сохранить ещё раз**, тогда он применится целиком. Так сказано и в подсказке окна.
- **Журнал.** Каждое изменение `agent_access.*`, пришедшее из файла (по сравнению действующего состояния до и после, в той же транзакции, что запись ключей), — строка `mcp_log`: `client = "settings.json"`, `tool = 'settings_file'`, `args_json` — флаг, режим и число чатов, без названий, `outcome = 'ok'`. Миграции нет: `tool` — текстовая колонка без перечисления; окно показывает «settings.json · доступ изменён» по `tool`, а не по имени клиента. Изменения из окна журнала не требуют: их делает сам пользователь.
- **Видимость.** Рядом с разделом, изменённым файлом, — «Изменено через settings.json · время» (в памяти; у `mirror.folder` тоже). Предупреждение о провайдере модели при включении из окна остаётся; при включении файлом его показать некому — поэтому и строка журнала, и пометка.
- `mirror.folder` из файла — тоже риск (открытый текст копии в произвольной папке): поэтому он под теми же проверками.

**Локальность.** Файл и `settings_file_hash` не синхронизируются, в конверты и outbox не попадают, в Markdown-копию не пишутся. Синхронизация настроек между устройствами по-прежнему вынесена из ADR-0001 («Не решается»); стабильные id чатов в `agent_access.chats` оставляют её возможной.

**Каталог данных** создаётся с режимом 0700 (как `mcp/`); существующий не трогается. Иначе при umask 002 (Linux) каталог оказался бы доступен на запись группе, и ключи доступа из файла не применялись бы никогда.

**Окно.** Отдельное окно Tauri `settings`, создаётся при первом открытии (`index.html#settings`), закрытие уничтожает; поток файла сам ждёт главный поток (регистрация сочетаний в `tauri-plugin-global-shortcut` 2.4.1 идёт через `run_main_thread!` и блокируется до конца), но взаимной блокировки нет: все команды, вызывающие `edit` (ждущие поток файла), — `async` и идут в пуле потоков, а команды главного потока (`open_settings`, `shortcut_recording`, `get_settings_file`) поток файла не ждут; события окнам уходят из потока без ожидания; ⌘, и «Настройки…» в меню значка. У него своя capability: `get_language`, `get_settings`, `set_text_size`, `choose_mirror_folder`, `set_shortcut`, `reset_shortcut`, `shortcut_recording`, шесть команд доступа 4a, новые `get_settings_file` и `settings_open_entry`, `core:event:allow-listen` / `allow-unlisten`. Чтения ленты, поиска, записи и импорта нет. Через `list_agent_log_entries` окно видит тексты записей, затронутых агентом (осознанно, как раздел «Журнал обращений» в 4a; ТЗ §12.3). У `main` перенесённые команды отзываются (остаются `get_settings`, событие `settings-changed` и новая команда `open_settings` для пункта «Настройки» профиля; события `open-message` и `settings-changed` он слушает); у окна захвата по-прежнему ровно семь. Отрицательные тесты — `src-tauri/tests/ipc.rs`.

## Отклонено
- **JSONC.** Приложение переписывает файл; комментарии пользователя пропали бы при первой правке из окна. Править с сохранением форматирования — отдельная работа, не нужная сейчас.
- **Отказ от `app_setting`** (файл как единственное хранилище). Предикат видимости чатов (ADR-0009) должен остаться SQL в одной транзакции с чтением журнала; битый или недоступный файл не должен менять права.
- **MCP-инструмент для настроек.** Агент менял бы собственные права по протоколу, который Rust проверяет как раз против него. Файловая система — путь, который у агента либо есть, либо нет.
- **`notify`.** См. выше.

## Последствия
- Новых крейтов в дереве нет: `kinige-store` берёт прямыми зависимостями `sha2` 0.10 (хэш файла) и `libc` 0.2 (`geteuid`, `O_NOFOLLOW`), обе уже стоят в `Cargo.lock` транзитивно. Если пользователь против прямых зависимостей — запасной путь: сравнивать с сохранённым содержимым вместо хэша и владельца файла сверять с владельцем каталога данных.
- **Гонка «окно ↔ агент».** Если внешний процесс заменил файл (`rename`) между перечитыванием в потоке и `rename` приложения, его правка теряется. Принято: окно перечитывает файл перед своей правкой, интервал — миллисекунды, побеждает последняя запись.
- **Окно «коммит → сочетание».** Файл применяется транзакцией, а сочетания принимает система уже после неё. Смерть процесса между ними теряет только правку сочетания из файла: хэш уже записан, поэтому при следующем запуске файл считается синхронизированным, а база хранит прежнее сочетание (файл при запуске перепишется из базы). Принято: правка сочетания редкая и видна пользователю.
- Папка копии, смена которой пришла во время прохода писателя копии, не теряется: проход начинается заново с новой папкой (`mirror.rs`), все дни помечены заново.
- Изменения за пределами 1–2 с применяются с задержкой опроса; правка и откат в пределах той же секунды с тем же размером и `mtime` теоретически не видны. Принято.
- Для `sync-crypto-guardian`: порядок применения при старте и после восстановления, проверки небезопасного файла, строка `mcp_log` с новым значением `tool` (без миграции), матрица IPC нового окна. Схема SQLite, протокол синхронизации и шифрование не меняются.
