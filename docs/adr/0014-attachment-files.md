# ADR-0014: Attachment files

Date: 2026-11-03. Status: **accepted** (KINIG-15, slice 7; the user chose the defaults of the slice questions on 03.11.2026). The synced part (groups, `core` bytes) is in ADR-0001 appendix §C.6. The `sync-crypto-guardian` pre-review of the spec is folded in.

## Context
Slice 7 stores photos and files next to the database, shows them in the feed, copies them into the Markdown folder and imports them from a Telegram export. Files can be gigabytes, the webview must not learn paths, and the first synced `attachment` rows must carry what slice 11 will need.

## Decisions

**Layout under `<data>`.** `attachments/<id>.<ext>` (one file per attachment, no deduplication, PRD §4.3), `attachments/.tmp/<process-uuid>/` (copies in progress), `attachments/.orphans/`, `thumbs/<id>.jpg|png`, `open/<process-uuid>/<id>/<name>`. `<id>` is the attachment UUID v4. **`ext`, defined once** (the §16 export reuses it): the lowercase original extension if it matches `^[a-z0-9]{1,10}$`, otherwise the one of the detected image format (`jpg`, `png`, `gif`, `webp`), otherwise `bin`. `attachment_local.file_name` is validated as `^<uuid>\.[a-z0-9]{1,10}$` before a path is built from it.

**Copy pipeline.** Stage 1, outside the writer: stream the source in 1 MiB chunks into `.tmp/<process-uuid>/<id>.part`, hash (sha256) and count bytes, compare with the source size (a source that changes size is `attachment_unreadable`), read the image header, `fsync`. Stage 2, one writer job: rename into `attachments/`, insert the `draft_attachment` row, commit. A crash between rename and commit leaves a file without a row; the sweep handles it.

**Sweep.** A writer job after the first frame, so it cannot interleave with stage 2. It removes `.tmp/` and `open/` directories of other process UUIDs, deletes thumbnails without a row, and for a file without a row: deletes it at once if the id has `tombstone(entity = 'attachment')` (a purge whose post-commit deletion failed), otherwise moves it to `.orphans/` (deleted after 30 days; a row whose file is in `.orphans/` gets it back, which covers restoring an older backup and then a newer one). A row without a file gets `attachment_local.state = 'missing'`.

**Decoding.** `image` 0.25 with `default-features = false` and the features `jpeg`, `png`, `gif`, `webp` (`zune-jpeg`, `gif`, `image-webp` are pulled in; `cargo deny` decides on licenses). `Limits`: `max_alloc` 512 MiB, `max_image_width` and `max_image_height` set. Thumbnails are built lazily by a pool of two threads under `catch_unwind`; a panic or an error gives the "No preview" tile. EXIF orientation applies to JPEG and WebP; PNG and GIF have none (`NoTransforms`). HEIC, AVIF, TIFF, BMP, SVG and RAW are stored unchanged as `file`.

**The custom protocol `kinige-media`.** `kinige-media://localhost/{thumb|full}/<uuid>` through `register_asynchronous_uri_scheme_protocol` (Windows origin `http://kinige-media.localhost`, per the wry docs). It does not go through the capability system, so the handler checks `UriSchemeContext::webview_label() == "main"` itself (the label is fixed when the webview is created, not read from the request): other labels get 403. The path must be exactly `thumb|full` and a lowercase UUID v4; anything else, a purged id or a `missing` file gets 404. A URL never carries a filesystem path. The responder takes the whole body in memory, so `full` serves only `kind = 'image'` with a detected format of JPEG, PNG, GIF or WebP and `byte_size <= 64 MiB`; larger files get the thumbnail. SVG is never served. Every answer has the `Content-Type` of the detected format, `X-Content-Type-Options: nosniff` and no `Access-Control-Allow-Origin`. CSP `img-src` gets `kinige-media:` and `http://kinige-media.localhost`. The Markdown renderer does not accept `kinige-media:` URLs written in entry text.

**Opening a file.** `open_attachment(id)` clones the file into `open/<process-uuid>/<id>/<sanitized name>` through a temporary name and a rename, mode 0600; edits in the system app never touch the stored file. A streamed copy likely lacks `com.apple.quarantine` (not verified), so a blocklist would be weak. The clone is opened with `open_path` only if its extension is on this **allowlist**: `jpg jpeg png gif webp heic heif avif tif tiff bmp pdf txt md rtf csv doc docx xls xlsx ppt pptx odt ods odp pages numbers key mp3 m4a aac wav flac ogg oga opus aiff mp4 m4v mov webm mkv avi`. Everything else (executables, scripts, archives, SVG, macro Office files, unknown) goes to `reveal_item_in_dir`.

**Drops and pastes.** A drop is read in Rust from `WindowEvent::DragDrop::Drop` of `main` only; JS gets a single-use token that expires, never a path. `attach_paste` takes raw bytes (64 MiB cap); its name is a sanitized hint. Paths from a drop or from a Telegram export are checked with `symlink_metadata` and `is_file` before anything is opened (no FIFO, no device); a NUL, a drive letter or an absolute path in an export is "bad path"; `..` and a canonical path outside the export folder are refused.

**Encodings.** `blob_key` and `sha256` are lowercase hex in the `core` group (the first write, so the choice is free; the JSON has no binary type). `blob_key` is 32 bytes from the OS CSPRNG (`getrandom`, pinned to the 0.4 line `uuid` uses); `remote_blob_id` is `Uuid::now_v7()` (uuid feature `v7`). Neither ever appears in `MessageView`, the MCP output, logs, an error text or the Markdown copy (property test).

**Placeholder rewrite (exception).** The Telegram import wrote a "[Photo not imported]" line. When the media later arrive, the line is removed from an entry that is unedited since import (`hlc(body) == hlc(core)` and `body_md` equal to the import's rendering in ru or en). The new `body` goes through the normal rewrite (new HLC, `base`/`supersedes`, `edited_at`, tags, search, `mirror_dirty`) but **no `edit` revision** is written: the old text is the new text plus one known line. This is an exception in the spirit of ADR-0006. For sync it is an ordinary body edit; two devices importing the same media produce equal texts and duplicate attachment rows (the §C.3 limitation).

**Markdown copy.** Files are cloned into `<chat>/<year>/<YYYY-MM-DD>/`, links are `![name](<YYYY-MM-DD/name>)` for images and `[name](<YYYY-MM-DD/name>)` for the rest, above the entry text. Names are sanitized for all three OSes and made unique case-insensitively with ` (2)`, ` (3)` in the order `(created_at, entry id, sort_index)`. A local table `mirror_file` records what the copy wrote, so a stale file is removed and nothing the user put there is ever deleted or overwritten (a file the copy wrote itself may be rewritten when the stored file's size changes). `fs::copy` is a clone on APFS (std docs); on another volume the bytes are copied, and a file already there with the same size is not copied again.

**Search.** The index text of an entry is its body plus the file-name stems; `SEARCH_INDEX_VERSION` goes up, so the index is rebuilt on open.

## Not verified
- Whether WKWebView hands a pasted Finder file to `clipboardData.files`.
- `http://kinige-media.localhost` on Windows (the Windows screenshots check it).
- The licenses of `gif` and `image-webp`: the `deny` job of CI passes with them (checked on the branch), so all four formats stay `image`.
- Whether `fs::copy` drops `com.apple.quarantine` on this macOS (the allowlist assumes it does).
