# ADR-0019: S4c-1 results, the sync server core on axum and Postgres

Date: 2026-11-06. Status: **accepted** after the review of `sync-crypto-guardian` (two rounds) and `slice-reviewer` (KINIG-98; spec `docs/slices/S4c1-server-core.md`, code `server/` with its `README.md`, the simulation in `spikes/S4a-sync`, feature `real-server`). Changes ADR-0001 (revision 10, each change marked "S4c, 2026-11-06"; HTTP shapes in the new appendix §A.6) and the PRD's version history; no change to the schema of the app, to `kinige-store` or to the formats of `kinige-crypto`.

## What was proven
The server side of ADR-0001 is buildable on axum and Postgres 17 with the same rules, and keeps them under real concurrency.
- Accounts, sessions and the credential flows of §8.3-§8.7 and §A.5 work over HTTP, ported from the S4b model: the server stores hashes only and compares them with `sodium_memcmp`; an unknown login looks exactly like a known one (the answer, the status and the log lines); registration and recovery are idempotent; a password change swaps on the credential version it was derived against (exactly one of six concurrent changes wins); a downgrade of the profile is refused by the server; recovery ends the other sessions; logout and a login that names the token it replaces exist.
- Push and pull follow §A.3 and §A.4 line by line (every row and every step has a named test, `server/README.md`); the lengths and the header of each envelope are judged with `Layout::parse` and the strict header parser before the rest of its bytes are read, and the whole body is limited as it is consumed.
- **The cursor does not skip records** (§B item 23). `seq` is issued under the account's row lock in the transaction of the write; 8 pushers and a puller never leave a gap, in three rounds, and the same race with `seq` from a plain Postgres sequence does (the negative control; the reader's cursor passes dozens of seqs that commit later, a different number every run). Pushes of two accounts do not wait for each other, and one account's push does wait for its lock.
- **No plain text in the database.** After a run with synthetic entries (text, title, `journal_date`, tag) and every credential flow with real keys, a scan of every table and of the whole log, for those texts and for 24 secrets in every encoding, finds nothing; the scanner finds a deliberate leak, the hashes the database really holds, and a text planted in a table nobody listed.
- Garbage (random and truncated bodies, random JSON, a real push body cut and flipped, on every route) gives a 4xx and never a 5xx or a panic: 5 000 cases at a seed other than the committed one, 300 in CI.
- **S4a with the real server** (feature `real-server`): the simulation's server is a trait with two implementations, and its properties 1-7 and 9 hold with every device talking to this server through its router, with real envelopes, at 30 and 8 cases (CI: 20 and 5); a client-side breakage still fails there. Property 8 and the restore generators are skipped: restore is S4c-2.

## What was found
1. **`tokio-postgres` writes every statement with its bound parameters into the log at `debug`.** The plain-text scan failed on the login, then showed key hashes and wraps in the same lines. The sink now writes the server's own records at the configured level and every other crate's at `warn` and above; the leak test runs at `trace` through the same filter (ADR-0001 §8.8).
2. **HLCs must compare as bytes in SQL.** A locale collation ignores hyphens at the first level; the columns are `COLLATE "C"` and the comparison is in Rust (§2).
3. **`stale` on a push needs the pusher's cursor in the request**, and any generation other than the current one is stale too. A new row of §A.3, step 4a of §A.4, a header of §A.6. The in-memory server of S4a does not answer it; the client treats it as "not acked, pull first".
4. **A repeated `purged` carries the accepted snapshot** (ADR-0017); the device must judge the ack against it (§3.5), which is slice 11's.
5. **The credential-version check comes before the old-key check**, so a stale client learns why. Idempotency compares the repeated request with the stored columns, which are hashes, instead of keeping `PackageRecord`s: a package changed by a later change is no longer "the same" (§A.5).
6. **§A.4 read the lengths before the session, so the server read up to 16 MiB of body from a client with no valid session** before it said 401. Decided (coordinator, review round 1): **authenticate before reading the push body.** The order is now the shape of the bearer token (no database) -> the session lookup -> the frames as before (declared length -> `Layout::parse` -> header -> body). Steps 1 and 2 of the server column of §A.4 are swapped, marked S4c; garbage without a session is a 401 and a test pins that no byte of the body is polled for it (`server/tests/push_input.rs`).
7. **`/v1/login/params` leaked that an account exists through the credential version** (review round 1): after one password change a known login answered version 2 and an unknown one 1, on an endpoint with no rate limit. The version is no longer in that answer; it comes with the login response, where the key was verified, and a password change names that one (§8.4, §8.5, §A.6). The test now compares a changed account with an unknown login: the answers differ in the salt only.
8. **The database's own log is a channel the scan does not read.** A registration race hit the unique index on `login` and Postgres wrote `DETAIL: Key (login)=(...) already exists`. Registration now takes transaction-scoped advisory locks on the normalized login and on the account id before it looks, so the index is not hit by a race (a test races eight registrations three ways and the Postgres log of the run has no error line). The operator must still protect Postgres's log like the server's own and keep statement logging off (§8.8, `server/README.md`).

## What is left
- **S4c-2 (KINIG-99):** blobs, backup and restore (the dump carries the lineage, the drops and the epochs; a restore appends a generation; the `GenerationChanged` path and the placement of §6.3 are built and unit-tested here, the abandoned-branch rule needs the cut time of a generation), account deletion, Q14, `docker compose`, TLS at a reverse proxy. For the push body: a read timeout (a client that holds a connection open and sends a byte a minute is limited only by the body cap today) and the proxy's `client_max_body_size`, which should sit at the 16 MiB of the server.
- **Slice 11:** the client side of everything above; the client sends the cursor header on every push (the server requires it); real rate-limit numbers; session expiry (a token lives until logout, a replacing login or a recovery); metrics.
- **Known limits, to be fixed in slice 11:**
  - Registration, push and pull have no rate limit and no size budget per account; only the login and the word checks are limited.
  - **There is no pool wait timeout.** A push holds a pool connection while it waits for the account row lock, the pool has 16 connections, and a request waits for a free one without a limit, so 16 simultaneous pushes to one account can stall every other account until they finish. A lock-wait timeout or a per-account concurrency limit, and a pool timeout that answers 503, belong with the real numbers.
- **Known limits:** compaction loads the open metadata of one account's whole log into memory (fine for 100 000 envelopes, not for a million); the `ops` table (idempotency) and `drops` are never trimmed; the rate limits are per process and empty after a restart; not run behind a connection pooler or on another Postgres than 17.
- **Not verified:** the throughput of push on a real disk (the S4a measurement of 100 000 envelopes needs a run of its own); the Windows and macOS builds (the crate is Linux first and is not in those CI jobs).
