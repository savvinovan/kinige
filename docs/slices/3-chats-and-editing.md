## Scenario
1. I update Kinige over a slice 2 database: all entries are in place. “Settings” has the row “Database backup: today, 09:12” and the backup folder. It holds the backup taken before the update and today's backup.
2. I press “+” next to the “Chats” section, type “Books”, pick 📚 in the picker. The new chat is open, the feed is empty, the cursor is in the input field. I write an entry: it goes to “Books”, “Books” has counter 1, Inbox keeps its count. I switch between chats with a click, and each has its own draft.
3. Right click on a chat: “Rename”, “Change emoji”, “Pin”, “Archive”. A pinned chat moves to “Pinned”, an archived one to “Archive”, which is collapsed. With a button I collapse the sidebar to a strip of emoji: the name shows on hover, the selected chat is highlighted.
4. In the input field I press “emoji”. The picker opens: recent, categories, search by name in English and Russian. A click inserts the emoji where the cursor is.
5. I hover over an entry: on the right, the row “copy, edit, task, favorite, more”. A right click or “more” opens the menu: “Copy”, “Edit”, “Task”, “Favorite”, “Change date”, “Delete”.
6. “Edit”: I change the text (where exactly is question 2), Enter saves, Esc cancels. The entry stays in its place with its time. The old version is saved in the database, and the Markdown copy is updated.
7. “Task”: the entry gets a checkbox, and a click on it marks the task done. “Favorite” adds a quiet mark. A click on `- [ ]` inside the text checks it; this is an edit of the text, and the old version is saved too.
8. “Change date” → calendar → I pick “yesterday”. The entry moves under the “Yesterday” label, and in the copy it moves to yesterday's file.
9. “Delete”: what I see in place of the entry is question 1. The counter goes down by 1, and the entry disappears from the copy. “Trash” at the bottom of the sidebar shows deleted entries: chat, date, “N days left”, “Restore”. A restored entry returns to its place. After 30 days the entry is deleted by itself.
10. I type «#идея …» (“#idea …”): `#идея` is highlighted. What a click on the tag does is question 3.
11. The menu bar icon menu: below “New note”, the recent chats. A click opens the main window directly on that chat.
12. After each step I do `kill -9` and launch again: chats, edits, dates, flags and the trash are in place.
13. The database is damaged (in the check, a test corrupts it). At start, the “The database is damaged” window with a list of backups and a button “Restore from the backup of …”. The damaged file is not deleted; it is moved aside next to the database.

## Included
- **Database backup and integrity** (§2.1, §10.4, §12.3), done first, before migration 3. Before any migration of an existing database, a backup is taken. Once a day (at start and by timer) a daily backup is taken; the 7 latest are kept. The backup is taken through the SQLite backup API from the read connection, into a temporary file + rename: in `rusqlite` 0.40.2 this is the `backup` feature, `Connection::backup` / `Backup::run_to_completion`, verified in the source. The fallback is `VACUUM INTO`: it is in the bundled SQLite 3.53.2 (`libsqlite3-sys` 0.38.2), while “available since 3.27” is from memory. A plain `fs::copy` does not work: under WAL the file without `-wal` is not consistent. `PRAGMA integrity_check` runs synchronously before a migration and in the background after the window is shown in all other cases, so as not to break the cold start < 1.5 s; its duration on 100k entries is not verified, measure it. The daily backup is taken only after a successful check; otherwise damaged backups would push out the good ones. On failure, the window from item 13. Restore: the damaged file is renamed to `corrupt-<time>.db`, the backup takes its place, a new `device_id` is created (ADR §1). The status and the backup folder are visible in “Settings”.
- **Migration 3** (`CREATE TABLE` without changing rows): the synced `message_revision` (`hlc_json` only `core`, `server_known`, `groups_raw`, `schema_version`) and `tombstone` (per §C), the local derived `message_tag` if question 3 is decided in favor of A or C.
- **Group rewrites** generalize `kinige_domain::append::rewrite_body` from slice 2 to any group. Bytes are written canonical, HLC grows strictly, the unknown is kept verbatim. For a message: `deleted` (delete and restore), `flags` (task, done, favorite), `placement` (`journal_date`; `base`/`supersedes` per §3.4, the first rewrite of this group), `body` (edit). For a chat: `meta` (name, emoji), `state` (pinned, archived). A new chat is created right away with all six groups under one HLC, `sv = 1`, and `order.sort_key` places it at the end of its section. Inbox can be neither archived nor deleted; it can be pinned. An entry with a group in an unsupported `sv` is read-only: menu items are unavailable.
- **An `edit` revision** is written in the same transaction on every `body` edit (including checking a `- [ ]`). It is a full snapshot of the entry before the edit (§4.2, ADR §3.4): the verbatim bytes of all groups with their HLC and `sv`, `raw` as a string, as for `conflict`. The format is added to the ADR-0001 appendix, §A.0. The id is a random v4. Appending with ⌘Enter still does not write a revision: the old text is a prefix of the new one (ADR-0006). There is no UI for version history.
- **Delete, trash, purge.** Delete and restore are Rust commands, without optimistic display. The test helper `mark_deleted` is removed, and the tests move to the real operation. Purge: at start and once a day, entries older than 30 days in the trash are deleted locally together with their revisions. Tombstones are written with a `purged_of` snapshot of all groups, including unknown ones; revisions get `cascade_of = id of the entry`, `held` = NULL; they are kept until binding and for no less than 180 days (ADR §3.5). There is no “Delete forever” button: question 4. The trash does not go into the Markdown copy (§16).
- **Chats in the main window:** selection by click, the feed and the draft of the selected chat, sending to it. The sections “Pinned” / “Chats” / “Archive” (collapsed); a section header is visible only if the section is not empty. The order is set by `sort_key`, for pinned chats by `pinned_at`. Creating and renaming happen in the D1 modal: a name of 1 to 128 characters, an emoji from the picker, 💬 when there is no emoji. The chat context menu. The collapsed state of the sidebar is stored in `app_setting`. The Markdown copy puts entries into the folder `<chat name>`: with identical names, a suffix from the start of the id; on rename, a rename of the folder and `mirror_dirty` for all days of the chat; the Inbox folder is still `Inbox`.
- **Entries:** the row of hover actions comes fully alive. The context menu is built with a design system component, not the system menu. It opens with a right click, the “more” button and from the keyboard (Shift+F10 / the menu key), moves with the arrows, closes with Esc. “Copy” copies the selection inside the entry, or the whole Markdown when nothing is selected. The calendar is our own month grid from tokens: the system `<input type=date>` is not used, its look is not controlled by tokens. Future dates are allowed (ADR §2).
- **Emoji picker**: one component for the input field and the chat. The data is in the bundle, no network (local-first). The look comes only from tokens. The base is `emojibase-data` data or a headless library (candidate: `frimousse`). From memory, **not verified**: versions, React 19, bundle size, Russian names, whether the library can work without a CDN. Check on npm in the first hour and record in the PR. “Recent” is stored in `app_setting`. The “Coming soon” hint is removed from the “emoji” button.
- **Tags:** `kinige-domain` parses `#tag`: letters of any alphabet, digits, `_`. Not a tag: inside code and links, `# ` in a heading, after a letter (`a#b`). Case does not matter. The tag is highlighted in the feed. If question 3 gives a filter, the `message_tag` table is updated in the same transaction as the entry and rebuilt from `body_md` during the migration.
- **Icon menu:** up to 5 recent chats by their latest entry, excluding the archive and Inbox. A click does `emit_to("main")`, and the main window opens on that chat.
- **IPC (§12.3):** new commands for the main window only. The capture window is denied each of them (negative tests); its set of six commands does not change.
- **Components** (the `design-system` agent, tokens only): chat row with a menu, section header, collapsed sidebar, context menu, emoji picker, calendar, editing inside the bubble, task checkbox and favorite mark, deleted bubble (per question 1), trash, tag, the “The database is damaged” window, the database backup row in Settings.

## User decisions (27.10.2026)
1. **After “Delete”** the bubble stays in place, dimmed, with the label “Deleted · Restore”, until the user leaves the chat. The feed does not shift. No toast.
2. **Editing happens right inside the bubble**, as in ChatGPT and Claude. Enter saves, Esc cancels, the draft in the input field is not touched.
3. **A click on a `#tag`** leaves only the entries with that tag in the feed of the current chat. At the top, the line “#tag ×”. The `message_tag` table is part of migration 3.
4. **The trash has “Delete forever”** for each entry, with a confirmation. This is the only confirmation in the app: the action is irreversible. Deleting writes tombstones (`purged_of`) and deletes revisions (`cascade_of`), the same as the automatic deletion after 30 days. There is no “Empty trash” button.

## User decisions (27.10.2026, acceptance)

1. **Moving an entry to another chat.** A correction of the spec: in PRD §5, “move to chat” is in the MVP context menu, with only “reply” marked P1 there, so the “Not included” line about moving entries is canceled. Two ways:

**Deviations and clarifications:**
1. **An entry with a group in an unsupported `sv` is entirely read-only** (`read_only`, menu items are unavailable, commands return `read_only`). The check item “`sv: 2` survives a rewrite of another group” is impossible in that form: there is no rewrite of such an entry. Unknown **groups** (by name) and unknown fields of known groups with `sv = 1` survive rewrites verbatim; a group with `sv > 1` blocks the whole entry.
2. **A tag of digits only (`#2026`) is not a tag** (`#1` is a number, not a topic; the rule was introduced in Rust, the spec did not have it): letters of any alphabet, digits and `_`, with at least one character that is not a digit.
3. **A damaged entry in the trash.** Purge reads only `hlc_json` and `deleted_at`; the `purged_of` snapshot is built as far as possible (unreadable groups are skipped, the tombstone stays); an entry whose `hlc_json` is unreadable stays in the trash entirely and shows an error, and the maintenance pass goes on (the `purge_failed` flag is visible in “Settings”). An entry whose `deleted` group is in an unsupported `sv` is not touched by automatic deletion; manually it gives `read_only`.
4. **The “database is newer than the app” state** (§10.4) is separate: the code `database_too_new`, `StartupState.databaseTooNew`, a screen without buttons; the file does not change, the backup folder is not created.
5. **Restore.** A restart after damage to the working database is allowed only with the `needs-recovery` mark; at launch the mark is re-checked synchronously (if not confirmed, it is removed); a restore runs once at a time, is marked by the file `restoring` and is repeated after a failure; the Markdown copy folder (per the backup's own setting) is renamed FIRST, before any move of the database, to `<name>-before-restore-<stamp>` (the name is unique; if the rename fails, the error `mirror_folder_busy`, nothing is touched), and all days are marked for rewriting; the folder path is not shown in the window (it depends on the chosen backup); a new `device_id` is created.
6. **Two fixes from the live run:** (a) after Enter/Esc in editing, focus returns to the bubble (the field disappeared and the keyboard lost its place: Shift+F10 and Tab started from zero); (b) the background integrity check runs at start and can find damage before the page subscribes to the event: `StartupState.corruptionFound` (the mark exists, the log is open), and the page asks for the state again after subscribing.
7. **Emoji:** `frimousse` 0.4.0 (headless, MIT, React 18 or 19, no network: our `resolveEmojiData` supplies the data) and `emojibase-data` 17.0.0 (en + ru, loaded dynamically at first open, ≈ 100 KB gzip per language). Version 18.0.0 was rejected: it was published less than two weeks ago. The picker detects which Unicode Emoji versions the system renders through a canvas (fallback threshold 15.1, from memory); on a real macOS 26.5 the set is rendered. The CSP did not change. The decision is recorded in `docs/adr/0007-emoji-picker.md`.
8. **Editing inside the bubble:** during editing the bubble keeps the width it had before; for a very short entry («Купить хлеб», “Buy bread”) the field is narrow, which is a matter of taste (the minimum width is one token). The line “Deleted · Restore” is longer than the time: the bubble of a deleted entry may become wider, and when the last line is tight, one line taller (the feed does not shift upwards; it is pinned to the bottom).

The other splits (the `groups.rs` tests, `hotkeys`, the store) were done by copying line ranges.
12. **Damage that is not visible at open.** Opening the database does not check integrity (the cost on a large database is not measured, cold start < 1.5 s): damage in the pages is found by the first background maintenance pass right after start, and the page receives “damage found” while the database is already open: the “The database is damaged” window in “restart” mode, and the list of backups after the restart (scenario item 13 happens in two steps). **Choice:** the window text in this mode no longer talks about “the working database” (“A check found damage in the database. Kinige will restart and offer backups…”). Showing the list right away without a restart cannot be done cheaply: a store once handed to the app (`app.manage`) cannot be removed from Tauri state, and the writer holds the database; a synchronous check before opening would be needed. If the check at start turns out to be cheap (a measurement on 100k entries), it can be placed before `open_store`. Besides the background pass, the same signal (the mark, a process flag, an event to the window; once per launch) is raised by any command that runs into `SQLITE_CORRUPT` / `SQLITE_NOTADB` (`Store::read` / `Store::write`), so “Restart” works in a window opened because reading the first settings failed. In the process it was found that `settings.rs` and `draft.rs` had their own local `read_err` / `write_err` without the “damaged” case: an error in settings and drafts on a broken page came as an ordinary read failure; now all modules use the shared ones. A finding during a restore is not lost: the flag is reset in `begin_restore` (a finding from the previous attempt does not apply to the new one), and the page asks for the state again after a successful `restoreBackup` (and on `database_corrupt` from `getSettings` of the restored backup switches to the “restart” window). A known theoretical gap, not fixed: the maintenance pass of a failed attempt, if it is still running, may set the flag after the reset in `begin_restore`. When a command makes the finding, the backup row in “Settings” (`backup.error`) also becomes `integrity_failed`, as in the window. In item 9, a third violation of rule 8 is added to the two `sed -i`: the edit of the `list_messages` call in the new test `maintenance_safety.rs` with a one-line Python replacement script (Edit would have been more precise).
13. **Search in the picker** works by substring in the label and the tags (`frimousse`: `label.includes` with weight 10, `tags.includes` with weight 1): “cat” finds both “Cat” and emoji whose tags have “cat” inside another word (books, phones). Narrowing it to the start of a word through the resolver's data is not possible (the library itself searches the prepared data, and the query is not passed to the resolver); our own search and list are separate work, not in this slice.
14. **An end-to-end IPC test of restore** (`restore_backup` → `resume_after_restore`) is impossible in the mock runtime: on macOS there is no window and no panel plugin (`panel::convert`), and on Linux `tray::setup` panics without GTK. The test `ipc_restore_e2e` checks the services failure (macOS): the store is not handed to the app, and the window with backups stays; the successful path was checked in the live window.
15. **Moving an entry to another chat (acceptance decisions).**
    - **Data.** `kinige_domain::message_ops::move_to_chat` rewrites only the `placement` group: a new `chat_id`, the same `journal_date`, `base`/`supersedes` through the same `chain_fields`/`set_chain` as for changing the date (ADR-0001 §3.4), a new group HLC (`next_hlc`); `core`, `body`, `flags`, `deleted` and revisions are not touched, no `edit` revision is written. `Store::move_message` refuses: the entry is in the trash or does not exist: `message_not_found`; any group with `sv > 1`: `read_only`; the target chat does not exist or is deleted: `chat_not_found` (an archived one is allowed); a move to the same chat is a success without a write. In the same transaction `mirror_dirty` is set on the entry's day **in the old and in the new chat**. Chat counters, the “recent chats” of the icon menu (`tray::refresh` after the command) and the tag filter read from the same tables and update by themselves. The command `move_message(id, chatId)` is `main` only (`MAIN_COMMANDS`, `build.rs`, `capabilities/main.json`); the capture window is denied (test `ipc_move.rs`, the `SLICE_THREE` matrix in `ipc.rs`).
    - **The drag threshold** is the pointer leaving the bubble's bounds (not a pixel count): while the pointer is inside the bubble, text selection works as before. The mechanism is pointer events (`pointerdown`/`pointermove`/`pointerup` on the document), not HTML5 DnD: in WKWebView it draws a system shadow and competes with selection; this was not separately checked on a real WKWebView, the choice was made for the reasons above. The “ghost” is a clone of the bubble in a portal (`.record-ghost`, `opacity.drag-ghost`, `layout.drag.ghost-max-width` in `design/tokens/drag.json`), the target is found by `elementFromPoint` and the `data-chat-drop` attribute; Esc, dropping elsewhere and losing the window cancel the drag, and after a drop the click on the bubble is suppressed. Bubbles in edit mode, deleted, read-only and unsent ones are not draggable; interactive elements inside the bubble (links, tags, checkboxes) do not start a drag.
    - **Archived chats as a target**: only when the “Archive” section is expanded (when collapsed they are not on screen; in the collapsed strip only the open archived chat is). From the entry menu, archived chats are always available.
    - **The submenu** is a second level of the same menu panel (“Back” → chats), not a second panel: this way a click elsewhere and focus behave the same on both levels. Esc and the left arrow go back to the first level, a second Esc closes the menu. 16. **Emoji in the quick capture window.** A button in the field, the same `EmojiPicker`, but not a popup panel (the window has no room beyond its bounds): the picker sits **in the flow** between the context and the field row (`EmojiInline`, a portal into `.composer__emoji-host`), the panel grows, `ResizeObserver` reports the height, the window grows upwards through `capture_resize`, the bottom edge stays in place. Esc: from the picker (focus in search) closes only the picker; from the field with the picker open, also the picker first; the next Esc hides the window. The selection is inserted at the cursor position, and focus returns to the field. A click elsewhere does **not** close the picker (people often click into the field right away and type); the button, a selection and Esc close it.
    - **“Recent” is shared**: `CaptureState.recentEmoji` (from settings) arrives on every show; a selection is written by **a new capture window command** `capture_add_recent_emoji(emoji) → list`: without it a selection from the capture window would not reach the shared list, and the main window's `add_recent_emoji` is not given to the window. The command takes neither a chat nor an entry, changes only the “recent” list, and has the same validation rules as `add_recent_emoji`. The capture window now gets **seven** commands; the set is pinned by tests (`ipc.rs`: exactly seven, everything else denied; `ipc_flows.rs`: a list shared with the main window). ## Notes for the following slices
- **Slice 4 (search):** `message_tag` already exists and is rebuilt during the migration; build FTS over `body_md` and keep in mind that an edit (`edit`) writes revisions with a full snapshot: do not put revisions into the index. The trash (`deleted_at IS NOT NULL`) does not go into search.
- **Slice 11 (sync):** the `edit` revision format, `tombstone` (`purged_of`, `cascade_of`, `held`) and the first rewrite of `placement` are described in ADR-0001, appendix §A.0 and §C.2; when the `supersedes` chain overflows, `chain_fields` drops **the smallest HLC** (not “the oldest in write order”). `conflict` revisions and server confirmation are still covered by tests at the write level.
- **Integrity check once a day:** in a long session, damage will be found no earlier than midnight; if that is unacceptable, add a check after every N-th commit or a “Check now” button in “Settings”.
- **The “The database is damaged” window and single-instance:** the restart through `app.restart()` was checked live on a build with a separate `identifier`; with the working `identifier`, the user's instance running next to it will take the launch for itself: this is a property of the plugin, not of the slice.
- **Editing and large entries:** the edit field has no maximum height (behavior on very long entries was not checked); if needed, inner scrolling and a max-height token.
- **Picker:** the category names in the Russian `emojibase` data are clumsy in places («тело людей», “people body”; «флаг», “flag”); if it matters, add our own labels in `emoji.*`.
