**The user's decisions of 20.11.2026 (binding):**
- «да не надо settings.json, можешь убрать это, достаточно все хранить в sqlite»: the `settings.json` file goes away; settings live only in SQLite (`app_setting`).

## Scenario
1. I update Kinige and open Settings (⌘,). The tree has Appearance, Keyboard shortcuts, Copies, and AI agent access with Visible chats and Access log. There is no "Settings file" item, no path to copy, no error mark and no "Changed via settings.json" line anywhere. All my settings are as they were. My old `settings.json` stays where it was; Kinige no longer reads it, and editing it changes nothing.
2. Agent access is on in "Read and write". I ask Claude "make the text in Kinige larger". It reads the settings and changes the text size. The main window and the settings window switch to large text at once, without a restart; no window comes forward and nothing takes focus. The access log shows "14:02 · Claude Desktop · changed a setting: text size".
3. "Set the quick capture shortcut to ⌃⌥J". Keyboard shortcuts now shows ⌃⌥J, ⌃⌥J opens the capture window and ⌃⌥N no longer does. If the system or another app holds ⌃⌥J, if the clipboard shortcut already uses it, or if it has no modifier, the agent tells me so and ⌃⌥N keeps working.
4. "Turn off your access", "let yourself see my Work chat", "move my copy folder to Dropbox": the agent answers that only I can change that, in Kinige's settings window. Nothing changes; the log shows "denied: settings window only".
5. In "Read only" the agent can tell me my shortcuts and text size, and a change is denied ("denied: read only"). With access off every call is denied, as today. What it reads never shows a folder path or a chat it cannot see.
6. I `kill -9` Kinige and start it: the large text and ⌃⌥J are in place.
7. I restore the journal from a backup: agent access is off afterwards, the mode and the visible chats are those of the backup, and the copy folder is the backup's (the folder that was there moves aside to `…-before-restore-…`, as today).

- **The user's `settings.json`** is never opened, read, written, renamed or deleted, and the settings window says nothing about it. The PR description carries one line for the release notes: "Kinige no longer reads settings.json; you may delete it (it may hold chat titles)".
- **Start-up applies nothing from a file.** One idempotent clean-up step at every start removes our own leftovers: regular files in the data directory named exactly `.settings.json.<UUID>.tmp` (no link is followed, an error is skipped, the log gets only a count) and the `settings_file_hash` row of `app_setting`.
- **What `app_setting` holds, and what MCP may do with it.** No key holds a secret (the OpenRouter key goes to the system store, §9.2, P1).
  - Settings, readable and writable: `text_size`, `shortcut_capture`, `shortcut_clipboard`.
  - Settings, readable only in part, changed only in the settings window: `mirror_dir` (read as `markdown_copy`, never the path) and agent access `mcp_enabled` (implied: a call needs it on), `mcp_mode`, `mcp_chats` (read as the visible chat ids only).
  - Window state, neither read nor written: `sidebar_collapsed`, `recent_emoji`, `forest_view`, `forest_mode`, `on_this_day_dismissed`. Internal: `search_index_version`. Retired: `settings_file_hash` (deleted at start). Keys that later slices add stay out until the allowlist names them.
- **Two MCP tools** (`kinige_domain::agent::AgentTool`, through the single entry point `Store::agent_call`, one log row per call):
  - `get_settings` (read, `readOnlyHint`): `{"text_size", "shortcuts": {"capture", "clipboard"}` each as `{"value", "default", "assigned"}`, `"markdown_copy": "default_folder" | "chosen_folder" | "off"`, `"agent_access": {"mode", "visible_chat_ids"}`, `"writable": ["text_size", "shortcuts.capture", "shortcuts.clipboard"]}`. `visible_chat_ids` is selected with ADR-0009's visibility predicate, so an id in `mcp_chats` of an excluded, deleted or missing chat never appears; titles come from `list_chats`.
  - `set_setting(key, value)` (write, listed only in "Read and write"): `text_size` takes `"normal"` or `"large"`; `shortcuts.capture` and `shortcuts.clipboard` take the ADR-0006 form, such as `"Ctrl+Alt+KeyJ"`, and `null` for the default. The reply is the `get_settings` object after the change. `agent_access.enabled`, `agent_access.mode`, `agent_access.chats` and `mirror.folder` get the new `setting_not_writable` ("only the user can change this, in the Kinige settings window"). Any other key, a wrong type or form, a duplicate and a shortcut the system refused get `invalid_argument`, whose text says which; the old shortcut keeps working.
  - `instructions` get one sentence on what the two tools do and that access and the copy folder are the user's.
- **The same path as the window.** `text_size` goes through `Store::set_text_size`; a shortcut through `Hotkeys` with ADR-0006's steps (check, register in the system, save, release the old one). After a change the Tauri layer sends `settings-changed` to `main` and `settings` (`notify_changed`), as after a click. No tool shows, raises or focuses a window (rule 11).
- **One transaction.** The save step re-checks "access on" and "Read and write" inside the writer transaction that writes the value and its `mcp_log` row (ADR-0009). If it fails, nothing is stored, and a shortcut already registered in the system is released.
- **Shortcut changes are serialized.** `Hotkeys` holds one lock over check, register, save and release. The file thread used to queue the window's edits; MCP adds a second caller, and two interleaved changes could leave a stray system registration. The lock is never taken on the main thread (registration itself waits for it).
- **The log.** `args_json` of `set_setting` holds `key` (one of the seven names above, otherwise `"other"`) and, on success only, `value` (the canonical text size or accelerator); `get_settings` has `{}`. A new outcome `not_writable`. The access log shows "read the settings", "changed a setting: text size", "… capture shortcut", "… clipboard shortcut" and "denied: settings window only", in en and ru.
- **Settings window text.** Under the mode choice of "AI agent access", one quiet line: "In read and write mode an agent can also change the text size and the shortcuts." («В режиме чтения и записи агент может менять размер текста и сочетания клавиш.»)

What is stored: the `settings_file_hash` row deleted at start. IPC: one command removed from the settings window. ## For the guardian
1. **The allowlist.** `set_setting` maps `key` to a fixed Rust enum of three writable settings; no input string becomes an `app_setting` key. The four refused names and every other string write nothing: per key, `app_setting` is identical before and after.
2. **No path widens access.** `mcp_enabled`, `mcp_mode`, `mcp_chats` and `mirror_dir` change only through the settings window's commands, which MCP cannot reach; `settings.json` is gone; `get_settings` returns visible chat ids through the predicate and no path. Accepted, as PRD §4.1: a process that writes the database file itself.
3. **The mode check.** `set_setting` needs access on and "Read and write", checked before parsing and again inside the writer transaction of the change. `get_settings` needs access on, in either mode.
4. **The log row.** Every call is one row, refusals included; a change and its row are one transaction; `args_json` holds only `key` and the canonical `value`, never a refused value.
5. **Shortcuts and the transaction.** The system registration comes before the transaction, and a failed transaction releases it. A process death loses nothing: registrations end with the process, and the next start registers only the stored value.
6. **Restore.** Access off; the mode and the chats from the backup, inert until the user turns access on in the window, with the warning and the list in view; nothing applied afterwards.
7. **The clean-up.** It deletes only the exact names of our own temporary files, follows no link, never touches `settings.json`, and deletes one `app_setting` row.
8. **Window command sets (§12.3).** The settings window loses `get_settings_file`, which then is unknown to `main`, `settings` and `capture`; `main` is unchanged; capture keeps its ten. No new Tauri command.
9. **Accepted risk.** A write-mode agent can change the two global shortcuts, which the user notices when a key stops working. It is logged and reversible, and reserved or modifier-less shortcuts are refused.

## Open questions
None left for the user. Decided by the coordinator on 20.11.2026 (the user was told and has not objected; each is reversible):
1. An agent cannot change agent access (on or off, mode, visible chats) or the copy folder: only the settings window can.
2. Any change needs "Read and write"; reading works in "Read only" and shows no paths and no chat beyond the visible ones.
3. After a restore, agent access is off, and the mode and visible chats are the backup's. The copy folder is the backup's, and the previous one moves aside.
4. Kinige removes its own leftover temporary files of the old settings file at start; the file itself stays as it is.
5. The settings window says nothing about the old file.

Decided in this spec, on the same footing: no "changed by an agent" mark next to a section; the one-line hint under the mode; old log rows keep their "settings.json · access changed" label.
