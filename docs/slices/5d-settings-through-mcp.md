**The user's decisions of 20.11.2026 (binding):**
- «да не надо settings.json, можешь убрать это, достаточно все хранить в sqlite»: the `settings.json` file goes away; settings live only in SQLite (`app_setting`).

## Scenario
1. I update Kinige and open Settings (⌘,). The tree has Appearance, Keyboard shortcuts, Copies, and AI agent access with Visible chats and Access log. There is no "Settings file" item, no path to copy, no error mark and no "Changed via settings.json" line anywhere. All my settings are as they were. My old `settings.json` stays where it was; Kinige no longer reads it, and editing it changes nothing.
2. Agent access is on in "Read and write". I ask Claude "make the text in Kinige larger". It reads the settings and changes the text size. The main window and the settings window switch to large text at once, without a restart; no window comes forward and nothing takes focus. The access log shows "14:02 · Claude Desktop · changed a setting: text size".
3. "What is my quick capture shortcut? Set it to ⌃⌥J." The agent tells me it is ⌃⌥N, and that only I can change shortcuts, in Kinige's settings window. Nothing changes; the log shows "denied: settings window only".
4. "Turn off your access", "let yourself see my Work chat", "move my copy folder to Dropbox": the same answer, nothing changes, the same log line.
5. In "Read only" the agent can tell me my text size and shortcuts, and a change is denied ("denied: read only"). With access off every call is denied, as today. What it reads never shows a folder path or a chat it cannot see.
6. I `kill -9` Kinige and start it: the large text is in place.
7. I restore the journal from a backup: agent access is off afterwards, no chat is visible to agents and the mode is "Read only", whatever the backup held. The copy folder is the backup's (the folder that was there moves aside to `…-before-restore-…`, as today).

- **The user's `settings.json`** is never opened, read, written, renamed or deleted, and the settings window says nothing about it. The PR description carries one line for the release notes: "Kinige no longer reads settings.json; you may delete it (it may hold chat titles)".
- **The `settings_file_hash` row stays, inert.** No code of this slice reads, writes or deletes it, start-up and restore included. Reason (for ADR-0022): the slice has no migration, so 0.9.2 can still open the database after a downgrade, and in 0.9.2 a missing or different hash means "apply the file", which would switch access back on from a stale `settings.json`. With the row kept the hash matches, and 0.9.2 rewrites the file from the database. Accepted in words: a restore followed by a downgrade may still apply the stale file.
- **Start-up applies nothing from a file.** At every start one idempotent step removes our own leftovers: regular files in the data directory whose names have exactly the shape `.settings.json.` + 32 lowercase hex characters + `.tmp` (what `Uuid::new_v4().simple()` gave in `io.rs`). A hyphenated look-alike, a symlink and a directory are kept; no link is followed, an error is skipped, and the log gets only a count.
- **What `app_setting` holds, and what MCP may do with it.** No key holds a secret (the OpenRouter key goes to the system store, §9.2, P1).
  - Readable and writable: `text_size`.
  - Readable, changed only in the settings window: `shortcut_capture`, `shortcut_clipboard`.
  - Readable only in part, changed only in the settings window: `mirror_dir` (read as `markdown_copy`, never the path) and agent access `mcp_enabled` (implied: a call needs it on), `mcp_mode`, `mcp_chats` (read as the visible chat ids only).
  - Neither read nor written: the window state `sidebar_collapsed`, `recent_emoji`, `forest_view`, `forest_mode`, `on_this_day_dismissed`; the internal `search_index_version`; the retired `settings_file_hash`. Keys that later slices add stay out until the allowlist names them.
- **Why shortcuts are read-only through MCP** (the guardian's ruling; it goes into ADR-0022). `set_setting("shortcuts.clipboard", "Cmd+KeyV")` would pass `is_reserved`, which refuses only ⌘Q and unshifted ⌘W, ⌘H, ⌘M and ⌘Space, and would register. From then on every ⌘V in any app saves the clipboard to Inbox with only a tray blink, and an agent that sees Inbox reads the copied passwords and codes. `shortcuts.capture` is read-only too: it is a system-wide key grab that steals focus.
- **Two MCP tools** (`kinige_domain::agent::AgentTool`, through the single entry point `Store::agent_call`, one log row per call):
  - `get_settings` (read, `readOnlyHint`) is built from its own explicit struct, never by serializing the window's `Settings` and removing fields: `{"text_size", "shortcuts": {"capture", "clipboard"}` each as `{"value", "default"}`, `"markdown_copy": "default_folder" | "chosen_folder" | "off"`, `"agent_access": {"mode", "visible_chat_ids"}`, `"writable": ["text_size"]}`. A snapshot test pins this exact key set. `visible_chat_ids` is selected with ADR-0009's visibility predicate, so an id in `mcp_chats` of an excluded, deleted or missing chat never appears; titles come from `list_chats`.
  - `set_setting(key, value)` (write, listed only in "Read and write"). Only `text_size` is writable, with `"normal"` or `"large"`; the reply is the `get_settings` object after the change. `shortcuts.capture`, `shortcuts.clipboard`, `agent_access.enabled`, `agent_access.mode`, `agent_access.chats` and `mirror.folder` get the new `setting_not_writable` ("only the user can change this, in the Kinige settings window"). Any other key, including raw `app_setting` names (`mcp_enabled`, `mcp_mode`, `mcp_chats`, `mirror_dir`, `shortcut_capture`, …) and case or whitespace variants of the known names, and any wrong value get `invalid_argument`. A refused call writes nothing and touches no shortcut registration.
  - `instructions` get one sentence on what the two tools do, and that shortcuts, agent access and the copy folder are the user's.
- **The same path as the window.** `text_size` goes through `Store::set_text_size`. After the change the Tauri layer sends `settings-changed` to `main` and `settings` (`notify_changed`), as after a click. No tool shows, raises or focuses a window (rule 11).
- **One transaction.** The save re-checks "access on" and "Read and write" inside the writer transaction that writes `text_size` and its `mcp_log` row (ADR-0009). If access was switched off between the first check and the save, nothing is stored and one refusal row is logged.
- **The `Hotkeys` change lock stays.** The window is still a caller (two quick `set_shortcut` or `reset_shortcut` calls), and no file thread queues its edits any more. It is a second mutex, separate from `inner`, held over check, register, save and release. `inner` is never held across `register`; `on_shortcut` and `overlay` take only `inner`; `register_saved` needs no lock. `set_shortcut` and `reset_shortcut` stay `async` commands, so the change lock is never taken on the main thread (a pool thread holding it waits for the main thread inside `register`; a sync command waiting for it there would deadlock). The window's steps (ADR-0006) are otherwise unchanged.
- **The log.** `args_json` of `set_setting` holds `key` (one of the seven known names above, otherwise `"other"`) and, on success only, `value` (the canonical text size); `get_settings` has `{}`. A new outcome `not_writable`; `outcome` is plain `TEXT`, so it needs no migration. The access log shows "read the settings", "changed a setting: text size" and "denied: settings window only", in en and ru.
- **Settings window text.** Under the mode choice of "AI agent access", one quiet line: "In read and write mode an agent can also change the text size. In either mode it can read the text size and the shortcuts." («В режиме чтения и записи агент может также менять размер текста. В любом режиме он видит размер текста и сочетания клавиш.»)
- **`restore_backup`.** The pre-read of `mirror.folder` from the file and its second move-aside go. The backup's own copy folder moves aside as today, and the restored copy folder is the backup's. The restore transaction sets `mcp_enabled = 0`, `mcp_chats = []` and `mcp_mode = 'read'`: a restore can only narrow access. Reason: without the file, a backup's `read_write` would become effective for the first time, and a backup's list may hold chats removed from it since. Nothing is applied on top afterwards.
- **Screens scenarios.**
  - No switch inside the app (an environment variable, a flag, a test hook or a driver step) ever turns agent access on. `sqlite3` on the throwaway database stays the only test path.
  - Every old scenario that switches large text by editing the file (13: `4b`, `5`, `6`, `7`, `7a`, `7b`, `chat-color`, `kinig-132`, `kinig-134`, `kinig-135`, `kinig-145`, `kinig-153`, `viewer`) sets it through the settings window with the screens driver (ADR-0016) instead: one `lib.sh` helper, `screens.yml` enables the driver for these scenarios, and no MCP session or access log row is added to them. `7b.sh` sets its agent access with `sqlite3` before launch. `4b.sh` loses its file shots (08, 09, 11, 12, `settings-file.txt`); those stay in `docs/screens/4b/` as history.
  - New `scripts/screens/5d.sh`, the only scenario that uses the MCP tool. Its helper switches the three access keys on with `sqlite3` for the session and puts them back afterwards, on failure too (a `trap`).
  - The driver helper is proven by one run of `7b.sh` (its access setup changes too) besides `5d.sh`; the other twelve take the same one-line change and are not rerun.

## For the guardian
1. **The allowlist.** `set_setting` maps `key` to a fixed Rust enum with one writable setting, `text_size`; no input string becomes an `app_setting` key. The six refused names, the raw `app_setting` names, their case and whitespace variants and every other string write nothing: `app_setting` is byte-identical before and after.
2. **No path widens access.** `mcp_enabled`, `mcp_mode`, `mcp_chats`, `mirror_dir` and both shortcuts change only through the settings window's commands, which MCP cannot reach; `settings.json` is gone; `get_settings` returns visible chat ids through the predicate and no path. No in-app switch turns access on for tests. Accepted, as PRD §4.1: a process that writes the database file itself.
3. **The mode check.** `set_setting` needs access on and "Read and write", checked before parsing and again inside the writer transaction of the change. `get_settings` needs access on, in either mode.
4. **The log row.** Every call is one row, refusals included; a change and its row are one transaction; `args_json` holds only `key` (a known name or `"other"`) and the canonical `value` on success, never a refused value.
5. **`get_settings`** is its own struct with a pinned key set, without `assigned`, paths, titles or window state.
6. **Restore.** Off, `read`, no visible chat; nothing applied afterwards.
7. **The hash row and the clean-up.** The row is kept and never touched (the downgrade reason; the restore-then-downgrade corner accepted). The clean-up deletes only regular files of the exact 32-hex shape, follows no link and never touches `settings.json` or `app_setting`.
8. **The `Hotkeys` lock.** A second mutex; `inner` never held across `register`; presses and the overlay never wait for a change.
9. **Window command sets (§12.3).** The settings window loses `get_settings_file`, which then is unknown to `main`, `settings` and `capture`; `main` is unchanged; capture keeps its ten. No new Tauri command.

## Open questions
None left for the user. Decided by the coordinator (the user was told and has not objected; each is reversible):
1. An agent cannot change agent access (on or off, mode, visible chats) or the copy folder: only the settings window can (20.11.2026).
2. Any change needs "Read and write"; reading works in "Read only" and shows no paths and no chat beyond the visible ones (20.11.2026).
3. Shortcuts are read-only for agents, on the guardian's ruling of 20.11.2026 (the ⌘V risk above). The user may later allow `shortcuts.capture` with Ctrl+Alt combinations only.
4. After a restore, agent access is off, no chat is visible and the mode is "Read only", on the guardian's ruling. The copy folder is the backup's, and the previous one moves aside.
5. Kinige removes its own leftover temporary files of the old settings file at start; the file itself stays as it is (20.11.2026).
6. The settings window says nothing about the old file (20.11.2026).

Decided in this spec, on the same footing: no "changed by an agent" mark next to a section; the hint under the mode; old log rows keep their "settings.json · access changed" label.
