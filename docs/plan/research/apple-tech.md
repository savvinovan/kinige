## 1. Sync: CKSyncEngine and CloudKit

### 1.1 CKSyncEngine
- Availability iOS 17 / macOS 14: UNCERTAIN-close-to-CONFIRMED. Introduced at WWDC23 (session "Sync to iCloud with CKSyncEngine"), https://developer.apple.com/videos/play/wwdc2023/10188/ . The documentation page itself did not open in this session (404), so the OS versions are confirmed only by secondary sources and my memory (iOS 17+/macOS 14+). Before fixing the minimum OS, check the page https://developer.apple.com/documentation/cloudkit/cksyncengine manually.
- Purpose: CONFIRMED (per the WWDC23 session description) - for apps with THEIR OWN local storage (not NSPersistentCloudKitContainer). The engine takes care of scheduling sends/fetches, change tokens (via a serializable `State`), batching, retries, reacting to account changes and push notifications. You implement `CKSyncEngineDelegate`: `handleEvent` (fetchedRecordZoneChanges, sentRecordZoneChanges, stateUpdate, accountChange...) and `nextRecordZoneChangeBatch` (you assemble the CKRecords to send). You save the state (`stateSerialization`) yourself in your DB - UNCERTAIN in the details (per the session and memory), but the pattern is standard.
- For SQLite apps: the pattern is an "outbox/pending changes" table + record metadata (recordName = row UUID, CKRecord system fields as archived data via `encodeSystemFields` in order to keep the recordChangeTag). Apple published a sample (CloudKit Samples: CKSyncEngine), linked from the session page.
- Conflicts: CKError.serverRecordChanged arrives in `sentRecordZoneChanges.failedRecordSaves`, userInfo contains serverRecord/clientRecord/ancestorRecord; resolution is manual (field-level merge) and re-queuing. This is the "record change tag" model (optimistic locking). UNCERTAIN as a documentation quote (the page did not open), but the serverRecordChanged behavior is classic CloudKit behavior.
- Because of this, the schema should be designed so that conflicts are rare: messages are immutable/append-mostly, text is edited as a whole field with LWW (last-writer-wins) by timestamp, deletions are tombstones.

### 1.2 CloudKit limits
- Per-operation limit: CONFIRMED. Per the CKError.limitExceeded documentation, "server limits may change; general guideline: 400 items (records/shares) per operation, 2 MB per request (not counting assets). On limitExceeded - split the operation in half and retry". https://developer.apple.com/documentation/cloudkit/ckerror/limitexceeded
  (CKSyncEngine splits batches itself, but it is better to limit your own `nextRecordZoneChangeBatch` to ~ tens of records.)
- Record size 1 MB (without assets): CONFIRMED only by the ARCHIVED CloudKit Web Services documentation (2016): "record size 1 MB without Asset fields", "asset file 50 MB", "200 operations per request". https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/PropertyMetrics.html . These numbers are outdated relative to "400 items" (see above), so: 1 MB per record - UNCERTAIN currency, but a reasonable working bound; the 50 MB per-asset limit - UNCERTAIN (archive; other, later sources name more, but I did not confirm that). Do not plan for files >50 MB without your own verification; for video, plan chunking or separate storage.
- Asset upload token limit: Apple forums (DTS) - up to 200 tokens per request; for batches of records with assets they advise ~100 or fewer (UNCERTAIN, forum): https://developer.apple.com/forums/thread/774403
- Rate limits: I did not find numeric values in the official documentation. Errors requestRateLimited/zoneBusy with retryAfter. UNCERTAIN; CKSyncEngine handles retryAfter itself. We do not give specific numbers.
- iCloud quota: CONFIRMED. CKError.quotaExceeded: in the private DB - the user has run out of iCloud storage, the app should suggest going to iCloud settings; in shared - the zone owner's quota. Data keeps living locally; sync stalls until space is freed. Private DB storage counts against the user's quota (not yours). https://developer.apple.com/documentation/cloudkit/ckerror/quotaexceeded . Consequence: heavy attachments quickly hit the free 5 GB - a "sync paused" UX and a "don't sync video" option are needed.

### 1.3 encryptedValues and ADP
- CONFIRMED: `CKRecord.encryptedValues`, iOS 15+/macOS 12+. Any supported types are encrypted, except CKAsset (always encrypted by default) and CKRecord.Reference (not encrypted, the server needs it). Only NEW fields can be encrypted (not existing schema fields) and not in the public DB. There are no indexes on encrypted fields - they cannot be used in CKQuery predicates/sorting. Encryption happens on the device. With ADP enabled, keys are available only to the record owner and share participants. https://developer.apple.com/documentation/cloudkit/ckrecord/encryptedvalues
- Consequence: server-side search is impossible -> FTS and semantics strictly local (that is your plan anyway). Put all user fields (text, file names, metadata) into encryptedValues from the very first schema release - adding it later is impossible for already existing fields. The CloudKit production schema can only be changed additively.
- CKSyncEngine + encryptedValues are compatible (both work at the CKRecord level) - UNCERTAIN (I did not check with a separate source, but it is the standard record API).
- ADP: private DB data with ADP gets end-to-end protection; without ADP, CloudKit fields marked encrypted are still encrypted with keys available only to the user (the docs explicitly describe only the ADP case) - do not make claims that "Apple cannot read it" without ADP.

### 1.4 Web / Android
- CloudKit JS and CloudKit Web Services (REST) exist; access to the PRIVATE DB is possible only after the user signs in with an Apple ID (web auth), server-to-server keys are only for the public DB. CONFIRMED by Apple TN2241 (archive): https://developer.apple.com/library/archive/technotes/tn2241/_index.html ; how current CloudKit JS support is and the limitations for encryptedValues on the web - UNCERTAIN (not checked; JS has limitations, and encrypted fields may be unavailable).
- Conclusion: an Android client via CloudKit is a bad path (no native SDK, sign-in UX through a web window). If Android/Web is really planned, keep the sync layer behind a protocol and allow for a second backend (for example, your own server/CRDT). This is a strong argument against tying the data model deeply to CloudKit specifics.

## 2. SwiftData vs GRDB vs Core Data

### SwiftData + CloudKit
- CONFIRMED by documentation and write-ups (https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices , https://fatbobman.com/en/snippet/rules-for-adapting-data-models-to-cloudkit/): no `@Attribute(.unique)`; all properties optional or with a default; all relationships optional; the `.deny` delete rule is not supported; ordered relationships are not allowed. Violations may make the store impossible to open (UNCERTAIN: sources disagree - "silently" or "crashes").
- No full-text search in SwiftData: UNCERTAIN (I found only an absence of mentions; SwiftData supports #Predicate with contains, but there is no FTS5/tokenization). The practical workaround is a separate SQLite FTS5 alongside.
- Maturity 2025-2026: forums report sync failures on iOS 26 (https://developer.apple.com/forums/thread/811675 - BAD_REQUEST after an update; thread without a confirmed solution) and migration problems with NSCloudKitMirroringDelegate (https://developer.apple.com/forums/thread/775060, reportedly fixed in the iOS 26 beta). These are individual reports, not proof of a systemic problem -> UNCERTAIN. For 100k messages with attachments, FTS, fine-grained transaction control and custom indexes, SwiftData is a risky choice. SwiftData sync also gives no control over conflicts and batching (NSPersistentCloudKitContainer under the hood).

### GRDB
- CONFIRMED (README, v7.11.1 of 2026-06-18; iOS 13+/macOS 10.15+, SQLite 3.20+, Swift 6.1+/Xcode 16.3+): migrations, full-text search (FTS5Pattern etc.), SQLCipher (separate installation), ValueObservation (including Combine). The repository is active (~8.7k stars). https://github.com/groue/GRDB.swift ; https://raw.githubusercontent.com/groue/GRDB.swift/master/README.md . (The first 100k characters of the README were read; I saw nothing about CloudKit in the README.)
- Shared DB in an App Group: the GRDB guide describes the 0xdead10cc problem and an experimental suspension mechanism (see section 7). https://mintlify.com/groue/GRDB.swift/guides/sharing-a-database

### SQLiteData (Point-Free)
- CONFIRMED: a library, a "lightweight alternative to SwiftData" on top of GRDB, with `@Table`, `@FetchAll` and CloudKit sync via `SyncEngine` (and sharing). Release 1.0 - 2025-09-18 (https://forums.swift.org/t/sqlitedata-1-0-an-alternative-to-swiftdata-with-cloudkit-sync-and-sharing/82211); currently the main documentation on the Swift Package Index refers to release 1.12.1. https://github.com/pointfreeco/sqlite-data
- Details of the limitations (UUID primary keys, foreign keys, unique constraints, asset sizes, minimum OS): UNCERTAIN - the documentation pages did not return text. Known from a secondary source: sharing of root records only (tables without foreign keys) - UNCERTAIN. Read the CloudKit article in their DocC before choosing. The 1.0 post does not mention that the sync is built specifically on CKSyncEngine - UNCERTAIN (to my knowledge it is built on it, but I did not confirm).
- Harmony (aaronpearce/Harmony): CONFIRMED per the catalog - GRDB + CloudKit, iOS 17/macOS 14, does not support foreign keys, direct writes to GRDB bypassing Harmony are not tracked, last push October 2024 -> practically abandoned. https://awesome.ecosyste.ms/projects/github.com%2Faaronpearce%2Fharmony . I do not recommend it.

## 3. Text editor

- SwiftUI TextEditor with AttributedString: CONFIRMED. iOS 26 / macOS 26: `TextEditor` accepts Binding<AttributedString> (rich text), there is a formatting panel, and the allowed formatting can be restricted (AttributedTextFormattingDefinition). WWDC25 session 280 "Cook up a rich text experience in SwiftUI with AttributedString", sample "Building rich SwiftUI text experiences" (iOS 26+). https://developer.apple.com/videos/play/wwdc2025/280/ ; https://developer.apple.com/documentation/swiftui/building-rich-swiftui-text-experiences . Open questions (forum): invoking the formatting panel programmatically is impossible/non-obvious. This is rich text, not live Markdown; for a Markdown editor with syntax highlighting you would have to map Markdown<->AttributedString yourself and control the selection (SelectionAPI in 26 - UNCERTAIN).
- TextKit 2: UNCERTAIN-CONFIRMED. NSTextView/UITextView use TextKit 2 by default (since iOS 16/macOS 13). STTextView is built on TextKit 2 and its author documents many TextKit 2/AppKit bugs that he reported to Apple. https://github.com/krzyzanowskim/STTextView
- swift-markdown (Apple, on cmark-gfm) - an AST parser: UNCERTAIN (I did not open it in this session, known from memory; good for parsing and for your highlighting).
- MarkdownUI: CONFIRMED - the README says "MarkdownUI is in maintenance mode"; the successor is Textual. https://github.com/gonzalezreal/swift-markdown-ui
- Textual (gonzalezreal): CONFIRMED - "spiritual successor to MarkdownUI", a SwiftUI text rendering engine: InlineText/StructuredText, text selection with copying, parsing via Foundation AttributedString, inline attachments, animated images, code highlighting, math. The README shows installation `from: "0.1.0"`, there are no releases on the page, platform minimums are not stated -> a young library, UNCERTAIN on stability. https://github.com/gonzalezreal/textual . This is a RENDERER, not an editor.
- STTextView: CONFIRMED - TextKit 2, macOS 14+/iOS 16+, a SwiftUI wrapper with an AttributedString binding; LICENSE GPLv3 (commercial license separately) - an important risk for a closed-source app. https://github.com/krzyzanowskim/STTextView
- Runestone: CONFIRMED - "performant plain text editor for iOS", macOS is not the focus (Catalyst "should mostly work"); not archived. Not suitable for cross-platform. https://github.com/simonbs/Runestone
- Bear: UNCERTAIN/partial. Publicly: Bear 2 is a "custom text editing engine" rewritten from scratch, markup is hidden and shown on selection (https://blog.bear.app/2023/07/bear-2-is-here/); the same engine is in Lettera (https://9to5mac.com/guides/lettera/). I did not find technical details (TextKit or not) publicly available. Common practice (my knowledge, not confirmed by a source for Bear): store plain Markdown, parse on every edit and apply attributes to NSTextStorage.

## 4. Feed

- ScrollPosition / scrollPosition(id:) / defaultScrollAnchor: CONFIRMED. `scrollPosition(id:anchor:)` and `scrollTargetLayout` - iOS 17/macOS 14; the `ScrollPosition` struct and `defaultScrollAnchor(_:for:)` (roles) - iOS 18/macOS 15 (`defaultScrollAnchor(_:)` without a role - iOS 17). The documentation itself says that SwiftUI tries to keep the view with the given id visible across changes (data reordering, resize); a point-based position (offset) is NOT preserved when content size changes. https://developer.apple.com/documentation/swiftui/scrollposition ; https://developer.apple.com/documentation/swiftui/view/scrollposition(id:anchor:) ; https://developer.apple.com/documentation/swiftui/view/defaultscrollanchor(_:for:)
- Known problems (forums, UNCERTAIN as "current state", but reproducible):
  - LazyVStack with variable height: stutter/jumps when scrolling up (https://developer.apple.com/forums/thread/685461, 2021, a 2024 reply - still on iOS 17.2).
  - Jank with thousands of rows in List and LazyVStack, switching to List did not help (https://developer.apple.com/forums/thread/718929).
  - defaultScrollAnchor(.bottom) + LazyVStack: blank screen with long messages (https://developer.apple.com/forums/thread/741406).
  - A thread about iOS 27: scrollTo stopped reaching unrealized LazyVStack rows; position preservation on prepend does not work (https://developer.apple.com/forums/thread/848608) - a beta report, UNCERTAIN.
- What chat SDKs do: Exyte Chat - CONFIRMED, the list is built on UIKit UITableView (README: onWillDisplayCell, performBatchUpdates), iOS 17+. https://github.com/exyte/Chat . Stream Chat SwiftUI - CONFIRMED (their blog): ScrollView + LazyVStack, "flipped"; they compared it with List and chose LazyVStack for flexibility (https://getstream.io/blog/build-message-list-swiftui/). The 180-degree flip trick is old (2019), UNCERTAIN currency. I did not find comparative measurements of List vs LazyVStack vs UICollectionView - no numbers.
- Conclusion (mine, engineering): for 100k messages, variable heights, prepend/append and jump-to-date, the most predictable option is UICollectionView/NSCollectionView (or UITableView like Exyte) with UICollectionViewDiffableDataSource, pagination from GRDB and anchor preservation (index + offset) when inserting at the top; cells on UIHostingConfiguration (iOS 16+). Pure SwiftUI is acceptable for an MVP with a bounded window (a few hundred items in memory) and height caching, but the risk of jumps remains. On macOS - NSCollectionView/NSTableView with NSHostingView; the behavior differs from iOS, plan a separate verification.

## 5. Forest (isometric calendar)

- SceneKit: CONFIRMED - at WWDC25 (session 288) a "soft deprecation" was announced: maintenance mode (critical bugs only), no new features, no hard deprecation planned (Apple promises advance notice), new projects are recommended to use RealityKit; there is a sample "Bringing your SceneKit projects to RealityKit" (iOS 26+). https://developer.apple.com/videos/play/wwdc2025/288 ; https://developer.apple.com/documentation/realitykit/bringing-your-scenekit-projects-to-realitykit . A third-party note's claim that SwiftUI SceneView is "formally deprecated in iOS 26" - UNCERTAIN, not confirmed by Apple.
- SpriteKit: CONFIRMED partially. A DTS answer on the forum: the framework is NOT deprecated, there is no deprecation marker in the iOS 26 SDK headers; Apple does not comment on plans (https://developer.apple.com/forums/thread/830810 , https://developer.apple.com/forums/thread/826562). I did not find an official "use SpriteKit" recommendation. There are complaints about FPS drops on iOS 26.x (https://developer.apple.com/forums/thread/816719; per the report it was fixed in 26.2 and came back in 26.3) - UNCERTAIN, a single thread. SpriteView in SwiftUI works.
- Canvas vs SpriteKit vs RealityKit for ~400 sprites with hit-testing, zoom/pan: I did not find official guidance/benchmarks. My analysis, not fact: 365 tiles + trees is a very small load. SwiftUI Canvas (immediate mode, images resolved once, TimelineView for the growth animation) is quite sufficient; hit-testing is computed manually (inverse isometric projection + z-order by depth), which is trivial for a grid. SpriteKit provides ready-made animations/particles/camera, but carries risk (maintenance, FPS regressions). RealityKit is overkill for 2D sprites. Recommended: Canvas + your own math, with sprites pre-rendered into atlases.

## 6. On-device AI

- Foundation Models: CONFIRMED availability iOS/iPadOS/macOS/visionOS 26.0+ (https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel). Availability depends on the device and region with Apple Intelligence; states .available / .unavailable(.deviceNotEligible / .modelNotReady / ...). There are `contextSize`, `tokenCount(for:)`, `supportedLanguages`, `supportsLocale(_:)`; model versions: 26.0-26.3, 26.4, 27.0.
- Context size: 4096 tokens (shared between input and output) - UNCERTAIN-CONFIRMED: secondary sources agree (https://www.infoq.com/news/2026/03/apple-foundation-models-context); `contextSize` and `tokenCount` appeared in 26.4 (per the same sources). Read `contextSize` at runtime, do not hardcode it. For notes: map-reduce/summarization in chunks.
- Russian language: the list of supported Apple Intelligence languages at https://support.apple.com/en-us/121115 (dated 2026-09-14) - 16 languages, Russian is NOT among them (per the result of reading the page; re-read the page itself, this is the result of a retelling). Conclusion: Russian in Foundation Models is most likely NOT supported -> treat as WRONG for "works in Russian" plans; verify on the device via `supportedLanguages`. Also from the forum: the model is unavailable when the device language is outside the list (https://developer.apple.com/forums/thread/805378).
- NLContextualEmbedding: CONFIRMED iOS 17+/macOS 14+. Produces a sequence of per-token vectors (not one vector per text), has `dimension`, `maximumSequenceLength`, `languages`, `scripts`, requires `requestAssets` and `load()`. Russian support: UNCERTAIN - the models are tied to scripts (from my memory, a Cyrillic model exists), but it cannot be confirmed without running `NLContextualEmbedding.contextualEmbeddings(forValues:)` on a device. NLEmbedding.sentenceEmbedding - Russian UNCERTAIN (not checked). For reliable Russian semantics, expect to need your own CoreML model (for example, multilingual-e5/MiniLM, converted) - this is my recommendation, not a fact from a source.
- Vision feature prints (VNGenerateImageFeaturePrintRequest) and classification: the page did not open -> UNCERTAIN; from memory the API has existed for a long time (iOS 13+), similar-image search is supported; searching images by a text query would require a CLIP-like model.
- SpeechAnalyzer: CONFIRMED iOS/iPadOS/macOS/tvOS/visionOS 26.0+. Modules (SpeechTranscriber), AsyncSequence input, asset download via AssetInventory, support for files and the microphone. https://developer.apple.com/documentation/speech/speechanalyzer . The list of locales, including Russian, - UNCERTAIN: check `SpeechTranscriber.supportedLocale(equivalentTo:)` and `supportedLocales`.
- sqlite-vec: CONFIRMED "pre-v1, expect breaking changes", sponsors Mozilla and others, ~8.2k stars, 159 open issues. The README does not mention iOS. https://github.com/asg017/sqlite-vec . There are third-party Swift wrappers (jkrukowski/SQLiteVec, v0.0.14, iOS builds pass; SQLiteVecKit) - CONFIRMED via the Swift Package Index. ## 7. Capture surfaces and the shared DB

- 0xdead10cc: CONFIRMED. An app suspended while holding a file/SQLite lock (especially in an App Group) gets killed; Apple advises beginBackgroundTask (for extensions - ProcessInfo.beginActivity) before writing; the problem shows up most often specifically for files in the shared container. iOS 14b7+ became "more lenient" towards flock. Marco Arment's advice is not to keep the DB in the shared container. GRDB offers an experimental "database suspension" technique (after it, queries fail with SQLITE_INTERRUPT/ABORT and need to be resumed). https://developer.apple.com/forums/thread/728957 ; https://mjtsai.com/blog/2025/05/15/sqlite-databases-in-app-group-containers-dont/ ; https://mintlify.com/groue/GRDB.swift/guides/sharing-a-database
- Safe architecture (my recommendation): extensions (Share Extension, Intents, widgets, Control) do NOT open the main DB; they write to a small "inbox" (JSON files + attachments in the App Group container, atomic write via rename) and/or to a separate tiny SQLite with short transactions and closing the connection; the main app picks up the inbox on launch/activation and inserts into the main DB. This way the main DB lock never crosses the suspension boundary.
- Availability by surface: Share Extension, App Intents/Shortcuts (including the Action button, input without opening the app), interactive widgets (iOS 17), Control Center controls (ControlWidget, iOS 18), Lock Screen widgets - all of these exist; the ControlWidget pages did not open -> availability on macOS 26 (Control Center controls) UNCERTAIN. macOS menu bar and global hotkey: via NSStatusItem/MenuBarExtra and Carbon RegisterEventHotKey or a library (for example, KeyboardShortcuts) - UNCERTAIN as the "recommended path" (not checked); the app lives in a single process, so there are no App Group problems - it can write directly to the main process's DB.

## Stack recommendations

1. DB: GRDB (SQLite, WAL) as the single source of truth + FTS5 (external-content table, unicode61 tokenizer with remove_diacritics; for Russian morphology, stemming is not available in SQLite out of the box - a custom tokenizer/lemmatization or prefix search is needed; UNCERTAIN/mine). Store attachments as files next to the DB, metadata in the DB. Do NOT use SwiftData. SQLCipher - only if a custom encryption layer is needed; CloudKit encryptedValues already protects the cloud.
2. Sync: CKSyncEngine directly with your own wrapper over GRDB (outbox, tombstones, storing system fields/changeTag), or SQLiteData as a ready-made option - but first read its limitations (UUID PK, FK, assets). All user fields in encryptedValues from day one. Attachments - CKAsset, treat the ~50 MB limit as conservative; account for the iCloud quota in the UX. Design a transport abstraction in case of Android/Web (CloudKit JS - sign-in via Apple ID only, not a native path).
3. Editor: store plain Markdown. Parser - swift-markdown (UNCERTAIN, verify) for the AST. Editing - either a thin wrapper around NSTextView/UITextView (TextKit 2) with AST-based highlighting and "hide markup outside the cursor" behavior (as in Bear), or TextEditor with AttributedString (iOS/macOS 26) for the first version, if live Markdown is not critical. STTextView - only if the GPLv3/commercial license is acceptable. For display - your own renderer from the AST or Textual (young, assess stability); avoid MarkdownUI (maintenance mode).
4. Feed: UICollectionView/NSCollectionView + UIHostingConfiguration/NSHostingConfiguration, diffable data source, pagination window from GRDB, anchor preservation on prepend, height cache, jump-to-date via an index offset query. SwiftUI ScrollView+LazyVStack+ScrollPosition - only as a quick prototype; re-verify on iOS 26/27.
5. Forest: SwiftUI Canvas (+TimelineView for animation) with manual hit-testing and zoom/pan gestures; pre-rendered sprite atlases. SpriteKit - fallback option (not deprecated, but FPS regressions on 26.x in reports). SceneKit/RealityKit - not needed.
6. AI: FTS as the basis of search. Semantics - optional and later: NLEmbedding/NLContextualEmbedding after verifying Russian on a device, otherwise a CoreML model; store vectors as BLOBs in GRDB, brute force via Accelerate; sqlite-vec - optional and with the pre-v1 caveat. Foundation Models - only as an optional feature (no Russian per the Apple Intelligence list, 4096 tokens, AI devices only). Transcription - SpeechAnalyzer (iOS/macOS 26+), verify the Russian locale.
7. Capture: extensions write to an inbox (files/a small SQLite), not to the main DB; the main app imports. On macOS - direct writes from the main process.

## Main technical risks
1. CloudKit conflicts and schema evolution: already existing fields cannot be encrypted, the production schema only grows; a mistake at the start is expensive.
2. Feed: position jumps in SwiftUI lists with variable height, iOS 26/27 differences; requires a UIKit/AppKit implementation and tests at 100k.
3. Attachments and the iCloud quota: asset limit, batching (400 items/2 MB without assets, asset tokens), quotaExceeded, video volume.
4. 0xdead10cc with a shared DB in an App Group: solved by the inbox architecture.
5. Russian in on-device AI: Foundation Models probably does not support it; NLContextualEmbedding/SpeechAnalyzer have not been verified for Russian - a risk for "semantic search" and "auto-notes".
6. Less mature dependencies: Textual 0.x, sqlite-vec pre-v1, Harmony abandoned, STTextView GPLv3.
7. Android/Web: CloudKit gives no native path; early lock-in to it will complicate future cross-platform work.
8. Platform regressions (SpriteKit FPS on 26.x, SwiftUI scroll on 27, TextKit 2 bugs): a regular test on every OS point release is needed.
